## Findings (verified)

### F1 — HIGH: an enrolled TOTP secret can be read again with only a session and the password

- `/two-factor/get-totp-uri` (`totp/index.mjs:70–112`) uses only `sessionMiddleware`. It decrypts the stored secret and, after a password check, returns it inside `totpURI`.
- Nothing in `src/` calls it. Enrolment takes the URI from `/two-factor/enable` (`src/app/(auth)/aktifkan-2fa/enrol-form.tsx`), and the Better Auth client does not call it on its own.

### F1b — HIGH (plan review round 1, both reviewers): backup codes can be minted with only a session and the password

- `/two-factor/generate-backup-codes` (`backup-codes/index.mjs:240–305`) needs the session and the password. It returns 10 new plaintext codes.
- Those codes pass the sign-in challenge and the step-up endpoint `verify-backup-code`. A step-up success sets `second_factor_at`, which `vendor_guard` uses for vendor writes.
- So the holder of a session and the password gets a lasting second factor without the device.
- The current rule (DEC-033, T-023 "regenerate backup codes after a password re-check") allowed this. **DEC-041 (1) supersedes that part.**

### F2 — MEDIUM: wrong codes sent from an open session are never counted

- The plugin decides sign-in or step-up through `verifyTwoFactor` (`verify-two-factor.mjs:14–15`): `getSessionFromCtx` resolves a **valid** session from the database. A missing, expired or revoked session counts as a sign-in.
- With a valid session, `verify-totp` (`totp/index.mjs:139–170`) and `verify-backup-code` (`backup-codes/index.mjs:193–234`) skip all of these: `assertTwoFactorNotLocked`, `beginAttempt` and `recordTwoFactorFailure`.
- A success sets `auth_session.second_factor_at` (after hook, `SECOND_FACTOR_PATHS`).
- DEC-010 ("5 failed codes lock 15 min") therefore holds only at the sign-in step.

### F3 — LOW: backup-code storage is never asserted

- `tests/auth/auth.test.ts` selects `t.backup_codes` without an assertion.
- Storage relies on the default `storeBackupCodes: "encrypted"` (`two-factor/index.mjs:26`).

### 1. Before hook: order of checks

1. Surface (foreign session) and the vendor address allowlist (existing).
2. `/two-factor/get-totp-uri` refused unconditionally (below), so it never claims an attempt.
3. The session gate (existing: locked or not-yet-enrolled sessions).
4. The RATE-2 claim for password endpoints (existing; it includes `/two-factor/disable` and `generate-backup-codes`).
5. For `disable` and `generate-backup-codes`: the required code is validated (6 digits) and verified through the nested `auth.api.verifyTOTP`, which change 2 counts.
6. The plugin's own password check (inside the endpoint).

Classification and counting for `verify-totp` and `verify-backup-code` (change 2) run after step 3. A request refused by steps 1–3 (foreign surface, disallowed vendor address, locked or not-yet-enrolled gate) is never classified or counted (test 2.11).

So a wrong authenticator code on `generate-backup-codes` keeps exactly one RATE-2 claim and adds exactly one second-factor failure (test 2.2).

- **`/two-factor/get-totp-uri` is always refused:** `FORBIDDEN`, code `TOTP_URI_UNAVAILABLE`, no data.
  - It is removed from `PASSWORD_PATHS` and `ENROL_PATHS`.
  - A comment explains that the URI is returned only at enrolment (`/two-factor/enable`).
- **`/two-factor/generate-backup-codes` needs a current authenticator code** in addition to the password, the same pattern as `/two-factor/disable`:
  - It follows the order above. Step 4 is the RATE-2 claim. Step 5 validates the body `code`, which must be 6 digits or the request gets 401 `INVALID_CODE`, then verifies it through `auth.api.verifyTOTP` with the request headers. Step 6 is the plugin's password check.
  - The nested call goes through the hooks, so it is counted by change 2 and refused while locked.

### 2. Per-account counting for codes verified from an open session (step-up and enrolment)

- **Classification, once, in the before hook,** for `/two-factor/verify-totp` and `/two-factor/verify-backup-code`:
  - Use `sessionRow(ctx.headers)`: a **valid** session of this surface, read from the database the way the plugin's `getSessionFromCtx` does. Not cookie presence.
  - If there is no such row, it is a sign-in. The plugin counts it; this hook does nothing.
  - If there is a row, it is session-bearing (step-up, or enrolment completion). The classification `{ userId }` is stored for this request in a `WeakMap` keyed on the request headers object, which is the same object in the after hook. It is never re-derived after verification: a successful enrolment replaces the session (`totp/index.mjs:157–166`).
- **Counting, for a session-bearing call, in one transaction:**
  - `select … for update` the user's `auth_two_factor` row (this row lock serializes concurrent counts). If there is none, do nothing: the plugin answers `TOTP_NOT_ENABLED` or `BACKUP_CODES_NOT_ENABLED`.
  - **Expired lock reset:** if `locked_until` is set and `<= clock`, set `failed_verification_count = 0` and `locked_until = null` first, as the plugin does at sign-in (`verify-two-factor.mjs:134–149`).
  - If `locked_until > clock`, refuse: 429, code `ACCOUNT_TEMPORARILY_LOCKED` (the plugin's code and message).
  - Otherwise count this attempt: `failed_verification_count + 1`. When it reaches 5, set `locked_until = clock + 15 min`.
  - **Serialization:** the row lock (`select … for update` on the user's `auth_two_factor` row) is what serializes concurrent counts for one user.
    - The advisory lock is not added: the row exists whenever there is anything to count, and the row lock already orders the read and the write.
    - The mutation that matters is removing the row lock (a plain `select`). Test 2.12 makes it deterministic.
- **Settlement, in the after hook:** on success, look up the stored classification and reset that user's row by `user_id` (`failed_verification_count = 0`, `locked_until = null`). A failure keeps the counted attempt. Success means no `APIError` in `ctx.context.returned` and no status ≥ 400, the existing check.
- **Clock:**
  - The plugin reads and writes `locked_until` with `Date.now()`. The new code uses the same clock, `Date.now()` (not the injected `config.now`), so both paths judge one field on one clock.
  - The tests move time with `vi.setSystemTime` (fake `Date` only, `toFake: ["Date"]`), which moves both. TOTP codes for the tests are generated at that same time.
- **Interactions:**
  - **`/two-factor/disable` and `generate-backup-codes`** call `auth.api.verifyTOTP` from the before hook. That nested call is session-bearing, so it is counted once by this code, and refused while locked. The outer endpoint is not a verify path, so there is no double count.
  - **Sign-in is unchanged:** the plugin counts it. A session-bearing request is never counted by the plugin.
  - **Vendor surface:** the same code path. `sessionRow` is surface-bound, and the allowlist check runs earlier in the hook.

## Risks

- **A lost authenticator** (DEC-041 (1) consequence, corrected after plan review round 3):
  - A remaining backup code still recovers **sign-in**.
  - **Replacing** the authenticator still needs a current code from the old one: `/two-factor/disable` asks for it, and `/two-factor/enable` refuses to replace a verified authenticator.
  - So when the old authenticator is unavailable, replacement needs assisted recovery (an admin reset), with or without backup codes left. This is a support procedure, not built in M0.
  - The possession guards stay. A backup code is never accepted in place of the current authenticator code; that would be a new recovery decision with its own task.
- **Better Auth upgrade:** if the plugin starts counting session-bearing attempts itself, test 2.9 and the double-count mutation make it visible.
- **Changing system time in tests:** only `Date` is faked; timers and the database keep real time. The plugin and the new code both use `Date.now()`, so they stay consistent.
