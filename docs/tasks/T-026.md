# T-026 — Support-session scope approval and read audit (PR-60, TEN-14)

## Requirement

- **PR-60:** platform-level vendor views show counts and status codes only; clinic data is reachable only in a support session (PR-53) that the owner sees in Saya › Akses Vendor, can end, and must approve first when the scope includes clinical data or specific personal data (TEN-14); every record read in a session is listed to the owner; infrastructure access (SEC-20) is reported the same way.
- **TEN-14 (the parts left after T-025):** owner approval before a scope with clinical kinds or specific personal data activates, and again for a clinical-scope extension; every record read is audited (object kind, id, time) and shown to the owner grouped by session.
- **Scenarios (02 §8):**
  - *PR-60 owner sees vendor access:* a support session opened for tenant A; the owner's Akses Vendor data shows operator, reason, scope and end time, and the owner can end it.
  - *PR-60 clinical scope without approval:* a session request whose scope includes specific personal data; while the owner has not approved it, it does not activate and the request is audited.
  - *PR-60 expired grant:* an onboarding grant created 31 days ago, tenant not live: the catalog is denied (built in T-024; re-run here as part of Done-when).
- **Done when (TASKS.md):** scenarios PR-60 (owner sees access, clinical scope without approval, expired grant) pass.

## What exists (T-025)

`support_sessions` with `pending_approval` for any scope containing a `personal` or `clinical` table (no way to activate it yet); `support_session_end_by_owner`; `support_session_reads` (rows touched, possibly forged for made-up ids); `support_bind_tickets` (`ticket_issued` in the tenant chain = one access window per read transaction); bind refusals in `vendor_actions` with `tenant_id` null and `object_id` = session.

## Design (one migration, 0047: functions and two indexes, no new table)

1. **`support_session_owner_decide(session, approve boolean)`** — clinic_app, Owner only (`onboarding_owner()`: acting role owner, takes the tenant's `staff_access` lock first). Lock order as T-024/T-025: `staff_access` → session row `FOR NO KEY UPDATE` → audit.
   - Refusals (audited in the tenant chain and committed; return `refused:<code>` like `vendor_dual_identity_clinic_decide`): `not_found` (not this tenant), `not_pending` (already active/ended), `tenant_closed`, `operator_inactive` (approve only: opener no longer active vendor staff), `approver_is_requester` (approve only: the Owner's account is the opener's account — a dual identity; rejecting is the safe direction and stays allowed), `invalid_input` (no decision). No free-text reason: `audit_events.reason` is reserved for break-glass (as the dual-identity decision).
   - **Approve:** `pending_approval → active`, `activated_at = clock_timestamp()`, `ends_at = activated_at + minutes` (the TTL starts at approval, as T-025 decided). Audit `support_scope_approved` (actor = Owner) and a vendor-log row so the console sees it.
   - **Reject:** `pending_approval → ended`, `end_reason = 'owner'`, audit `support_scope_rejected`.
2. **Extension of an approval-scoped session:** stays refused (`needs_owner_approval`, T-025). TEN-14 allows *at most* one extension and requires the owner's approval again for a clinical-scope extension; the operator opens a new session, which needs a new approval. Stricter than the spec for personal scopes (owner may relax later; recorded in DECISIONS.md).
3. **Owner listing (Akses Vendor data, page T-028)** — clinic_app, Owner and Admin Pusat (19: "Akses Vendor (owner; Admin Pusat read)"):
   - `support_sessions_for_owner()` → every session of the tenant, newest first: operator name, purpose, scope with classes, state (`expired` when active past its end), requested/activated/ends/ended times, extension reason, end reason, `needs_approval`, counts of access windows (tickets issued), refused binds and listed reads.
   - `support_session_reads_for_owner(session, offset, limit)` → the session's access windows (ticket issue = "access window opened", bound or not), refused binds, and **every** read record (object kind = table, id, first read time), a page at a time (limit 1–500), each flagged `row_found`: true (the row exists now in this tenant), false (deleted since, or never this tenant's — a forged record, shown as evidence), null (not checkable). Revised in review round 1: hiding unmatched records would also hide real reads whose row was deleted later (TEN-14 "every record read is listed").
   - `support_read_row_exists(table, tenant, id)`: `public.` tables in `support_object_kinds` (not `never`) only, resolved through `pg_class`/`pg_namespace` (never `search_path`), and only when the table has uuid `id` and `tenant_id` columns; otherwise null. A test checks every classed table is checkable.
   - Counts in the session list are plain `count(*)` (no per-record check), so the list cost does not grow with what an operator read.
4. **Scenario "clinical scope without approval":** WhatsApp messages do not exist yet. The test uses a scope with a `personal` table (specific personal data class) and a test-only `clinical` table registered in the throwaway database, shows both stay `pending_approval`, cannot bind, and the request is in the tenant chain (`awaiting_owner`). The messages/media tables must be classed `personal` or `clinical` when they arrive (TEN-14 lists them as specific personal data).

## Acceptance (runnable) — `tests/vendor/support-scope.test.ts` (as built)

- **PR-60 owner sees access:** operator, purpose, scope with classes, state, minutes and end time; the Owner ends the session and reads stop.
- **PR-60 clinical/personal scope without approval:** a scope with a clinical (test-only table) or personal table stays `pending_approval`, cannot bind (`awaiting_owner`), and the request and the refused read are in the tenant chain. Approval activates it (TTL counted from approval, also for a back-dated request); the clinical read works and is listed to the Owner (`row_found: true`); the approval is attributed to the Owner's staff id.
- **PR-60 expired grant:** a tenant moved to onboarding through the console; the catalog is open, then denied once the grant is 31 days old.
- **Approval rules:**
  - only the acting Owner decides: Admin Pusat and a manager get `ERR_FORBIDDEN` and the session stays pending (tested). The refusal is raised by `onboarding_owner()`, so it rolls back and writes no chain row, as `support_session_end_by_owner` (by design; no assertion counts chain rows for it);
  - another tenant's Owner gets `not_found`, written to that tenant's chain (tested); a NULL session is refused with `P0002` (tested; the SQL raises before any audit write); no decision returns `refused:invalid_input` (tested; its chain row is not asserted);
  - only a pending session (`not_pending` otherwise); a rejection ends it (`owner`) and is final;
  - approve refused for a closed tenant (`tenant_closed`), an inactive operator (`operator_inactive`) or the opener's own account (`approver_is_requester`); rejecting stays allowed in the last two cases;
  - chain rows asserted: `support_scope_not_found`, `support_scope_rejected`, `support_scope_not_pending`, `support_scope_operator_inactive`, `support_scope_tenant_closed`, and `support_scope_approved` attributed to the Owner's staff id. The SQL writes a chain row for every returned refusal, including `invalid_input` and `approver_is_requester`, but those two rows are not asserted. The vendor log gets `approved_by_owner` / `rejected_by_owner` (both asserted).
- **No extension** of an approved personal or clinical scope (`needs_owner_approval`).
- **Access log:**
  - one stream of events (`window`, `refused`, `read`), oldest first, with totals per kind, paginated as a whole (limit 1–500; out of range refused in the module and in SQL);
  - every read record is listed, none hidden: `row_found` true (asserted for config, personal and clinical reads) or false for a deleted row or a forged record (a made-up id or another tenant's real id; asserted). The value null (table not checkable) is asserted on `support_read_row_exists` directly, not through a `sessionLog` event;
  - events with the same time keep one order across pages;
  - a pending session of a closed tenant is not `needs_approval`; an active session past its end is `expired`;
  - each readable-class (`support_class <> 'never'`) catalog entry of the migrated schema, excluding the test-only clinical table, returns false for a random id (asserted individually, before the test adds its invalid entries); the clinical table is checked separately through a real read (`row_found: true`). Being classed is not enough: the SQL also requires a `public.` name and uuid `id` and tenant columns, and returns null otherwise, never an error (asserted on examples: a `never`-class table, a platform table, an unqualified name, a `pg_temp` name, a classed `config` table without a tenant column);
  - Owner and Admin Pusat read; a manager is refused; another tenant's Owner sees no session and gets `not_found` for the log.
- **Privileges:** `clinic_app` cannot read the support tables or call `support_read_row_exists`; `clinic_vendor` cannot decide; `clinic_operator` cannot list.
