**Root cause, stated to the strength of the evidence:** concurrent database creates and drops by the
integration harness are a demonstrated cause of multi-hundred-millisecond to multi-second stalls of new
connections on this disk (the mechanism is in the PostgreSQL source, and the stall is reproduced; in the
measured runs serializing creates lowered the worst samples and the relation-map waits). It is the most likely cause of the 5 s test timeout, but that run lacks
the samples to prove it. The residual spikes are consistent with migration fsync prolonging a single
create's relation-map hold; that mechanism is not established independently, this change does not remove
it, and its share is not measured.

## Change

In `tests/rls/harness.ts`, plus `tests/db/migrations.test.ts` for its own creates and drops:

- **One lock helper, used only by the two wrappers below, exported from `tests/rls/harness.ts`:**
  - `withDatabaseDdlLock(server, mode, fn)` takes `pg_advisory_lock(K)` for a create
    (exclusive) or `pg_advisory_lock_shared(K)` for a drop, runs `fn`, and unlocks in `finally`.
  - **Error precedence and cleanup:**
    - Acquisition fails: neither the callback nor the unlock runs, and the acquisition error is thrown.
      The caller still owns, and ends, its connection.
    - Operation throws and the unlock succeeds: the operation's error is thrown.
    - Operation throws and the unlock fails: the helper ends the connection, which releases the session
      lock. The operation's error stays the thrown one; the unlock error is attached as its `cause` only
      when it has none.
    - Operation succeeds and the unlock fails: the helper ends the connection and throws the unlock
      error. A drop that happened is not hidden by a successful return over a connection in an unknown
      state.
    - Ending the connection is best effort and never replaces the error being thrown.
    - **What an unlock failure leaves behind, and who cleans it:**
      - In `createHarness`, a create that succeeded but whose unlock failed leaves the new database,
        because the error path can no longer drop it over the ended connection.
      - In `close()`, the drop then cannot be followed by `drop_roles` on that connection, so its roles
        stay.
      - Both are removed by a later harness's stale sweep: the per-database lifetime lock was released
        when the session ended, so the sweep may claim them.
      - A second `server.end()` from the caller after the helper ended the connection is tolerated
        (caught and ignored).
- **The key K** is a fixed bigint above 2³¹, outside `hashtext()`'s int32 range (the per-database keys) and
  different from `MIGRATION_LOCK_KEY` (7 202 611 020). It is stated in the file with that reason.
- **Scope of the lock:**
  - Advisory locks are per database. Every participant takes the lock on a connection to the same admin
    database (`TEST_DATABASE_URL` or the local default). The helper and this document state that
    invariant. CI uses one URL for all files.
- **Where it is used:**
  - The harness: `CREATE DATABASE`, the stale sweep's drop, the drop after a failed migration, and
    `close()`'s drop.
  - `tests/db/migrations.test.ts`: its creates and drops, through the exported helper.
  - The lock is held only around the single statement. Migrations, role work and tests run unlocked and in
    parallel.
- **Lock order** (no deadlock): a harness takes its own per-database lifetime lock first and the DDL lock
  only around the statement. While holding the DDL lock it never performs a blocking acquisition of
  another harness advisory lock. The CREATE/DROP statement itself still takes ordinary PostgreSQL locks.
  The sweep's per-database locks are `pg_try_advisory_lock` (non-blocking).
- **Error paths:**
  - `createHarness` wraps everything after `server.connect()` so `server.end()` always runs on a throw:
    in the sweep, the create, or the drop after a failed migration.
  - Today a throw there leaks the session, and with it the per-database lock (and with this change the
    DDL lock) until the worker exits.
- **Timing:**
  - `close()` records a separate `lock_wait` step (HYG-004's per-step report), so a slow close shows
    whether the time was waiting or dropping.
  - `createHarness` records its lock wait the same way. It is printed only when slow (≥ 5 s, the HYG-004
    threshold).
- **Test-only options** (passed only by `tests/rls/harness-lock.test.ts`; the structural test checks
  `ddlLockKey`):
  - `ddlLockKey`, `afterAcquire`, `run`, `slowMs`;
  - `onLockWait` (the measured wait, reported whether or not the acquisition succeeded; an error it
    throws is ignored, so it can never leave an acquired lock without its unlock handling);
  - `observerName` and `observer` (the observer connection's name and factory);
  - `migrate` and `stalePattern` on `createHarness`, and `pattern` on `sweepStaleDatabases`.
- **The sweep** keeps a failed drop's error: after a failure its own per-database unlock may fail on
  an ended connection, and that error is ignored (the ended session released the lock).
- **No change** to `vitest.config.mts`, migrations, product code or CI.

**Rejected:**

- **Template database.** Each file would no longer migrate from zero (migration coverage). Database
  privileges are not copied from a template, so migration 0003's `REVOKE CONNECT, TEMPORARY … FROM PUBLIC`
  would have to be re-applied by hand. It adds a global setup. Its performance with serialized creates
  and drops was the best in the exploratory loop. It is rejected for coverage and complexity, not
  performance.
- **Exclusive lock on drops.** It nearly triples forced checkpoints (18 → 48) and makes `close()` about
  about 5× slower than the shared variant and 6–13× slower than the current harness (run-level p50 1 278–1 335 ms against 232–285 and 97–200 ms).
- **A longer test timeout.** It hides the stall.

## Lock wait policy

- **Waits are unbounded inside the helper and bounded by the hook.** A create or drop waits only for other
  harness DDL statements: one statement at a time for creates, about 0.5 s each in the stress. A
  `lock_timeout` here would only turn a long queue into a failed file.
- **A vitest hook timeout does not end a pending query or its connection.** The hook fails at 120 s; the
  worker's connections end when the worker process exits after the run. The error-path cleanup above
  covers throws, not a hook timeout.
- **Diagnostics instead of a bound.**
  - When the wait for the DDL lock passes 5 s (the HYG-004 slow-close threshold), a timer fires while the
    acquisition is still pending. It opens a separate connection to the admin database, which an
    advisory-lock query queued on the waiting client could not use.
  - That connection reads the holder backends (`pg_locks` for that advisory key joined to
    `pg_stat_activity`: pid, state, the first 60 characters of the query). The harness prints one stderr
    line, then closes the observer connection.
  - Diagnostics are best effort: an observer failure prints a short note and never affects the lock or
    the operation.
  - **As built (implementation review round 1):** the report never delays the operation. When the
    acquisition settles (granted or failed), a report still in flight is cut off by ending its
    connection, and its line is then not printed: a wait shorter than the time the observer needs prints
    nothing. The observer connects and queries with 2 s timeouts.
  - The timer is cleared, and a still-open observer is closed, on every settlement path: acquired, failed
    or thrown.
  - Round-1 LOW (bounded wait) is answered this way: a report while waiting, not a timeout.

## Test isolation (other files run at the same time)

`pnpm test` runs other files beside the lock tests, and their harnesses take the real key. Identity alone
cannot keep those harnesses out of a positive "did not wait" check, because PostgreSQL's fair queue lets
an unrelated waiting exclusive request delay a correct shared request. So the lock tests do not share
the real key:

- **Per-test key.** The helper, both wrappers, `createHarness` and `sweepStaleDatabases` accept a
  test-only `ddlLockKey` option (default: the real key K). Each lock test draws its own key above 2³¹,
  distinct from K, `MIGRATION_LOCK_KEY` and every other test's key, so no other participant can hold or
  queue on it.
  - The structural test (12) checks that no file under `tests/` passes `ddlLockKey` except
    `tests/rls/harness-lock.test.ts`, and that the default is K.
- **Identity.** The test's own connections set a known `application_name`, and harness connections
  set `application_name = 'harness:<dbName>'`. Waits are matched on that identity, with
  `granted = false` and the expected `mode`, never on "any waiter for the key".
- **Barrier after acquisition.** The helper accepts a test-only `afterAcquire` hook. It awaits the hook
  after taking the lock and before running the statement. A test uses it to observe the participant's
  granted lock row, then releases the barrier explicitly. A finished wrapper has already unlocked, so
  its row cannot be observed afterwards.
- **Migrations paused by a barrier.** `createHarness` accepts an injected migration runner (test-only
  option; default `runMigrations`). The runner signals and then waits on a barrier.
- **Stale sweep.** `sweepStaleDatabases(server, { pattern })` takes the name pattern (default
  `^rls_[0-9a-f]{12}$`, what the harness uses). The test creates a stale database with a test-only
  prefix that no other file's sweep matches. So only its own sweep can claim it; no lifetime-lock handoff
  is needed.

## Risks

- **A test process holding the lock.** These are session locks: released when the connection ends, so a
  killed worker cannot block later runs. A live worker that leaks a connection is closed by the error-path
  change. A vitest hook timeout alone does not end the connection: that is why the error paths close it
  explicitly.
- **Lock waits counted against a hook.** `createHarness` runs in `beforeAll` (120 s, HYG-004); `close()` in
  `afterAll` (120 s). The stress shows `createHarness` p50 about 2 s and `close()` p50 about 0.3 s.
- **Helper misuse.** Session advisory locks are reentrant in PostgreSQL (each acquisition needs its own
  unlock). A shared-to-exclusive upgrade could wait on, or deadlock with, other sessions. So the helper's
  contract **prohibits** nested calls and upgrades; PostgreSQL does not prevent them by blocking. It is
  called only around a single statement. PostgreSQL's lock queue keeps newly arriving shared requests
  from passing a queued exclusive one, so drops do not starve a create.
- **CI** uses one admin URL for the whole job, so it gets the same serialization. Nothing else in CI
  changes.
