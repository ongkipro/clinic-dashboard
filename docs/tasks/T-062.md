## Open points (for the reviewer)

1. **Item class.** Proposal: `stock_items.material_class` `bulk` | `standard` | `precise` (default `standard`), set by pharmacist / purchasing / admin pusat through a new `stock_item_class_set(item, class)` (frozen? no: changing it affects only later consumptions; history keeps the class used on each consumption line). No UI in this task (the /stok item form is T-060's path; a follow-up adds the field).
2. **Request (selection never changes stock).** `material_requests` (tenant, branch, visit, plan item?, room depot, state `open` | `issued` | `reconciled` | `cancelled`, requested by/as/at) with `material_request_lines` (item, quantity requested; issued, consumed, returned, wasted running totals). Created by doctor / nurse / therapist / pharmacist for an open visit at the active branch; a request moves no stock (asserted). Request lines name stock items directly; linking the free-text catalog BHP recipe to stock items (the automatic list, PR-18) is T-065's (it is in `src/modules/catalog/**`, outside this task) — flagged.
3. **Issue (pharmacist).** `material_issue(request, from depot, lines?)`: per line FEFO in the source depot (`stock_fefo_depot`, fit stock only, CLIN-019), each pick written as two linked movements of kind `issue` on the same batch: out of the source depot (−q, leg `out`) and into the request's room depot (+q, leg `in`). The batch quantity is unchanged (stock moved, not used). `stock_movements_check` is widened so `issue` and `return` carry legs like transfers (0079 drops/re-adds the constraint; existing rows comply). An issue row (`material_issues`: request, source depot, by/as/at, command key unique) records the picks (`material_issue_lines`: request line, batch, quantity).
4. **Consumption (one per execution item, CLIN-008).** `material_consume(request, lines)` once per request (`material_consumptions` unique (tenant, request)): per line the performer confirms the actual quantity (default = issued, deviations only). By class:
   - `standard` / `precise`: `consume` movements (−q) from the room depot on the issued batches (FEFO among the request's issue lines; `precise` requires the batch named on the line).
   - `bulk`: the pack already left usable stock when it was issued to the room; consumption records the estimated quantity on the line (`estimated = true`) and writes **no movement**. The room depot holding of a bulk item falls only through room counts (T-060/T-061 counts per depot) — the one coherent method; PR-16's scenario asserts the batch quantity unchanged by the completion.
   - A retried consumption with the same key replays; a second consumption for the request (another key) is refused `ERR_VERSION_CONFLICT` and moves nothing.
5. **Return (pharmacy acceptance).** `material_return_propose(request, lines, condition)` by room staff (`unopened` | `opened` | `damaged`; stock stays in the room depot, state `pending`), `material_return_decide(return, accept_to depot?, outcome)` by the pharmacist: `usable` → `return` legs room → pharmacy depot (out/in, batch unchanged); `waste` → `waste` movement from the room depot; `hold` → `return` legs into the pharmacy depot and the batch? no — holding a single return without quarantining the whole batch is not modelled; proposal: `hold` is not offered; uncertain stock is decided by the pharmacist at once (usable or waste). Returnable quantity ≤ issued − consumed − returned − wasted per line.
6. **Waste.** `material_waste(request, lines, reason)` by room staff during or after treatment (contaminated/damaged material from the issued quantity): `waste` movement (−q) from the room depot, reason required. Disposal of pharmacy stock (pemusnahan, CD-21 approvals with witness and thresholds, SET-43) is not this task: flagged as a gap (no M3 task names it; proposal: T-068's B3 waste register or a hygiene task).
7. **Reconciliation.** A line is reconciled when consumed (non-bulk) + returned + wasted = issued; bulk lines reconcile at consumption (their remainder stays in the room depot by design). The request becomes `reconciled` when every line is; `material_request_cancel` before any issue cancels; after an issue only returns/waste can close it. Visit closure gating (CLIN-025) stays with T-064/T-065.
8. **Who and what is seen.** Writers: request (doctor, nurse, therapist, pharmacist at the active branch), issue and return decision (pharmacist at the branch; purchasing? no — clinical demand), consume and waste and return proposal (doctor, nurse, therapist at the branch). Readers: the same roles and manager at the branch; purchasing and auditor through `stock_card` (masked). RLS on the new tables through a `material_readable(tenant, branch)`; support class `personal` (patient-linked). Events `StockIssued` / `StockConsumed` / `StockReturned` / `StockWasted` with ids and codes only (no item names, no patient). Idempotency key on every command (`runCommand`).

## Plan review round 1 (Argon `79fbe2b5`): REVISE PLAN → adopted

Every finding was checked against the code before adoption: `stock_move_depot` clamps an open vial only when `remaining > depot balance` (0078:200-203), so a vial beside sealed stock in its depot is not run down; `stock_fefo_depot` returns a vial row and a sealed row for the same batch (items.test.ts:152-158) and the source key is unique per (source, batch, depot, leg) (0078:106); `plan_items` is unique on (tenant, id) only (0070:102); `stock_actor` gives a role other than manager/pharmacist the passed branch, not the active one (0077:239-246).

- **P1-1 (open vials, FEFO split, returns):** issue aggregates FEFO picks per (request line, batch) before writing legs and lines (one out/in pair per (issue, batch)); when an issue (source depot) or a consumption (room depot) takes from a (batch, depot) with a fit open vial, the writer lowers the vial by `least(remaining, taken)` and finishes it at 0; a waste in the room depot does the same, closing it `lapsed` when unfit else `finished`; a return accepted `usable` requires condition ≠ `damaged`, the batch fit (`ERR_STOCK_UNFIT`) and sealed quantity in the room depot (holding − open vial remaining ≥ quantity, as `transfer_take_lines`), so damaged, unfit or open-vial stock never becomes usable sealed stock elsewhere.
- **P1-2 (per-batch reconciliation):** new `material_wastes` (request, reason, command key unique per tenant, by/as/at) and `material_waste_lines` (request line, batch, quantity, unique (waste, batch)); one atomic issue per request (`material_issues` unique (tenant, request); every line issued, 0 < issued ≤ requested, default requested); extras during treatment are a new request (UX-9 Bahan Tambahan). Free quantity per (request line, batch) = issued − consumed − returned − wasted − pending return (returns in state `pending` reserve); when `batch_id` is omitted (standard), allocation runs over the line's batches with free quantity in FEFO order. A consumption line may be 0 (recorded, no movement; the units are returned or wasted). Reconciliation: non-bulk consumed + returned + wasted = issued; bulk consumed > 0 or returned + wasted = issued; after a bulk line is consumed, return and waste on it are refused (room counts own it). The request becomes `reconciled` when every line is and no return is pending.
- **P2 (plan item FK, actor):** `material_requests.plan_item_id` → `plan_items (tenant_id, id)` (as 0073/0076), checked in the writer and guard: not removed, of an active plan of the visit's patient. New `material_actor(roles)` / `material_reader()` on `tenant_actor_lock()` keeping the active branch for every Level 3 role, capability `existing_appointment` (or `configuration`); no 0077/0078 function is re-created (no T-060/T-061 function drift).
- **P3 (hardening):** `stock_movements_check` re-created in 0079 with the full kind/leg/sign table (receive > 0 no leg; adjust no leg; consume, waste, supplier_return, dispense < 0 no leg; transfer_out out < 0; transfer_in in > 0; issue and return out < 0 or in > 0); a new ENABLE ALWAYS trigger `stock_items_materials_guard` freezes `unit` / `vial_size` once a request line names the item (0077's guard untouched); lock order in every writer: staff_access → `material_requests` row → child header → batches (id order) → holdings (id order).
