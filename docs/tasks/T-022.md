# T-022 — Tenant lifecycle states and suspension effects (TEN-12, PR-56)

Status: Planned (starts after HYG-002 is reviewed and committed) · Risk: R3 (tenancy, vendor access) · Depends on: T-020 (vendor staff, maker-checker requests, `vendor_request_consume`), T-021 (vendor console, session-bound guard) · Executor: pi (cc/claude-opus-5-5)

## Requirement

- **PR-56:** the vendor manages each tenant through provisioning → onboarding → live → suspended → exit → closed, with reason and owner notice on suspend and exit. Suspension is manual and reversible by the platform owner with a reason. While suspended: new bookings, public pages and marketing stop; existing appointments, cashier, care messages (aftercare, reminders for existing bookings, complaint replies) and clinical read/export continue.
- **TEN-12:** the lifecycle state lives in the platform registry (`tenants_registry.lifecycle_state`). provisioning → onboarding requires the signed processor agreement and NDA (PRIV-8); no real personal data enters a tenant before it. suspended → live only by the platform owner with a reason. Suspended tenants keep clinical read/export, purpose reads, existing appointments, cashier, care messages, the SATUSEHAT outbox, record corrections, patient copies and data-subject requests; they lose new bookings, public pages (edge cache purged) and marketing messages.
- **Done when (TASKS.md):** Scenario PR-56 "manual suspension keeps records" passes (given a live tenant with an unpaid server fee, when the platform owner suspends it with a reason, then new bookings are refused, the owner is notified, and staff can still read and export clinical records). Suspended tenants keep care-message eligibility; the aftercare half of PR-56 completes in the aftercare task.

## Design

1. **History table `tenant_lifecycle_events`** (platform, DATA-48): `tenant_id`, `from_state`, `to_state`, `reason` (10–500 chars), `actor_kind` ('vendor_staff' | 'service'), `actor` (vendor staff id or service name), `vendor_request_id` (the consumed request, for suspension and exit), `at`. Append-only (guard trigger, ENABLE ALWAYS), no clinic_app access.
2. **Transition function `tenant_lifecycle_transition(...)`** (SECURITY DEFINER, `clinic_executor` only), called inside the effect transaction after `vendor_request_consume`:
   - Allowed edges: provisioning→onboarding, onboarding→live, live→suspended, suspended→live, live→exit, suspended→exit, exit→closed. Anything else is refused.
   - provisioning→onboarding requires the tenant's `processor_agreement_signed` evidence to be approved (the same rule as the gate; TEN-12/PRIV-8).
   - live→suspended and live/suspended→exit require a consumed vendor request of that kind for that tenant (maker-checker, PR-57).
   - suspended→live requires a consumed request of the new kind `reactivation`, which only a platform owner may request and another platform owner must approve. **Spec check:** PR-56 says "reversible by the platform owner with reason", 19 §3 lists "Aktifkan Kembali" next to Ajukan Suspend, and PR-57 makes vendor actions maker-checker. Reactivation as a second-person request keeps PR-57 intact. If the spec intends a single platform owner, this is an escalation.
   - Serialised per tenant (row lock on `tenants_registry`), writes the history row, emits a platform event `TenantLifecycleChanged` (ids only, 18 TD-13), and raises an owner notification on suspend and exit ("Klinik ditangguhkan" / "Proses keluar dimulai", reason shown to the owner) through a new notification type `tenant_lifecycle` (system-raised, owner recipient).
3. **Effect primitive for later tasks: `tenant_capability(p_tenant, p_capability)`** plus the TS `assertTenantCapability`. Capabilities and the states that allow them:
   - Allowed only in `live`: `new_booking`, `public_site`, `marketing_message`.
   - Allowed in `live` and `suspended`: `existing_appointment`, `cashier`, `care_message`, `clinical_read`, `clinical_export`, `purpose_read`, `satusehat_outbox`, `record_correction`, `patient_copy`, `data_request`.
   - `onboarding` allows configuration and synthetic data only (ARCH-10); it is covered by later tasks.
   - `exit` keeps read/export and data requests; `closed` allows nothing.
   - Refused calls raise `ERR_TENANT_SUSPENDED` (TD-51 code in Bahasa Indonesia: "Klinik sedang ditangguhkan. Hubungi vendor.").
4. **Executor service** `src/modules/vendor/lifecycle/lifecycle.ts`:
   - `suspendTenant(pool, requestId, tenantId)`, `reactivateTenant`, `startExit`, `closeTenant` and `advanceOnboarding` (no request; vendor onboarding role through the console is T-023/T-024).
   - Each runs `executeVendorRequest(..., effect)` on the `clinic_executor` pool.
   - The `clinic_executor` role gets EXECUTE on the transition function only.
5. **Edge cache purge** is the public-site task's job (T-127 area). T-022 emits the event the purge consumer will read.

## Acceptance (runnable)

- `pnpm exec vitest run tests/vendor/lifecycle.test.ts`:
  - **PR-56 scenario:** a live tenant with an unpaid server fee (fixture) is suspended. Vendor finance requests it, a platform owner approves, and the executor consumes the request. Then:
    - `assertTenantCapability(new_booking)` refuses with `ERR_TENANT_SUSPENDED`.
    - The owner has the `tenant_lifecycle` notification.
    - `clinical_read`, `clinical_export` and `care_message` stay allowed.
  - **Edges:**
    - Every disallowed edge is refused.
    - provisioning→onboarding is refused until the processor agreement is approved.
    - Suspension without a consumed request is refused, and so is a request for another tenant.
    - A request is never used twice.
    - Reactivation needs a second platform owner.
    - exit→closed.
  - **History:** append-only, with reason and actor; the event carries ids only.
  - **Isolation:** clinic_app cannot read the lifecycle tables or call the transition. The executor role reads no table.
  - **Concurrency:** two transitions at once are serialised; exactly one wins.
- `pnpm test:vendor`, `pnpm test:rls`, `pnpm test:isolation`, the full suite, typecheck, lint and docs:check.
- Mutation-test every control, then an independent R3 review before commit.
