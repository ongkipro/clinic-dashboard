## Design: merge by redirect, never by moving rows

Moving rows from the duplicate to the survivor would rewrite the patient column of six guarded tables (and every later clinical, money and commission table), and an unmerge would have to know which rows moved — fragile and against "never rewrite history". Instead:

- **`patient_merges`** (tenant-shared, insert-only except the undo stamp): `survivor_id`, `merged_id` (the duplicate), `reason` (10–500), `merged_by/as/at`, `undone_at/by/reason` (10–500), state derived from `undone_at`. Partial unique index: a patient is merged into at most one survivor at a time (`merged_id` where not undone); a survivor cannot itself be an active `merged_id` (no chains); a merged patient cannot be a survivor of another active merge (checked in the writer under `tenant_actor_lock`, and by a guard).
- **Effect while active:** the duplicate's rows stay where they are, attributed to the duplicate. Readers resolve the survivor: `patient_canonical(id)` returns the survivor for an actively merged id, else the id. `patient_get` on the duplicate returns the survivor's profile with a `merged_into` marker (re-created from 0057: one added lookup, drift-tracked); search (`patient_search`, T-041) hides actively merged duplicates (re-created from 0066: one predicate); `patient_consents`, the visit history and appointments of the survivor's profile include the duplicate's rows (the survivor's profile reads both ids) — the profile pages are later tasks' (T-040's page reads through `loadProfile`, which calls `patient_get`; no page change here).
- **Writers would refuse a merged duplicate** (new bookings, check-in, consent grants, registration matches) — **open point 1**: in T-042 only `patient_canonical` and the search/get readers change; writers keep accepting the duplicate id (its rows still belong to it), and a later hardening task makes them redirect. Recommend: leave writers unchanged in T-042 (Done-when is merge/unmerge fidelity), record the follow-up.
- **Unmerge** sets `undone_at/by/reason`; nothing else changes, so both patients are exactly as before with all their linked rows (the Done-when).
- **Authority:** records officer only (19:77), within their branch set? Patients are tenant-shared (DEC-050); the records officer's branch set limits clinical reads, not identity. Recommend: records officer of any branch of the tenant (open point 2). `tenant_actor_lock`; capability `record_correction` (live, suspended).
- **Audit:** `audit_append('settings_change', 'patient', survivor, 'success', 'patient_merged' | 'patient_unmerged')` and the same on the duplicate; the reason is on the merge row (never in audit or events, AGENTS). Event `PatientMerged` / `PatientUnmerged` (ids only) for later consumers (search caches, SATUSEHAT IHS link) — open point 3.
- **Guard:** no delete; identity columns fixed; undo once.

**Module `src/modules/patients/merge/merge.ts`:** `mergePatients(db, key, survivorId, mergedId, reason)`, `unmergePatients(db, key, mergeId, reason)`, `mergesOf(db, patientId)`, `canonicalPatient(db, id)` through `runCommand` (go-live gate).
