## Decisions proposed (DEC-111)
1. **Table `waitlist_entries`**: id, tenant_id, branch_id, patient_id (canonical), item_id (the service: a catalog item of kind service —
   not a version; branch offerings use item_id, 0058:43-50, so a new version still matches), state waiting | offered | booked | removed,
   offered_appointment_id null, offered_at null, booked_appointment_id null, command_key, created_by/as/at, closed_by/as/at,
   close_reason null (booked | removed). **No free-text note and no preferred date window** (review r1: not required by PR-81; no UI in
   this task to carry a privacy notice — YAGNI, revisable with the Daftar Tunggu page). One open entry (waiting | offered) per (tenant,
   patient, branch, item) (partial unique); one open offer per freed appointment (partial unique on offered_appointment_id where state =
   'offered'). Guard (staff_access first): never deleted; created waiting; transitions waiting→offered (trigger only), offered→waiting
   (declined), offered→booked, waiting|offered→removed; identity columns frozen. RLS: owner, admin_pusat, central_cs tenant-wide;
   manager, fo_cashier at allowed branches (the Daftar Tunggu roles, 19:66, + the appointment writers). Operator policy; support class
   `personal`.
2. **Commands** (bound, actor lock first, keyed through runCommand; roles = the appointment writers owner, admin_pusat, manager,
   fo_cashier, central_cs; a manager / FO only at an allowed branch): `waitlist_add` (the branch offers the item — branch_services; the
   item is a service; tenant capability new_booking; one open entry), `waitlist_remove`, `waitlist_offer_outcome` (offered → booked with an
   appointment that is the same canonical patient's, at the same branch, of a version of the same item, live; or declined → waiting).
   Reader `waitlist_list(branch, item?)` — the patient's name and MRN for these roles; no clinical content.
3. **On cancellation (Scenario PR-81)**: an AFTER UPDATE OF state trigger on appointments (no appointment function re-created; separate
   from 0108's no-show trigger), acting on a real transition OLD.state IN ('booked','confirmed') → NEW.state IN ('cancelled',
   'rescheduled') with NEW.starts_at > clock_timestamp() (review r2 P2: now() is the transaction start and a cancellation can
   wait on staff_access across the slot's start — wall clock, as appointment_live 0062:19-22; regression at a lock-wait time boundary): it selects exactly one waiting entry for (tenant, branch, item of NEW.catalog_version_id),
   oldest first with an id tie-breaker (ORDER BY created_at, id LIMIT 1 FOR UPDATE), sets it offered with offered_appointment_id, and
   prompts staff by **inserting the notification rows directly** (review r1 P1: notification_raise reads the session actor, app_staff_id(),
   and rejects a system-only type when a staff member cancels — calling it would roll back the cancellation; precedent 0036:543,
   0038:141): one row per recipient role (fo_cashier, central_cs, manager), branch = the slot's branch, subject waitlist_entry / the
   entry id, type `waitlist_offer` (a new notification_types row, raisable_by_staff false); ids only. Every supported cancel path is
   covered: appointment_cancel, appointment_cancel_clinic, deposit_refund_clinic's cancel (0093:372-373), appointment_reschedule. The
   appointment writers already serialize on the tenant-wide staff_access lock (0062:382-405, 0048:40-44), so two cancellations cannot
   offer the same entry and one cancellation offers one entry only. No message to the patient.
4. **Deferred, recorded (review r1 P2)**: a hold that expires frees its slot by time alone (appointment_live 0062:19-22; cleanup touches
   reservations, not appointment state, 0061:164-169), so no state trigger fires — hold expiry is NOT covered; PR-81's named scenario
   (a cancelled slot) is. Also deferred: the Daftar Tunggu page (19:66), automatic booking, a WhatsApp offer to the patient.
