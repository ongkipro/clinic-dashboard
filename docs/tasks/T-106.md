## What is built (migration `0125_coretax`; DEC-120)

### Gate and preconditions
`coretax_block` checks these in order:
1. a valid month that is not in the future;
2. the tenant's NPWP;
3. PKP: the tenant is PKP now, or issued PKP-at-issue invoices in that month;
4. the feature gate `coretax_export → tax_advice`, a new `feature_gates` row: the same tax-advice evidence as VAT on invoices (PR-97).

The export takes `feature_gate_lock` first. Refusals are returned rather than raised, so the denied audit row is kept. Each refusal is
audited as `export / coretax / denied / coretax_<reason>`. A closed gate names the missing evidence (Scenario PR-98).

### Documents
All four documents are built in the database from frozen facts only. Patient identity is never read.

1. **Digunggung, end consumer.** DJP `RetailInvoiceBulk` (Lampiran I.A.5 / I.A.9 / I.B):
   - One `RetailInvoice` per line of a PKP-at-issue invoice issued in the month (branch-local).
   - `TrxCode`: `Normal` for taxable lines, `08` for `exempt_medical` (I.A.9, VAT exempted) and `NoVAT` for `non_object`.
   - `GoodServiceOpt`: `A` for goods or products, `B` for services.
   - Buyer: `Konsumen Akhir` / `NIK` / `0000000000000000`.
   - `SerialNo` = YYYYMM × 10⁶ + the line's ordinal among that month's PKP lines. It is stable: a later void never renumbers the month.
   - `TransactionDate` = the issue date. `Info` = invoice number / line ordinal.
   - `TaxBaseSellingPrice` = the frozen `vat_base`. `OtherTaxBaseSellingPrice` = ROUND(11/12 × DPP) for taxable lines, else the base. `VAT` =
     the frozen `vat_amount`.
   - Lines of an invoice voided in the same month are left out; they appear in the cancellation register.
2. **Faktur with a named buyer.** DJP `TaxInvoiceBulk`:
   - A pure serializer whose element order equals DJP's sample v1.4. It sets `SellerIDTKU` = TIN + `000000` and `BuyerCountry` `IND`.
   - The clinic records no buyer tax identity, so the monthly document is the **structural envelope** — `TIN` and an empty
     `<ListOfTaxInvoice/>` (Panel 2 decision 2.2; r2 P1). It is downloadable when the gate is open and logged as a zero-row export; only the
     faktur may log zero rows (table check).
3. **Retur.** DJP `OutputSpecialDocReturn`:
   - One row per refund paid in the month that reversed VAT on a PKP-at-issue line.
   - `DocumentNumber` = the invoice number (the document returned). `ReturnDocumentNumber` = `RTR-<refund id>`.
   - Codes `01` / `1` / `01` / `01` (the template's defaults).
   - `DocumentDate` is DD-MM-YYYY. The buyer is the end consumer.
   - `ReturnVAT` = `vat_reversed`; `ReturnTaxBase` = amount − `vat_reversed`.
4. **Daftar pembatalan.** The clinic's own register, **not a DJP import format**:
   - Every PKP line voided in the month, with its original `SerialNo` and issue and void dates.
   - `TaxPeriodReported` = the issue month when that month is earlier, so the line was in that month's digunggung document and must be
     cancelled in Coretax by hand. It is `none` when the line was issued and voided in the same month.

### Export log and readers
- **Export log:** `coretax_exports` records month, document kind, the SHA-256 of the exact UTF-8 bytes served, rows, DPP, PPN, who, role
  and when.
  - Append-only; TRUNCATE is refused.
  - Supported ceiling (r2 P2): 10⁶ rows and Rp10¹⁵ DPP / PPN per document, all exact JavaScript numbers. `coretax_in_bounds` decides
    before any total is returned or logged: the status reports `bounds_exceeded` with no totals, and the export refuses `bounds_exceeded`
    (audited) instead of hitting the table check. Document totals are summed as `numeric`, never overflowing.
  - tenant-ledger RLS: owner, finance and auditor read; the operator reads in a support session (money totals class); the app writes
    only through the definer.
  - Exports are audited `export / coretax / success / coretax_<kind>`.
  - `invoice_lines.tax_document_ref` is never written: DJP assigns the NSFP after upload.
- **Readers and writers:**
  - `coretax_status(text)` (owner, finance, auditor): PKP facts, the gate and what it waits for, each document's counts and totals,
    pending discounts, frozen-VAT rounding differences, a per-document `bounds_exceeded` flag, and the last 20 exports.
  - `coretax_export(text,text)` (owner, finance).
  - Internal and not granted: `coretax_tin`, `coretax_txt`, `coretax_other_base`, `coretax_in_bounds`, `coretax_lines`, `coretax_doc_retail`,
    `coretax_doc_faktur`, `coretax_doc_retur`, `coretax_doc_pembatalan`, `coretax_block`.
- **TS module:** `src/modules/accounting/coretax/coretax.ts`.

### Page
`/keuangan/pajak` (UX-22 ▸ Pajak):

## Where DJP's published files override a detail of Panel 2's decisions (recorded; no product decision changed)
- **`TransactionDocument` in the retur document.** Panel 2 wrote the original invoice number there. DJP's template defines it as a code
  (`01`–`10`, `01` = documents equivalent to a tax invoice). The invoice number goes in `DocumentNumber`, per DJP's own field note "Nomor
  Dokumen yang akan diretur".
- **`SerialNo`.** Panel 2 proposed "invoice number + line ordinal". The XSD types `SerialNo` as `xs:long` and the clinic's invoice number
  is alphanumeric. SerialNo is therefore numeric and stable, and the invoice reference goes in `Info`.
- **`GoodServiceOpt` of `exempt_medical`.** Panel 2 mapped it to `B`. A or B follows the item kind (goods or service), because an exempt
  product is still goods.
- **Digunggung PPN rounding.** DJP's retail workbook computes VAT = ROUND(12 % × ROUND(11/12 × DPP)). The clinic's frozen VAT = amount −
  ROUND(amount × 100/111) (`tax_vat_split`, BILL-6) differs by ±1 rupiah on about 10 % of amounts (for example Rp15: DPP 14, VAT 1; DJP's
  formula gives 2).
  - Decision 3 says the frozen VAT is exported as is.
  - The rows that differ are counted on the page ("periksa dengan konsultan pajak sebelum unggah") and reported in `coretax_status`.
  - Whether Coretax accepts a ±1 difference on a retail row is a question for the tax adviser (OPEN, below).
