## 4 Design

### 4.1 The switch per template (default off)
- New table **`package_sharing`** (`src/modules/packages/schema.ts`): `tenant_id, item_id` (the package item; unique per tenant),
  `enabled boolean`, `changed_by, changed_as, changed_at`, `version`. Composite FK to `catalog_items`; guard: item kind `package`, staff_access
  first, never deleted, version + 1 per change. No row = off (**default off**, P-24/B-03).
- Writer **`package_sharing_set(p_item uuid, p_enabled boolean, p_reason text)`**: **owner only** (PR-93 "where the owner enables it";
  open point 1), `tenant_actor_lock` first, reason 3–500, audit `settings_change`/`package_sharing_set`. Idempotent by state (same value =
  no-op, no version bump). Applies to packages sold **after** the change.
- Why a table and not `catalog_versions`: version content is immutable (`0054:196`) and the template page edits sharing like other
  template fields; a separate row keeps the change out of the catalog review flow and inside Allowed Paths. Sold packages keep their snapshot.

### 4.2 Snapshot at sale
- `packages.sharing_allowed boolean NOT NULL DEFAULT false` (DATA-67). Existing packages: false (expand-only, default).
- `package_open` re-created: `sharing_allowed := coalesce((SELECT enabled FROM package_sharing WHERE item = l.item_id), false)` at the issue
  instant (the package opens at issue, or at T-080's discount decision — both run `package_open`).
- `packages_guard` re-created: `sharing_allowed` joins the frozen sale tuple; insert allows either value (set only by `package_open`).

### 4.3 Beneficiaries
- New table **`package_beneficiaries`**: `id, tenant_id, package_id, patient_id` (canonical), `granted_by, granted_as, granted_at` (= from),
  `grant_reason`, `removed_by, removed_as, removed_at` (= to), `remove_reason`, `command_key`. Partial unique `(tenant, package, patient)
  WHERE removed_at IS NULL`. Guard: staff_access first; never deleted; insert only on an **active** package with `sharing_allowed`, patient ≠
  the owner's cluster, patient not merged; update only `removed_*` once (active → removed).
- **`package_beneficiary_add(p_key, p_package, p_patient, p_reason)`**, **`package_beneficiary_remove(p_key, p_beneficiary, p_reason)`**:
  `package_actor(['owner','manager','fo_cashier'])` (UX-13 Paket & Saldo actors; open point 2); `package_locked` (row lock, active, valid);
  `sharing_allowed` false → `ERR_VERSION_CONFLICT: sharing_disabled`; patient of another tenant / missing → `ERR_NOT_FOUND`; the owner or a
  patient of the owner's cluster → `ERR_INVALID_INPUT: beneficiary_owner`; duplicate active → replay-safe no-op returning the row.
  Remove is refused while the beneficiary holds a **reserved** session of the package (`ERR_VERSION_CONFLICT: beneficiary_reserved`; release
  first). Audit both (`settings_change`, `package_beneficiary_added/removed`); event: none in the catalogue (open point 4).
- Reader flag: `package_row` adds `sharing_allowed`, `beneficiaries` (active: id, patient id, name, MRN, from) and `can_share`
  (= sharing_allowed AND role in owner/manager/fo_cashier AND active). **"The action is not offered"** = `can_share` false when the snapshot
  is off; the writer refuses anyway.

### 4.4 Reservation by a beneficiary (locked)
- `package_reserve` re-created: the visit's canonical patient must be **the owner, or an active beneficiary of a package with
  `sharing_allowed`** (checked after `package_locked`, i.e. under the package row lock); otherwise `ERR_NOT_FOUND` as today. The paid-value
  check is unchanged and runs under the same lock → **two beneficiaries cannot reserve beyond the paid value** (DATA-67).
- `package_sessions_guard` re-created: the reserved-visit rule (`:551-555`) accepts the owner's patient or an active beneficiary of a
  sharing package.
- **Who redeemed**: the treated patient is the reserved visit's patient; `reserved_visit_id` is kept and frozen once redeemed (`:132`,
  guard `:543`). The plan **derives** the beneficiary from it instead of a second column (open point 3 — DATA-67 names a
  `beneficiary_patient_id` on a redemptions table that does not exist; derivation cannot drift from the visit). `package_row` sessions add
  `patient` (id, name) for reserved and redeemed sessions.
- Lock order unchanged: staff_access → visit → package → sessions. The beneficiary row is read under the package lock; add/remove also lock
  the package first, so a removal and a reservation serialise.
- **Concurrency note**: every clinic writer of a tenant already serialises on staff_access (`tenant_actor_lock`), so two reservations run one
  after the other; the package row lock is the per-package guarantee DATA-67 asks for and the one that would hold if staff_access were ever
  narrowed. The concurrent test proves the outcome (exactly one), not which lock decided it.

### 4.5 Money, clinical, ownership
- Nothing posts or moves cash (BILL-11): no change to `package_open`'s amounts, `package_close_do`, refunds, balances (owner's), commission
  (follows the execution, as any session).
- Clinical: the beneficiary's own visit carries consent, eligibility and records (DATA-67); no package data enters clinical tables.
- Readers for the beneficiary: `package_patient_get` re-created to also list **packages shared with this patient** (active beneficiary)
  with `shared_from` (owner name, MRN; masked for the auditor) and `can_reserve` for the beneficiary's open visits; owner-only actions
  (cancel, top-up) not offered on a shared package from the beneficiary's view.
