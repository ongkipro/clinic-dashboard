## Decisions proposed (DEC-112)
1. **Segment** = a saved filter (`campaign_segments`: tenant, name, rules jsonb). **Closed rule set without clinical predicates** (review
   P1-1): registered branch (or any), last visit within / not within N days (visit DATE only, no service), birthday month, age band, sex.
   No service, procedure, package or diagnosis rule in this task (07:26/:34, PR-63). Members are computed at read and send time and
   **always intersected with an active `marketing_wa` consent on the canonical patient cluster** (PR-4); merged records count once.
   Editable at any time (the Scenario's "segment remains editable").
2. **Campaign workspace on the existing `campaigns` row** (expand-only columns): `segment_id`, `template_id`, `scheduled_for` (date),
   `send_state` ∈ draft | scheduled | queued | cancelled (review P2-2: `queued` = handed to the outbound queue; delivery outcomes are DERIVED
   from outbound_messages — queued / sent / skipped / failed counts by source ('campaign', id) — never claimed at enqueue). Existing rows
   (lead tags) default `draft`. The guard (0107) is re-created to also enforce: insert as draft; edges draft→scheduled, scheduled→draft,
   scheduled→queued, draft|scheduled→cancelled; queued and cancelled are terminal; workspace fields frozen once queued.
3. **Readers split (review P2-1)**: the table's broad SELECT is replaced by column grants of the legacy lead-tag columns (id, tenant_id,
   name, code, channel, active, created_*, updated_at) to clinic_app and clinic_operator, so central_cs / manager / bc / config-support keep
   reading tags but never the workspace columns; `campaigns_list` keeps its legacy projection unchanged. New definer reader
   `campaign_workspace_list()` (owner, admin_pusat, marketing; auditor read) returns the workspace fields, derived outcome counts and the
   gate state.
4. **The gate covers every campaign path (review P1-2)**:
   a. a shared check `campaign_gate_open(p_tenant)` evaluates the gate tenant-explicitly (the same obligation rules as feature_gate_open,
      for a given tenant — usable by the unbound worker);
   b. `campaign_send` (owner, admin_pusat, marketing): actor lock → capability → `feature_gate_lock('campaign_sending')` → gate check;
      closed → `ERR_GATE_CLOSED` "Pengiriman kampanye terkunci sampai bukti hukum disetujui" (exact Scenario copy), nothing enqueued, the
      campaign stays scheduled, its segment editable;
   c. the generic `outbound_enqueue` refuses `source_kind = 'campaign'` (`ERR_INVALID_INPUT`) — campaigns enter the queue only through
      campaign_send (re-created; body otherwise unchanged; drift-pinned);
   d. `outbound_claim` re-checks the gate for `('promo','campaign')` rows: closed (revoked or expired evidence) → the row is skipped with a
      new skip reason `campaign_locked` (outbound_messages_check + OUTBOUND_SKIP_REASONS) and an OutboundMessageSkipped event (ids only).
5. **Frequency cap applied everywhere a promo becomes sendable (review r1 P1-3, r2 P1)**:
   a. at enqueue (campaign_send): staff_access (actor lock) → `automation_cap_lock(tenant, canonical)` → `automation_cap_day(today,
      SET-19 batas_harian, …)` → outbound_enqueue_do with planned_for = that day; no day with room within 7 → the member is reported
      skipped `cap_horizon_exceeded` in the send result, not queued. Key per (campaign, canonical patient).
   b. **at dispatch (one check covers budget deferral, suspension deferral and overdue carryover)**: in outbound_claim, before a due
      MARKETING row becomes `sending`, under the tenant's staff_access (already held) then the patient's cap lock:
      - **today's count** = `automation_cap_count(tenant, patient, today, today, tz) − 1` — the T-097 definition (care_reminder, aftercare
        and promo rows sending/sent today PLUS every queued row due today or overdue, care included), minus the candidate itself (it is
        queued with planned_for ≤ today, so it counts exactly once on today). Care rows due today count whether the loop reaches them
        before or after the promo (review r3 P1: the claim orders by planned_for, so a care row may be processed later). A care row that
        is later budget-deferred makes this conservative (a promo may wait a day it could have used) — never over the cap.
      - count < batas_harian → the promo proceeds to the existing budget check unchanged;
      - else it is deferred: a new helper `outbound_cap_defer_day(tenant, patient, today, cap, tz)` returns the first day in
        **today + 1 … today + 7** (explicit window, measured from the dispatch day) with `automation_cap_count(tenant, patient, day, today, tz)
        < cap` — called with the REAL today, so the candidate (counted on today) never counts against a future day (review r3 P2); the
        row's planned_for moves there, deferred_reason `cap_reached` (new value). NULL (no room in that window) → skipped
        `cap_horizon_exceeded` (new skip reason) with an OutboundMessageSkipped event (ids only).
      Rows deferred earlier in the same loop have moved their planned_for, so later rows see them on the new day. The existing budget and
      suspension deferral branches stay unchanged (they only move planned_for; this check governs every later transition to `sending`).
      Care messages are never cap-deferred (as today). The check applies to every promo (T-097 refill / birthday too) — PR-94's cap;
      recorded as a behaviour change in DEC-112. automation_cap_count and automation_cap_day are NOT re-created.
   c. drift contract (review r2 P2): outbound_claim is re-created with exactly two changes — (i) the campaign-gate skip (4d), (ii) the
      dispatch cap check (5b) — and the drift test asserts the new body equals the reviewed 0109 body with those two inserted blocks and
      nothing else (utility path, tenant lock order, existing skips, payload, security attributes, grants unchanged), comparing databases
      migrated to exactly 0114 and exactly 0115. outbound_enqueue: exactly one change (the 'campaign' refusal). campaigns_guard: the edge
      rules added, identity freeze unchanged. outbound_messages_check: two skip-reason values and one deferred-reason value added.
6. **Capabilities (review P1-4)**: segment and schedule writes (`campaign_segment_save`, `campaign_schedule`, `campaign_cancel`) need
