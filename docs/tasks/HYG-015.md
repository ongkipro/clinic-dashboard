# HYG-015 — One error listener for every test database connection

Status: plan approved (Argon `5a66ee0f` APPROVE PLAN, findings adopted below) · Risk: R2 (tests only; no product code, no migration) · Requirement: HYG-015 (no PR; hygiene, owner 2026-11-11)

## Why (verified)

- A `pg.Pool` re-emits an idle client's backend error on the pool (`pg-pool` `makeIdleListener` → `pool.emit('error')`); a `pg.Client` emits it on itself (`pg/lib/client.js` `_handleErrorEvent`). An `EventEmitter` with no `error` listener throws, which vitest reports as an unhandled error and fails the run even when every test passed.
- That happened on `main` at least three times:
  - CI 42615137831 attempt 1 (T-048): `57P01` during `tests/vendor/support.test.ts`; fixed for that file only in T-039.
  - CI 42753612376 attempt 1 (T-051 `833b84d`): `error: terminating connection due to administrator command`, `code: '57P01'`, "originated in tests/vendor/lifecycle.test.ts", 0 tests failed (log read 2026-11-11). That file's four raw pools (`owner`, `exec`, `opPool`, `consoleDb`) have no listener, and `op = await opPool.connect()` is held checked out for the whole file (a checked-out client has no pool listener at all).
  - HYG-006 lock-tests: an unhandled `57P01` from a killed query (fixed there with a handler on the promise).
- Census on `f52b793` (outside `tests/rls/harness.ts`): **74 `new pg.Pool(` (on 73 lines; `staff.test.ts:533` has two) in 51 files** and **14 `new pg.Client(` in 6 files**; only 23 constructions add `on("error", () => {})` by hand. `openAppPool` (product code) already has a listener and is not touched. The cause of the termination itself (which backend was killed, by whom) is not established; this task makes it non-fatal in tests, it does not claim to explain it.

## Change

1. **Helpers in `tests/rls/harness.ts`** (the one shared test-database module every file already imports):
   - `testPool(config: pg.PoolConfig): pg.Pool` — `new pg.Pool(config)`, a no-op `error` listener on the pool, and `pool.on("connect", (c) => c.on("error", () => {}))` so a client also has a listener while it is checked out (pg-pool removes its idle listener on checkout; `lifecycle.test.ts` `op` is that case).
   - `testClient(config: pg.ClientConfig): pg.Client` — `new pg.Client(config)` with a no-op `error` listener.
   - A listener only stops the process-level throw: a query in flight still rejects (pg errors every queued query before emitting), so no test can pass on a swallowed error. Comment says so.
   - `poolAs`, `connectAs`, the `server`/`admin` clients and `defaultObserver` use them (their hand-written listener lines go). `startHolderReport` keeps its own `observer.on("error")` because a test may inject an observer.
2. **Mechanical replacement** in `tests/**`: `new pg.Pool(` → `testPool(`, `new pg.Client(` → `testClient(`; add the names to the file's existing `../rls/harness` import (`tests/ui/shell.spec.ts` imports it dynamically inside its describe; the helpers join that import). A hand-written `X.on("error", () => {})` on the line right after `X = testPool(...)`/`testClient(...)` is removed (redundant); listeners on other objects (promises, `openAppPool` pools, injected observers) stay. `import pg from "pg"` stays where `pg.` types are still used, otherwise it goes. Done by a script that asserts its replacement counts (74 pools, 14 clients, 53 files; harness excluded), then reviewed by diff.
3. **Guard** `tests/rls/pg-listener.test.ts`:
   - reads every `*.ts` under `tests/` and `docs/evidence/` and fails on `new pg.Pool(` / `new pg.Client(` / `new Pool(` / `new Client(` imported from `pg`, except in `tests/rls/harness.ts` and two frozen milestone evidence files (`docs/evidence/m1/m1-flow.test.ts`, `docs/evidence/m2/m2-flow.test.ts`: exit evidence already committed with its own listeners, left byte-identical so the M1/M2 maps and receipts stay valid); a positive control proves the scan finds a planted construction;
   - behaviour: a `testPool` client left idle, its backend terminated with `pg_terminate_backend` → the pool drops it (`totalCount` → 0) and the process sees no `error` event (an `uncaughtException`/`unhandledRejection` spy stays empty); the same for a client checked out from `testPool`, and for an idle `testClient`. Each case is red without the helper's listener (mutation).
4. **Docs:** `TASKS.md` hygiene queue row 10; `STATUS.md` (T-059 done `f52b793` / CI 42898877698, the M3 goal, HYG-015 in progress); `DECISIONS.md` DEC-069 (M3 execution and the owner's 2026-11-11 authorization); `BUILD-LOG.md` gotcha (raw pg pools/clients in tests: always `testPool`/`testClient`).
