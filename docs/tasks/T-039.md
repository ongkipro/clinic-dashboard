## Design

**Migration `0065_privacy.sql`** (tenant-shared; readers and writers: Owner, and Admin Pusat with the `data_protection` duty — "privacy officers"):
- `processors`: `name` (2–120), `service` (2–200), `data_categories` (2–300), `location` (2–120, country/region), `role` (`processor` | `sub_processor`), `cross_border` (bool), `transfer_basis` (required when cross-border, 3–300), `agreement_ref` (nullable, ≤ 200), `active`, `created_by/at`, `updated_by/at`. Edited (not versioned); every change audited; ended with `active = false`, never deleted.
- `breaches`: `aware_at` (≤ now), `deadline_at` generated as `aware_at + 72 h`, `description` (10–2000), `affected_count` (nullable, ≥ 0), `data_categories` (2–300), `state` (`open`, `assessed`, `notified`, `not_notifiable`, `closed`), `not_notifiable_reason` (required in that state, 10–1000), `assessed_at`, `closed_at`, `created_by/at`. Transitions: open → assessed → notified | not_notifiable → closed (`notified` requires at least one notice; `closed` requires notified or not_notifiable). Each transition: one writer call, an audit row (codes only), stamps.
- `breach_notices`: `breach_id`, `recipient_kind` (`data_subjects` | `authority` | `other`), `recipient` (2–200), `sent_at` (≤ now), `channel` (2–60), `content_summary` (10–2000), evidence file bytes as the compliance evidence (content, media type sniffed, size ≤ 5 MB, sha256 recomputed), insert-only, the breach must be assessed or notified.
- Readers: `privacy_overview()` — the consent texts per purpose (all versions, from T-038), consent ledger counts per purpose (active / withdrawn) and the latest 50 consent events across patients (purpose, state, date, patient MRN and name — the officer is an identity reader), processors, breaches with deadline and notices (metadata, not bytes); `breach_notice_file(id)` for the download.
- Writers (definer, `tenant_actor_lock`, privacy officer check, `configuration` capability for processors, `data_request` capability for breaches so a suspended tenant can still record a breach, audit, idempotency): `processor_upsert`, `processor_set_active`, `breach_record`, `breach_assess`, `breach_conclude(p_breach, p_notifiable, p_reason)` (→ notified needs a notice; → not_notifiable with reason), `breach_close`, `breach_notice_add`.
- RLS: SELECT for the officers only (the duty is checked in the policy through a helper `privacy_officer()`); `support_object_kinds`: processors `config`, breaches and notices `personal`? — breaches may describe patients: `personal`; operator policies; scope map. No event payloads (no outbox consumer yet): audit only.

**Module `src/modules/privacy/`**: `privacy.ts` (readers and writers, the file sniffing reused from compliance), `schema.ts`.

**Page `src/app/(app)/privasi/`**: segments Persetujuan · Pemroses · Kebocoran (Permintaan is T-121's subpage). ## Plan review r1 (Argon `1958be82`: REVISE; the four open points approved, `configuration` = onboarding and live) and the revised design

- **P1-1** `deadline_at` is a plain column set by `breach_record` to `aware_at + 72 h`, with `CHECK (deadline_at = aware_at + interval '72 hours')` and kept immutable by the guard; `aware_at <= created_at` and `sent_at <= created_at` as column checks; `<= clock_timestamp()` in the writers.
- **P1-2** stamps for every transition (`assessed_at/by`, `concluded_at/by`, `closed_at/by`, composite staff FKs) with state-bound checks; `not_notifiable_reason` kept when a not-notifiable breach closes (the path stays readable); always-enabled guards on all three tables (no delete, identity fixed, the allowed transitions only, `notified` needs a notice, `closed` final; notices insert-only on an assessed or notified breach; truncate refused); `breach_conclude` refuses a reason with "notifiable".
- **P1-3** writers and the notice download use a volatile `privacy_actor(p_capability)`: `tenant_actor_lock()` first, then the officer check (Owner, or Admin Pusat with an active `data_protection` duty) on the post-lock snapshot, then the capability; the overview uses `approval_actor()` and the same check and returns the database time. `breach_notices` content is never granted: column grants without `content` for `clinic_app` and `clinic_operator`; the bytes come only through `breach_notice_file` (audited `export`).
- **P2-1** the notice command's idempotent body carries `sha256`, `fileName`, `mediaType`, `sizeBytes` and the fields, never the bytes; errors mapped outside `runCommand`.
