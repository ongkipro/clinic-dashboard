## Design (proposed)

- **Table `branch_prices`** (tenant-shared): `tenant_id`, `branch_id`, `item_id`, `price` (bigint rupiah, `> 0`, or null = "back to the normal price" from that moment), `effective_from` (timestamptz), `state` (`active` | `cancelled`), `reason`, `created_by`, `created_as`, `created_at`, `cancelled_at`, `cancelled_by`. Composite tenant FKs to `branches` and `catalog_items` (ON DELETE RESTRICT); `UNIQUE (tenant_id, id)`; one active row per `(tenant, branch, item, effective_from)`.
- **Keyed by item, not by catalog version (deviates from the DATA-15 column list; needs the plan review).** A catalog version changes on every price, clinical or recipe edit. An override keyed by version would silently disappear whenever anyone published a new version of the item, so the owner's branch price would fall back to the normal price without the owner acting. Keyed by item, the override holds until the owner changes or ends it, which matches B-08 ("shared master + branch price override"). The invoice snapshot (DATA-6) still records the catalog version and the effective price at sale time. If the review prefers the literal DATA-15 shape, the alternative is to copy active overrides onto each new version inside `catalog_publish`, which touches T-033/T-034 functions again.
- **Effective price** `catalog_branch_price(item, branch, at)`: the newest active row with `effective_from <= at`; its price, or the active version's `normal_price` when there is none or its price is null. One read function for the cashier, packages and the public site later.
- **Writes** (SECURITY DEFINER, under `tenant_actor_lock`):
  - `branch_price_set(item, branch, price, effective_from, reason)`: Owner only (Admin Pusat, Manager and every other role refused, `ERR_FORBIDDEN`). The item must belong to the tenant and have an active version; `price` null, or between 1 and Rp1,000,000,000,000 (the `catalog_versions_price_check` bound); `effective_from` from now (one-minute lag allowed) up to 366 days ahead, never backdated; a reason of 3–500 characters. A row with the same `effective_from` is a conflict (`ERR_VERSION_CONFLICT`), not an overwrite.
  - `branch_price_cancel(id)`: Owner only, and only a row that has not taken effect yet (`effective_from > clock_timestamp()`); a row in effect is changed by a newer row, never edited.
  - Audit `settings_change` with reason codes `branch_price_set` / `branch_price_cancelled`; event `BranchPriceChanged` with ids only.
- **Kinds:** services, products and packages. Materials (BHP) are not sold at the counter, so `material` is refused. (Needs the plan review.)
- **Readers:** a branch price is commercial data, not clinical. Every member of the tenant reads `branch_prices` through RLS (`tenant_id` match), like the commercial catalog projection (DEC-046 (2)). `scope_map` tenant-shared; vendor support class `config` with one operator policy (TEN-19).
- **Immutability:** rows never change except `active` → `cancelled` before they take effect; no delete or truncate (triggers, ENABLE ALWAYS).
- **UI:** `/katalog/harga-cabang` lists the sellable items with the normal price and, per branch, the effective price today and the next scheduled change; filters by branch and kind. `/katalog/harga-cabang/[item]` shows each branch's history and, for the Owner only, the form (branch, price or "kembali ke harga normal", date from which it applies in the branch's timezone, reason) and Batalkan on a scheduled row. Other roles see the page read-only, with no form. The date input means 00:00 in the branch's timezone (DATA-7); "hari ini" means now.
- **Scope expansions (ledger, before building):**
  - `src/app/(app)/layanan/[id]/page.tsx` and `src/app/(app)/katalog/[id]/page.tsx`: the Harga Cabang tab shows the effective prices and links to the editor instead of "belum tersedia" (UX-25).
  - `src/modules/settings/registry.ts`: SET-5 links to `/katalog/harga-cabang` and SET-30 to `/layanan`; both point today to `/master-layanan`, a route that does not exist (the Master Layanan route is `/layanan`, T-034).
  - `src/components/shell/nav.ts` if the page needs its own entry.

## Plan review round 1 (Argon; GPT-6.1 Sol returned 429): REVISE PLAN → adopted

Accepted as designed: overrides keyed by item (recorded as a decision row at integration, since it deviates from the DATA-15 column list); materials excluded; readers every member; vendor support class `config`. The design below replaces the matching parts of "Design (proposed)".

1. **Effective-price reader (P1-1).** `catalog_branch_price(p_item, p_branch, p_at timestamptz DEFAULT clock_timestamp()) RETURNS bigint` is `STABLE SECURITY DEFINER` with `search_path = pg_catalog, pg_temp`, granted to `clinic_app`, and on the definer allow-list. The cashier role cannot read `catalog_versions` (DEC-046 (2)), so an invoker function would return null for it. It requires the caller's tenant and a staff context, joins the branch in the same tenant and the item's active version, refuses materials, and returns null when any of these is missing (another tenant's or an unknown branch never falls back to the normal price). It takes the newest active row with `effective_from <= p_at` (`ORDER BY effective_from DESC LIMIT 1`), including a "back to normal" row, then `coalesce(row price, normal_price)`. The default is `clock_timestamp()`, so an override set "now" is visible later in the same transaction.
2. **Table invariants (P1-2).** FKs `tenant_id` → `tenants`, `(tenant_id, branch_id)` → `branches`, `(tenant_id, item_id)` → `catalog_items`, `(tenant_id, created_by)` and `(tenant_id, cancelled_by)` → `staff`, all ON DELETE RESTRICT. Checks: `price IS NULL OR price BETWEEN 1 AND 1000000000000`; `state IN ('active','cancelled')`; `(state = 'cancelled') = (cancelled_at IS NOT NULL AND cancelled_by IS NOT NULL)`; `created_as = 'owner'`; reason 3–500 characters after trimming. Guard trigger `BEFORE INSERT OR UPDATE OR DELETE`, ENABLE ALWAYS: an insert starts `active` with no cancellation; an update may only move `active` → `cancelled`, set the two cancellation columns, and only while `OLD.effective_from > clock_timestamp()`; no delete; no truncate.
3. **Effective dating (P1-3), the settings rule.** `branch_price_set` stores `greatest(coalesce(p_effective, clock_timestamp()), clock_timestamp(), newest active row in effect + 1 µs)`, as `setting_effective` does. A write "now" therefore always takes effect after the row currently in force and never lands before it. A requested time more than one minute in the past or more than 366 days ahead is refused. The same future time as an existing active row is a conflict (`ERR_VERSION_CONFLICT`, partial unique index on active rows). The server action converts the form date in the branch's own `branches.timezone` (Asia/Jakarta, Asia/Makassar or Asia/Jayapura): today in that timezone means now (null); a later date means 00:00 there; an earlier date is refused as backdated. Both pages format times in each branch's timezone.
4. **Scope expansions (P1-4).** Add `src/app/(app)/layanan/data.ts`, `src/app/(app)/katalog/data.ts`, `src/app/(app)/katalog/page.tsx` (a link to `/katalog/harga-cabang`) and `tests/ui/layanan.spec.ts` (it asserts "belum tersedia" on the Harga Cabang tab). Drop `src/components/shell/nav.ts`: 19 §2 has no separate menu row for Harga Cabang; it is reached from Katalog & Harga, Master Layanan and Pengaturan SET-5.
5. **Authority and events (P2-1).** Both writers check `a.role = 'owner'` and that the branch (or the row's branch) belongs to the tenant; they never restrict by the active branch, so an Owner with a branch selected changes any branch's price (HYG-009 N2). Event: `branch_id` = the row's branch, `type` `BranchPriceChanged`, `aggregate_kind` `branch_price`, `aggregate_id` the row id, `payload` `{item_id, branch_id, change: "set" | "cancelled"}`; no price or time in the payload (`events_payload_ok`).
6. **UI (P2-2).** The Harga Cabang section on `/katalog/[id]` and `/layanan/[id]` appears only for a non-material item with an active version, linking "Atur harga cabang" (Owner) or "Lihat harga cabang" (others). `/katalog/harga-cabang/[item]` answers not-found for another tenant's item, a material or an item without an active version. The next scheduled change is the earliest future active row (`ORDER BY effective_from ASC LIMIT 1`). Both server actions refuse a stale context (HYG-009 B2-1).
7. **Tests added (P2-3).** The cashier reads the effective price with no override, with one, and after "back to normal"; another tenant's or an unknown branch returns null; an Owner with branch A selected sets and cancels branch B's price; two scheduled changes (next = earliest; once both pass, the latest governs); "today" and a future date for an Asia/Makassar and an Asia/Jayapura branch; `branch_price_set` and `branch_price_cancel` in the authority-clock writer list; the three definers on the allow-list.
