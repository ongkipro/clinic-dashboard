### 4.1 Tables (DATA-68; tenant-ledger; never deleted; `*_no_truncate` ENABLE ALWAYS; composite `(tenant_id, …)` FKs; guards take staff_access first)
- **`promo_codes`** — the stable identity: `id, tenant_id, code` (upper-cased, `^[A-Z0-9-]{3,32}$`, unique per tenant), `quota` (1..1,000,000,
  shared across versions, BILL-36), `used` (reserved + consumed; `0 ≤ used ≤ quota` CHECK), `active` (owner/Admin Pusat/Marketing may
  deactivate; never reactivated past its period), `created_by/as/at`, `command_key`. **The quota counter lives on this row** (§4.3).
- **`promo_code_versions`** — the terms: `id, tenant_id, promo_id, version` (1.., unique per promo), `valid_from`, `valid_to` (branch-local
  dates, inclusive), `discount_kind` (`percent` | `rupiah`), `discount_value` (percent 1..100 or rupiah 1..MONEY), `max_discount` (rupiah cap,
  nullable), `item_ids uuid[]` (eligible catalog items, non-empty), `branch_ids uuid[]` (eligible branches; empty = every branch),
  `per_patient_limit` (nullable; uses per canonical patient, "pemakaian per pasien" `19:128`), `created_by/as/at`, `command_key`. **Immutable
  once any usage references it** (BILL-36): the guard refuses UPDATE when a `promo_usages` row exists; an edit inserts version + 1.
- **`promo_usages`** — one per invoice line: `id, tenant_id, branch_id, promo_id, version_id, invoice_id, invoice_line_id` (unique, "one promo
  per line"), `patient_id` (canonical, nullable for a counter sale without a patient), `discount` (rupiah given), `state`
  (`reserved` → `consumed` | `released`), `reserved_at`, `consumed_at`, `released_at`, `release_code` (`void` | `removed` | `refunded_full`).
  Guard: insert reserved; reserved → consumed or released; consumed → released only with `refunded_full`; frozen otherwise.
- `invoice_lines`: T-080's check widened to `discount_kind in ('manual','promo')`; a promo line has `discount > 0`, `discount_approval_id NULL`.

### 4.2 Applying a code (inside `invoice_issue`, the only line writer that takes a discount)
- Input: `lines[].promo_code` (string) beside `item_id`, `quantity`; a line carries **either** `discount` (manual) **or** `promo_code`, never
  both (`ERR_INVALID_INPUT: promo_and_discount`) — "one promo per line" and BILL-28 keeps promo discounts out of the manual limits.
- Resolution: the code (tenant, upper-cased) → its latest version; refusals in this order, each `ERR_VERSION_CONFLICT: promo_<reason>`
  (open point 2): `not_found` (`ERR_NOT_FOUND`), `inactive`, `outside_period` (the branch-local issue date), `branch` (not eligible),
  `item` (the line's item not eligible), `patient_limit`, `exhausted`.
- Amount: `percent` → `floor(gross × value / 100)`, capped by `max_discount`; `rupiah` → `least(value, gross)`; at least 1 and less than the
  gross for a package line (as T-080: `packages_check` price ≥ 1). VAT then on `line_total = gross − discount` (DEC-081 item 4; the snapshot's
  own `tax_vat_split`).
- The snapshot (`invoice_line_snapshot`, 9 args: T-080's 8 + `p_promo uuid` = the resolved version) inserts the line with
  `discount_kind = 'promo'` and **does not** call `discount_within_limit` (pre-approved). `invoice_issue` then inserts the `promo_usages` row
  (`reserved`) after the snapshot returns the line id.
- A promo on a counter sale, an addition line, a substitution line or the consultation fee line: counter allowed (products); substitution
  and consultation refused (`ERR_INVALID_INPUT: promo_line`; their prices are fixed by other rules); addition allowed.

### 4.3 The atomic quota (Done-when: two concurrent cashiers cannot exceed it)
- **Mechanism: one conditional UPDATE on the code row, inside the issuing transaction:**
  `UPDATE promo_codes SET used = used + 1 WHERE tenant_id = $t AND id = $p AND active AND used < quota RETURNING used` — no row back →
  `promo_exhausted`. PostgreSQL takes the row lock for the UPDATE; a second transaction targeting the same row waits for the first to commit
  or roll back, then **re-evaluates `used < quota` on the committed row** (READ COMMITTED, EvalPlanQual), so of two cashiers taking the last
  use exactly one gets a row and the other gets none. The CHECK `used ≤ quota` is the backstop.
- Why not SELECT … FOR UPDATE then UPDATE: same lock, two statements; the single conditional UPDATE has no read-then-write window.
  Why not count `promo_usages`: a count is not atomic without the same row lock.
- Lock order: staff_access (kasir_actor) → visit → invoice → line insert → promo code row → usage insert. Every promo writer takes the code row
  only after staff_access; no promo writer holds a code row lock before staff_access (the `0048:9-24` rule). Two invoices with codes A then B
  and B then A cannot deadlock because the issue takes the codes in line order **sorted by promo id** (resolve all first, then UPDATE in id order).
- Per-patient limit: counted from `promo_usages` (reserved + consumed) of the canonical patient **under the code row lock** (after the UPDATE),
  so two concurrent issues for one patient also serialise; over the limit → raise (the UPDATE rolls back with the transaction).

### 4.4 Consumed and released (BILL-36)
- **Consumed when the line is paid:** the line's paid value (`kasir_line_paid`) reaches `line_total − cancelled_amount` → the usage moves
  reserved → consumed. Where: `kasir_record_payment` (and the port settle path) after allocation, `deposit_apply_do`, and `receivable_convert`
  (a converted remainder counts as settled for the quota: the patient owes it). One helper `promo_usage_sync(tenant, line)` called by each.
- **Released (used − 1):** `invoice_void_sync` (void, only unpaid: the usage is reserved → `void`); a line removal before payment
  (`cancelled_amount` set on a line with nothing paid: `interrupted_to_balance`, `package_close_do` on an unpaid package) → `removed`;
  a refund of the **full** line value (`refund_settle` when paid refunds + this one = line_total − cancelled) → consumed → released
  `refunded_full`. Any partial refund keeps it consumed. Each release does `UPDATE promo_codes SET used = used − 1` under the same row lock.
- Release is idempotent per usage (state machine); the counter cannot go below 0 (CHECK).

### 4.5 Writers, readers, RLS, events, audit
- **Code management** (owner, Admin Pusat, Marketing; `tenant_actor_lock` + role list; tenant-wide): `promo_code_create(p_key, p)`,
  `promo_code_version(p_key, p_promo, p)` (new terms → version + 1; also edits a version with no usage in place? No: always a new version,
  simpler and BILL-36-safe), `promo_code_set_active(p_key, p_promo, p_active)`, `promo_code_quota(p_key, p_promo, p_quota)` (raise or lower,
  never below `used`). Idempotent by key; audit `settings_change` / `promo_code_*`.
- **Readers:** `promo_codes_list()` (owner, Admin Pusat, Marketing, auditor read; finance and manager read for the Kasir) with usage
