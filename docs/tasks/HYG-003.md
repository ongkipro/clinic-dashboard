# HYG-003 — Vendor console first users: bootstrap command and minimal Tim Vendor (DEC-036)

Status: Planned · Risk: R3 (vendor access, account creation) · Owner: Paduka Ongki · Executor: pi (cc/claude-opus-5-5) · Wave 7 (before T-024; migrating task of the wave, DEC-035)

## Why

A fresh server (staging, production) has no vendor staff, so nobody can sign in to the vendor console. Creating the first platform owner is only possible from test code (`bootstrapVendor`). The first-owner maker-checker (DEC-033) also needs a second platform owner, and Tim Vendor (UX-46) is only scheduled for T-129 (M9). The owner chose one procedure for staging, production and live (DEC-036, 2026-11-03):

1. The first platform owner is created by a terminal command.
2. Everyone after that is invited from Konsol Vendor › Tim Vendor.

Not a `TASKS.md` task: hygiene the owner authorised directly, like HYG-001 and HYG-002.

## Requirements served

- **IAM-1:** individual accounts and passwords, TOTP for every vendor role.
- **IAM-10 / PR-57:** vendor staff and roles, TOTP, allowlist, logged.
- **UX-46:** Tim Vendor, minimal part.
- **SEC-16:** vendor actions are logged.
- **DEC-033 / DEC-036.**

## Design

### 1. `pnpm vendor:bootstrap` (`src/db/vendor-bootstrap.ts`)

- **How it runs:** like `src/db/migrate.ts`, Node runs it with type stripping. It needs `DATABASE_URL` (the migration/owner role, the only role that may call `vendor_bootstrap`) and is shipped in the image next to the migration runner, through a Dockerfile `COPY`.
- **Arguments:** `--email`, `--nama`, `--cidr` (console allowlist, at most /16 as T-020), `--label`.
- **Password:**
  - Read twice at a hidden prompt when stdin is a TTY, or as two lines from stdin otherwise (piping for tests or a secrets manager).
  - Never taken from an argument or an environment variable, so it never lands in shell history or the process list.
  - Checked against the IAM-1 policy with `passwordProblem`, the same function the app uses.
- **One transaction:**
  1. Refuse when vendor staff exist (`already_bootstrapped`) or the email already has an account (`account_exists`). The second case is a person to invite instead; an existing clinic account is never taken over.
  2. Create `auth_user` (email lower-cased, unverified, no TOTP) and its `credential` account with Better Auth's own password hash (`better-auth/crypto` `hashPassword`, the hash sign-in verifies).
  3. Call `vendor_bootstrap` (platform owner, allowlist, vendor log).
- **On refusal:** roll back, then write the refusal to the vendor log in its own transaction. The command exits non-zero with an Indonesian message and never prints the password or a hash.
- **First sign-in:** on `/vendor/masuk` the person must enrol TOTP before anything else (T-021 `totpAlways`).

### 2. Tim Vendor invitations (migrations `0041` table, `0042` rules)

- **Table `vendor_staff_invitations`** (platform, RLS on, no grants):
  - email, display name, roles (the five vendor roles), token hash, inviter, invited/expires (7 days), state pending → accepted | cancelled | expired, accepted account, closed time;
  - a forward-only history trigger, no delete or truncate;
  - one open invitation per email.
- **Console functions** (session token + `vendor_guard`, platform owner only, logged; reads 12 h, writes 10-minute step-up, as T-020/T-021):
  - `vendor_console_staff_list(token, ip)`: staff (name, email, roles, state, TOTP enrolled) and open invitations (no token).
  - `vendor_console_staff_invite(token, ip, email, name, roles, token_hash)`: refused for an email that is already vendor staff or has an open invitation; validated.
  - `vendor_console_staff_invite_cancel(token, ip, invitation)`.
  - `vendor_console_staff_state(token, ip, staff, state)` (`active` | `suspended`): goes through `vendor_staff_update` with the session's account and second-factor time. All T-020 rules apply: never oneself, never the last TOTP-enrolled platform owner, a dual identity re-checked on reactivation.
- **Acceptance** (`clinic_vendor`, no session yet):
  - `vendor_staff_invite_lookup(hash)`: name, email, roles while valid.
  - `vendor_staff_invite_accept(hash, account)`:
    - takes the `vendor_staff` lock;
    - requires: pending, not expired, the email matches, the account is not vendor staff, no unapproved clinic membership (IAM-10 dual identity), and the inviter is still an active platform owner;
    - creates `vendor_staff` with the roles, marks the invitation accepted, and logs it.
- **Console:**
  - `/vendor/tim`: list, Undang (name, email, role checkboxes), the one-time link shown once, Batalkan, Nonaktifkan / Aktifkan Kembali. Platform owner only: the nav item is shown only to that role (NAV-1), and other roles get a permission state.
  - `/vendor/undangan/[token]`: set a password (IAM-1 policy), then `/vendor/masuk`, where TOTP enrolment is forced.
  - Writes go through the existing JSON route (`/vendor/api/console/<action>`). Acceptance is the one action without a session: Origin check, token and password only, and the new account is discarded when acceptance fails (as T-031).

## Acceptance (runnable)

- `tests/vendor/bootstrap.test.ts` runs the command as a child process against a harness database:
  - **Success:** creates exactly one platform owner, the allowlist row and a vendor-log row. The password signs in on the vendor auth surface (the hash is Better Auth's), and TOTP enrolment is then required.
  - **Second run:** refused, logged, no new account.
  - **Refused with no account left behind:** weak password, mismatched confirmation, wrong CIDR or wider than /16, existing email.
  - **Secrets:** the password appears in no output.
- `tests/vendor/team.test.ts`:
  - **Invite → accept:** creates vendor staff with exactly the invited roles; the link works once, only for that email, expires, and is cancellable.
  - **Refusals:** acceptance is refused after the inviter lost platform owner, for an email that is already vendor staff, and for an account with an unapproved clinic membership.
  - **Access:** only a platform owner lists, invites, cancels or changes state; a stale step-up is refused; every refusal is logged.
  - **Rules kept:** not oneself, not the last platform owner.
  - **Privileges and history:** the invitation history is forward-only; `clinic_vendor` and `clinic_app` read no table.
- Browser (`tests/ui/vendor-team.spec.ts`) at 390/820/1180/1440 and 200% text:
  1. the first platform owner (made by the command) invites a second platform owner;
  2. the second accepts, sets a password, enrols TOTP, and approves a first-owner invitation (closing the DEC-033 loop);
  3. Nonaktifkan / Aktifkan Kembali;
  4. a non-owner sees no Tim Vendor menu;
  5. no console error and no CSP violation.
- Full suite, typecheck, lint, docs:check. Mutation-test every control. Independent review (codex, R3) until APPROVE.
