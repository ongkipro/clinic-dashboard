## Design (proposed)

No migration (the database already has the time rule and the releasing writer).

`src/modules/scheduling/lateness.ts`:
- `lateness(db, branchId)`: the branch's SET-15 in force now (`settingValue`), `null` when off.
- `lateReleasable(db, branchId)`: when SET-15 is set, the branch's appointments still booked or confirmed whose start + N minutes has passed (from `appointments_window` for today, read through the calendar); `[]` when off.
- `releaseLate(db, branchId)`: when SET-15 is off, releases nothing and returns `[]` (scenario PR-8); when on, marks each releasable appointment no-show through `markNoShow` (the existing writer: role, lifecycle, scope, the time rule, the reservation release, an ids-only event), each with its own idempotency key derived from the appointment (`lateness:<appointment id>`, so a repeated run replays instead of failing), and returns the released ids. No money moves; no session is touched (BILL-24).

## Open point for the plan review

1. Release = the no-show state (the only releasing state for an unattended appointment; DP effects then follow BILL-13 in M4, as SET-15 says). The alternative, a separate "released" state, needs a migration outside the Allowed Paths and duplicates no-show.
