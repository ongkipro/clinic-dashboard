## Design (proposed)

Principle: a manual discount within the issuer's SET-12 limit is applied at issue exactly as today; above the limit the line is issued **at full price** with a pending `manual_discount` approval for the requested amount, that line cannot be paid, and the discount is written to the line only when the approval is approved (BILL-28 "a pending discount blocks payment of that line only"). Promo codes (PR-77) are T-081.

### 1. Columns (migration: next free number, expected `0095_discounts` after T-077–T-079; `src/modules/cashier/schema.ts`)
No new table. DATA-53 `discount_limits` is served by SET-12 (`setting_versions`), so no second store of limits. DATA-61 columns on `invoice_lines`:
- `discount_kind text NULL` — `'manual'` only (T-081 adds `'promo'` to the check; no speculative value now).
- `discount_approval_id uuid NULL` — FK `(tenant_id, discount_approval_id) → approvals(tenant_id, id)`; unique per line by construction (approval subject = the line).
- Check `invoice_lines_discount_check`: `discount_kind IS NULL OR discount_kind = 'manual'`; `(discount_kind IS NULL) = (discount = 0 AND discount_approval_id IS NULL)`.
- The requested amount lives on the approval (`approvals.amount_rupiah`, integer rupiah, "the amount the approval covers"); the pending state is derived from `approvals.state` (no denormalised flag).
- Line states: no discount (kind NULL); within limit (kind manual, discount > 0, approval NULL); requested (kind manual, discount 0, approval pending); approved (discount = approval amount); rejected or withdrawn (discount 0, line at full price).

### 2. Limits per role (SET-12 only, read at the issue instant)
- `discount_within_limit(p_role text, p_gross bigint, p_discount bigint, p_at timestamptz) RETURNS boolean` (STABLE, not granted), reading `setting_value_at('SET-12', NULL, p_at)`:
  - `owner` → always true (CD-37 "owner unlimited");
  - `manager` → `p_discount * 100 <= p_gross * manajer_persen AND p_discount <= manajer_rupiah` (both evaluated, lower wins; integer arithmetic, no rounding);
  - `fo_cashier` → `p_discount * 100 <= p_gross * fo_persen` (SET-12 has no FO rupiah cap);
  - `finance` → the FO/Kasir limit (open point 1);
  - any other role → false (cannot reach `kasir_actor` anyway).
- `p_gross = unit_price × quantity` (VAT-inclusive branch price, BILL-28 "per invoice line on the VAT-inclusive price").
- The limit used is not stored separately: the setting version is reconstructible from `setting_versions` at `issued_at` (DATA-6 snapshot through the setting history; open point 6).

### 3. Writer: `invoice_issue` (re-created) and `invoice_line_snapshot` (replaced with an 8-argument version adding `p_role text`)
- Input unchanged (`lines[].discount`, integer rupiah, ≤ gross).
- In the snapshot, after the price is known: `discount = 0` → as today. Within limit → applied, `discount_kind = 'manual'`. Over limit → a new line id is generated, `approval_request('manual_discount', 'invoice_line', line_id, NULL, invoice.branch_id, p_discount)` is called first, then the line is inserted at full price (`discount 0`, `line_total = gross`, VAT on the gross) with `discount_kind = 'manual'`, `discount_approval_id` set.
- Package line with a pending discount: `package_open` is **deferred** to the decision (§5); a package discount equal to the gross is refused (`ERR_INVALID_INPUT: discount`; `packages_check` needs price ≥ 1).
- Lock order: `invoice_issue` takes staff_access first (`kasir_actor` → `tenant_actor_lock`), then the visit and invoice rows; `approval_request` re-enters staff_access (re-entrant advisory lock), the same precedent as `invoice_void_request` (`0087:812`) and `setting_set` (HYG-008a note `0048:20–24`). The line id is generated (`uuid_generate_v7()`) before the request so the approval's subject and the line's FK agree.
- Issue still succeeds ("the invoice waits for approval in Persetujuan"); the result JSON gains `discount_pending` (count of pending lines). Replay through `runCommand` returns the stored result (no second approval).
- `invoice_void_request` (re-created): refused while any line of the invoice has a pending discount (`ERR_VERSION_CONFLICT: discount_pending`); the requester withdraws first (`approval_cancel`).

### 4. Payment blocked on that line only
- Room of a line = `line_total − cancelled_amount − paid`, and **0 while its discount is pending**. Changed in: `kasir_record_payment` (cash/EDC/transfer/balance path line selection), `payment_charge_create` (charge lines), `payment_line_room` (port path).
- New `kasir_payable(p_tenant, p_invoice)` = outstanding of lines without a pending discount; `payment_receive` and `payment_charge_create` check overpayment against it; when it is 0 and a pending line exists the error is `ERR_VERSION_CONFLICT: discount_pending`.
- `kasir_outstanding` is **not** changed: the pending line is still owed at full price, so the visit payment step, treatment gating and visit close still see it (a visit cannot close with an undecided discount).
- Backstop: `payment_allocations_guard` refuses an allocation to a line whose discount is pending.
- Also any allocation writer added by T-077 (deposit apply), T-078 (receivable conversion) and T-079 must skip/refuse a pending line: the guard catches it; the auto-apply of a DP at issue must skip the line rather than fail the issue (re-create that writer if it targets lines without the room filter; verify at build time).

### 5. Decision: `discount_sync()` AFTER UPDATE OF state ON approvals (pattern `invoice_void_sync`)
- Fires for `type = 'manual_discount'`, `OLD.state = 'pending'`, `NEW.state <> 'pending'`.
- **Approver cap:** `decided_as = 'manager'` (approve or reject) is refused unless `discount_within_limit('manager', gross, amount, clock_timestamp())` (`ERR_FORBIDDEN: only the owner may decide this discount`) — "an approver approves only within their own limit, otherwise the owner". The owner is unlimited. Requester ≠ approver, approver roles, pending only, rejection reason: unchanged `approval_decide`.
- **Approved:** lock the invoice then the line; re-check (invoice `issued`, no allocation on the line incl. simulated, `vat_recognised_amount = 0`, `cancelled_amount = 0`); set `discount = amount`, `line_total = gross − amount`, `(vat_base, vat_amount) = tax_vat_split(line_total, tax_category, invoice.is_pkp_at_issue)` — identical to what the snapshot would have produced at issue (same PKP instant, same category; `vat_on_invoices` gate already passed at issue). Emit `DiscountApproved {invoice_id, invoice_line_id, approval_id}` (TD-7; ids only; does not post by itself, `11:136`).
- **Approved, rejected or withdrawn (cancelled):** if the line is a package line, `package_open(i, i.issued_by, i.issued_as, i.issued_at)` now (sale-time branch prices, SET-8/SET-9 and validity from the issue instant; BILL-7 split of the final `line_total` = "a package discount scales session values pro rata"). Then `kasir_visit_payment(i.tenant_id, i.visit_id)`.
- `invoice_lines_guard` (re-created) allows exactly one transition: `discount` 0 → the approved approval's `amount_rupiah` with the derived `line_total`/VAT, only while the approval is `approved`, nothing allocated, nothing recognised/cancelled; `discount_kind` and `discount_approval_id` frozen from insert.

### 6. Interactions
- **VAT:** always on the line total after discount (BILL-6/28) through `tax_vat_split`; no VAT exists on the pending line's payments because there are none.
- **Packages (BILL-7):** within-limit discounts already flow into `package_open` (split of the discounted `line_total`); pending ones open at the decision (above).
- **Additions (T-074):** addition lines may carry a discount; a pending one keeps the visit open (outstanding) until decided; release-before-payment is unaffected.
- **Substitution lines:** discount stays forbidden (unchanged).
- **Deposits (T-077) / receivables (T-078) / consultation (T-079):** never allocate to a pending line (guard + writer filter).
- **Integer rupiah:** all values `bigint`; percent test by cross-multiplication; no float or numeric rounding.

- `INSERT INTO approval_types VALUES ('manual_discount', 'Diskon manual', '{fo_cashier,manager,finance}', '{owner,manager}', false)`; mirror in `src/modules/approvals/inbox.ts` `APPROVAL_TYPES` (asserted by `tests/approvals/inbox.test.ts:170`).
- Inbox helper `approval_manager_decides_discount(uuid) RETURNS boolean` (STABLE SECURITY DEFINER, granted to `clinic_app`, as `approval_manager_decides_void`); `inbox.ts` list filter and detail `not-approver` like the void (`:115`, `:138`).
- Events: `ApprovalRequested`/`ApprovalDecided` (existing, ids only); `DiscountApproved` (ids only). No clinical content.
- Audit: existing `approval_requested`, `approval_approved/rejected` and `invoice_issued`; no new audit action.
- Grants/RLS: no new table; `invoice_lines` already readable (`0086:199–203`); new functions are not granted except the inbox helper. Reader `kasir_invoice_get` (re-created) adds per line `discount_kind`, `discount_pending` (requested amount while pending) for the Kasir screen.
- Report data (PR-72 "every manual discount appears in the suspicious-activity report", SEC-19 requester/approver/amount): `invoice_lines.discount_kind = 'manual'` + `invoices.issued_by` (requester) + `approvals.requested_by/decided_by/amount_rupiah`. The report reader belongs to UX-53 (open point 3).
