## What is built (candidate migration `0127_vendor_health`; DEC-122)

### Reader (function + grant only: no table, no index, no schema change; snapshot 0127 = 0126)
- `vendor_console_health(token, ip)` is SECURITY DEFINER with `search_path = pg_catalog, pg_temp`, and EXECUTE goes to `clinic_vendor` only.
  - **Guard:** `vendor_session`, then `vendor_guard(..., ['platform_owner','support'], 'health_read', ..., second factor 12 h)`.
  - **Clock:** one `clock_timestamp()`.
  - **Exit:** `vendor_log 'health_read'` success, then `vendor_authority_recheck` before the only success exit (HYG-008b).
- Per tenant (id, legal name, lifecycle state) and per provider, it returns counts, ages in seconds, instants and sanitised codes only:
  - domain-event outbox (`event_receipts` ⨝ `domain_events`: open, oldest, `dead_letter` = exhausted receipts now, per consumer code; its
    1-hour and 24-hour failure counts are `null` = not measured, since a receipt records no failure time);
  - WhatsApp outbound (`outbound_messages`, through the internal `vendor_health_whatsapp(tenant, now)`: due = `outbound_claim`'s branch-local
    day, Jakarta fallback; backlog age since `created_at`);
  - SATUSEHAT (`satusehat_outbox` / `satusehat_attempts`: queue, failure rate 1 h);
  - payment webhooks (`payment_webhook_events`);
  - Meta webhooks (`meta_webhook_receipts`, unrouted).
- WAL archive comes from `pg_stat_archiver` (readable without privilege on PostgreSQL 16) and is reported only while `archive_mode` is
  on, else `wal_readable: false`.
- The reader never returns patient ids, contacts, payloads, template / provider message ids, order refs, amounts or error bodies. A code
  that fails `^[A-Za-z][A-Za-z0-9_.]{1,48}$` becomes `lainnya` (`vendor_health_code`, `vendor_health_codes`: top 5, granted to nobody).

### Page `/vendor/kesehatan` (Konsol Vendor › Kesehatan Platform)
- `model.ts` (pure):
  - `projectHealth` keeps an explicit allowlist of the reader's keys;
  - `safeCode` mirrors the SQL pattern;
  - OBS-4 thresholds are constants (backlog > 15 min, SATUSEHAT failures > 5 %/h, heartbeat 5 min, backup 26 h);
  - `statusOf` returns alert / warning / ok / none.
- **Option A (D1):** uptime, worker heartbeat, backup age and the app error rate have no source yet. They always render "Belum terpantau"
  with the reason, never 0 or 100 %.
- `view.tsx`:
  - summary cards, provider and attention filters;
  - a table at ≥ 700 px, cards below;
  - states: permission, error, empty, filtered-empty, ok.
- `page.tsx`: `consoleGate`, role check (platform_owner, support), reader, `resolveView`. `loading.tsx` and `error.tsx` complete the route.
- Navigation: a "Kesehatan Platform" row in the console shell for platform_owner and support (`19` §3).

## r2 (independent review `1d2a370d`; Panel 2 `PANEL2-R1-REVIEW-DECISION.md`)
freeze-r1, close 1 and the review are kept. Both findings were reproduced on the r1 SQL with synthetic fixtures first
(`exec/r2-on-r1-1795124199.log` in the lane notes: the two new tests and the two r1 tests whose outbox assertions now expect
`dead_letter` failed), then fixed:
- **#1 WhatsApp due backlog (P1):** the reader used the Jakarta day for every message.
  - Now `vendor_health_whatsapp(p_tenant, p_now)` (internal, granted to nobody) applies `outbound_claim`'s rule (0115): `planned_for` ≤
    today in the message's branch timezone. The branch lookup is tenant-qualified; Asia/Jakarta applies when the message has no branch.
  - One predicate serves both the open count and the oldest age. The age is backlog age (since `created_at`), not time since due.
  - `p_now` is the reader's single clock read (the `p_now` pattern of `outbound_budget_limit` / `inbox_next_assignee`); no production
    clock override.
  - Test: at 2026-11-20 16:30 UTC (23:30 WIB, 00:30 WITA, 01:30 WIT), messages planned for the 21st give these results:
    | Branch | Open | Age | Status |
    |---|---|---|---|
    | WITA | 1 | 2400 s | alert |
    | WIT | 1 | 2400 s | alert |
    | WIB control | 0 | — | ok |
    | no branch (Jakarta fallback) | 0 | — | ok |
- **#2 Outbox (P2):** exhausted receipts were labelled "failures in 24 h".
  - They are now `dead_letter`, a current stock that stays actionable: the warning reads "N habis percobaan (surat mati)", also named
    beside an alert.
  - The outbox's 24-hour and 1-hour failures are `null` and render "Tidak diukur" in the table and the narrow cards. They are never 0,
    never the stock, never dated by `occurred_at`.
  - Test: a receipt exhausted 3 days ago gives `dead_letter: 1`, `failed_24h: null`. The same tenant's WhatsApp failures keep their real
    window: decided 2 days ago is out, 2 hours ago is in (`failed_24h: 1`).
  - Browser flow 12: the dead letter and "Tidak diukur" appear in the wide table and the card.
- SQL mutants: 13 (8 kept, one re-anchored to the helper with the same intent, 5 new), all killed.

Residual risks (recorded, not in scope):
- Error codes are sanitised lexically, not against a catalogue. A syntactically valid future SATUSEHAT code is shown.
- WAL archive-on behaviour is tested only statically (`archive_mode=off` in tests). An archive time is not a backup or restore proof.
- Pilot-scale scans (`// lazy:` in the SQL).
- The WhatsApp age is since creation even when a message was scheduled or deferred later. That is backlog age by decision #1; the time
  since due is not shown.
- The outbox has no failure-time source. A 24-hour failure flow would need a recorded failure instant on `event_receipts`.
