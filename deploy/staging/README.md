# Staging deployment (Coolify, KlinikMu Indonesia server)

Synthetic data only (MIG-2, DEC-034). `DEPLOY_ENV=staging` on the app and `platform_environment = 'staging'` in the database
keep the ARCH-10 real-patient gate exempt for synthetic runs only (DEC-125). Mock adapters for WhatsApp, SATUSEHAT, payments
and AutoLaris; no live provider call. Not a production definition.

## What runs

| Service | Image | Job |
|---|---|---|
| `postgres` | `postgres:16.15-bookworm` | database, default durability (unlike the local-dev `compose.yaml`, which runs `fsync=off`) |
| `migrate` | the app image plus `roles.sh` and `roles-entrypoint.sh` baked in | one-shot: `src/db/migrate.ts` as the owner role, then `roles.sh` (four login roles, `platform_environment`) |
| `app` | the repository `Dockerfile` | Next.js on port 3000; starts only after `migrate` exits 0; healthchecked via `GET /api/health/db` (`Host: $APP_HOST`) |
| `worker` | exact same built `app` image (`DEL-4`) | `node /app/migrate/worker/workers/runner.js` as `clinic_app_login` (outbox ledger posting, PR-52 export build + 24h expiry, PR-67 booking PII purge, internal CRM/daily scans; zero live external provider calls); healthchecked via `/tmp/clinic-worker-heartbeat.json` |

Not yet included: a pgBackRest sidecar for scheduled off-host backups; live Meta/SATUSEHAT/AutoLaris dispatch stays disabled on staging.

## Coolify settings

- Source: GitHub App, repository `ongkipro/clinic-dashboard`, branch `main`.
- Build pack **Docker Compose**, base directory `/`, compose file `/deploy/staging/compose.yaml`.
- **Auto-deploy off.** Deploy a commit whose CI is green, by hand.
- Environment name `staging`.
- Coolify > Advanced: **Inject Build Args to Dockerfile off** and every variable **runtime only** (not build time);
  otherwise Coolify writes the generated passwords into `ARG` lines that stay in the image history.
- Build paths resolve from the repository root: Coolify runs compose with `--project-directory` at the checkout root,
  and turns relative bind mounts into empty directories, so nothing here is bind-mounted from the repository.
- Domains, all on service `app`, port 3000:
  `https://stg-app.klinikmu.com:3000`, `https://stg-vendor.klinikmu.com:3000`, `https://stg.klinikmu.id:3000`.
- **Staging-only Cloudflare proxy exception (`OD-I9`):** unlike production (where `AGENTS.md` / `H-02c` forbids proxying `APP_HOST` and requires DNS-only), all three synthetic staging hosts sit behind Cloudflare proxy (`TRUSTED_IP_HEADER=cf-connecting-ip`). This exception is strictly staging-only (`MIG-2` synthetic data); origin port 443 IP restriction to Cloudflare ranges remains an open pre-production infra hardening item and production `APP_HOST` must stay DNS-only.

## One-time host preparation (KEK)

```sh
sudo install -d -m 0750 -o root -g 1000 /data/klinikmu/staging
umask 077; printf '1:%s\ncurrent=1\n' "$(openssl rand -base64 32)" | sudo tee /data/klinikmu/staging/kek >/dev/null
sudo chown 1000:1000 /data/klinikmu/staging/kek && sudo chmod 0400 /data/klinikmu/staging/kek
```

The app runs as uid 1000 (`node` in the image) and refuses a KEK file that is a symlink, not 0400/0600, or owned by another
user (`src/lib/keys/kek-file.ts`). Keep an offline copy of this file with the owner (ARCH-7): losing it makes encrypted fields
unreadable.

## After the first deploy

First platform owner (DEC-036), once, in the server terminal (needs a TTY; the password is typed at the script's hidden
prompt). Run a one-off container from the deployed migrate image on the application's network, with the database owner
password read from the `postgres` container's environment and passed to `docker run` by variable name only:

```sh
APP=<coolify application uuid>
PG=$(docker ps --format '{{.Names}}' | grep "^postgres-$APP")
IMG=$(docker inspect -f '{{.Config.Image}}' "$(docker ps -a --format '{{.Names}}' | grep "^migrate-$APP")")
P=$(docker exec "$PG" printenv POSTGRES_PASSWORD)
DATABASE_URL="postgres://clinic_owner:$P@postgres:5432/clinic_dashboard"; export DATABASE_URL; unset P
docker run --rm -it --network "$APP" -e DATABASE_URL -u node -w /app/migrate --entrypoint node "$IMG" \
  --disable-warning=MODULE_TYPELESS_PACKAGE_JSON src/db/vendor-bootstrap.ts \
  --email <email> --nama "<nama>" --cidr <your IP>/32 --label "Kantor"
```

Then sign in at `https://stg-vendor.klinikmu.com/vendor/masuk` and enrol TOTP.

## Synthetic demo seed & reset (`HYG-DEMO-1`)

Staging demo data is seeded exclusively through real application writers (`scripts/demo/seed.ts`) — including vendor tenant provisioning, maker-checker first-owner invitation, onboarding compliance & checklist, PR-59 go-live, Better Auth with production database rate limiting enabled, fresh per-sign StepUp proofs, and event-driven ledger outbox completeness verification — and reset by dropping, recreating, re-migrating, and stamping `platform_environment = 'staging'` (`scripts/demo/reset.ts`), never by deleting clinical or financial rows one by one. Reset must only target a dedicated, disposable staging PostgreSQL instance whose admin endpoint cannot address production.

- Both scripts fail closed unless **`DEPLOY_ENV=staging`**, **`public.platform_environment.deploy_env = 'staging'`**, AND **`public.residency_attestations` exists with zero `production` rows**.
- `scripts/demo/seed.ts` requires explicit deployed configuration (`DATABASE_URL`, `APP_DATABASE_URL`, `AUTH_DATABASE_URL`, `VENDOR_DATABASE_URL`, `DEMO_CREDENTIALS_FILE`, `APP_URL`, `VENDOR_URL`, `BETTER_AUTH_SECRET`, `DEMO_VENDOR_ALLOWLIST_CIDR`), holds a live `SHARE` fence on the marker tables + `SEED_LOCK_KEY`, verifies every physical connection across all four pools against the fence, and refuses to run twice (`DemoAlreadySeededError`); reset first before re-seeding.
- Demo passwords and TOTP secrets are generated at runtime and written atomically (Linux POSIX, verified ancestor chain + pinned parent fd + `O_EXCL | O_NOFOLLOW` + `fchmod 0600`) strictly to `DEMO_CREDENTIALS_FILE` **outside the repository** (never printed to stdout/stderr or committed).
