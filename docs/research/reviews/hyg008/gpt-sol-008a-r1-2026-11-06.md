### Findings

#### HIGH — The new post-audit-lock check does not revalidate role or branch authority

**Location:** `0048.sql:806–815`

The initial authorization joins staff, membership, acting role and branch scope (`0048.sql:785–800`), but the new post-lock check tests **only membership dates**.

This does not implement change item 3’s explicit requirement to repeat the same membership, role and branch check after the audit lock. A concrete interleaving is:

1. A role-removal transaction removes B’s acting role and holds the audit lock before committing.
2. B’s `audit_append` sees the still-committed old role, passes its initial check, and waits.
3. The removal commits.
4. B’s new recheck passes because B’s membership remains active, and an event is appended under the removed role.

Branch-scope removal has the same omission. The existing waited-audit test covers only membership termination (`authority-clock.test.ts:266–280`).

**Smallest fix:** repeat the initial staff/membership/role/branch authorization predicate after acquiring the audit lock, retaining the wall-clock bounds. Add role-removal and branch-removal interleavings that assert rejection at this check.

#### MEDIUM — An invitation appearing between the two token reads bypasses `staff_access`

**Location:** `0048.sql:970–976`

If the first token lookup returns no rows, the loop acquires no lock. The subsequent `SELECT … FOR UPDATE` is nevertheless executed. Because this is a volatile function with separate statements, that second read can see an invitation committed after the first read.

Thus:

1. Accept’s first lookup finds no token.
2. A concurrent invitation creation commits that token.
3. Accept’s second lookup finds it and proceeds without holding the tenant’s `staff_access`.

This defeats the new lock-order/serialization invariant precisely on the newly introduced two-read path. The supplied test exercises an already-existing invitation, so it does not cover this case (`authority-clock.test.ts:344–376`).

**Smallest fix:** resolve the tenant into a dedicated variable and immediately raise the existing generic `P0002` if no token was found. Only then acquire `staff_access` and reread the invitation `FOR UPDATE`. Require the reread to belong to the resolved tenant as well, rather than accepting any newly resolved mapping.
