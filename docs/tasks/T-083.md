## 4 Design

### 4.1 Tables (DATA-67; tenant-ledger; never deleted; guards take staff_access first; no-truncate ENABLE ALWAYS)
- **`instalment_schedules`**: `id, tenant_id, branch_id` (the target's branch: package `sold_branch_id`, receivable `branch_id`),
  `patient_id`, `package_id` | `receivable_id` (**CHECK exactly one**), `version` (1.. per target; unique `(tenant, target, version)`),
  `state` active | cancelled, `cancel_reason` (`replaced` | `target_closed` | `paid` | `manual`), `created_by/as/at`, `cancelled_by/as/at`,
  `command_key`. Partial unique: one **active** schedule per target.
- **`instalment_rows`**: `id, tenant_id, schedule_id, seq` (1..24), `due_on date`, `amount bigint` (1..MONEY), `reminded_on date` (set
  once by the scan). Rows frozen after insert except `reminded_on` (null → date once). "Linked payments" (DATA-67): **derived**, not stored
  (open point 2) — the reader shows each row as covered when cumulative paid on the target ≥ the cumulative scheduled amount up to that row.
- Schedule invariants checked by the writer: due dates strictly increasing, the first ≥ today (branch-local), sum of rows ≤ the target's
  **open amount** (package: `price − package_paid`; receivable: `amount − collected − written_off`), row count ≤ SET-41 `cicilan_maks` when set.

### 4.2 Writers
- **`instalment_schedule_set(p_key, p jsonb)`** — p: `{package_id | receivable_id, rows: [{due_on, amount}]}`. Roles: owner, manager,
  fo_cashier, finance (Paket & Saldo / Piutang actors, `19:115-116`); branch roles at the target's branch. Locks: staff_access → target row
  `FOR UPDATE` → current active schedule. Refused: target not active/open (`ERR_VERSION_CONFLICT: target_closed`), package without
  instalments (`min_dp = price` → `ERR_INVALID_INPUT: instalments_not_allowed`), row rules above. A previous active schedule is cancelled
  (`replaced`) and the new one is version + 1. Idempotent by key. Audit `settings_change` / `instalment_schedule_set`.
- **`instalment_schedule_cancel(p_key, p_schedule, p_reason)`** — same roles; `manual`.
- **Nothing else changes**: no receivable, journal, interest, fee, posting, event of money, or entitlement (BILL-9). `package_reserve` is
  not touched — the schedule cannot unlock a session because nothing reads it on the unlock path.

### 4.3 Automatic cancellation (DATA-67)
- When the target closes, expires or is fully paid, its active schedule is cancelled (`target_closed` | `paid`), and its un-reminded rows
  are thereby inert ("cancelling pending reminders").
- Hook: **AFTER UPDATE triggers** on `packages` (state leaves `active`) and on `receivables` (state leaves `open`), plus a check in the scan
  (a target fully paid without a state change — a package paid in full stays active → the scan cancels with `paid` when `package_paid ≥ price`).
  Triggers instead of re-creating `package_close_do`, `receivable_collect` and write-off: fewer re-created bodies, one rule. Verify at build that
  no writer updates these rows with triggers disabled.

### 4.4 The reminder (scenario PR-96)
- **`instalment_reminder_scan(p_today date DEFAULT NULL)`** — unbound worker only (as `logbook_due_scan`); for each active schedule's rows
  with `due_on < today` (branch-local), `reminded_on IS NULL`, and **not covered** (cumulative paid < cumulative scheduled through that row):
  set `reminded_on = today` and insert one `notifications` row: type **`instalment_due`** ("Cicilan lewat jatuh tempo"), recipient role
  `fo_cashier` at the target's branch, subject kind `instalment_schedule`, subject id the schedule (ids only, no amounts or names).
  Covered rows get `reminded_on` too (no reminder) so they are not re-scanned? → No: covered rows are skipped and stay null; the coverage
  test is cheap. Returns the count.
- The `notification_types` row is inserted by this migration (`raisable_by_staff false`, roles `{fo_cashier}`, kinds `{instalment_schedule}`).
- TS runner `src/modules/packages/schedules/scan.ts` (`runInstalmentReminderScan(worker, today?)`), as `expiry.ts`. Scheduling the worker
  call belongs to the platform worker wiring (the same place as the expiry scan; verify at build whether a registry exists — if it is outside
  Allowed Paths, the runner is exported and the wiring is a follow-up).
- WhatsApp to the patient: not here (messaging tasks; PR-4 consent).

### 4.5 Readers
- **`instalment_schedule_get(p_package uuid, p_receivable uuid)`** (exactly one) — Kasir readers (`kasir_reader`): owner, finance, auditor
  tenant-wide; manager, FO at the branch. Returns the active schedule and its history: rows with `due_on`, `amount`, `covered`, `overdue`,
  `reminded_on`; the target's paid and open amount. `package_row` / receivable readers are **not** re-created (open point 3).
- RLS on both tables: readable by the Kasir readers' rule (`package_readable` / receivables' policy); no write grants.

## 7 Open points (recommendations; no [OWNER] point)

1. **Reminder recipient.** Scenario says "a reminder task"; no task table exists. → In-app notification to FO/cashier at the target's branch
   (PR-54 mechanism; acknowledged once by anyone). A patient WhatsApp reminder waits for the messaging tasks.
2. **"Linked payments"** (DATA-67). → Derived coverage (cumulative paid vs cumulative scheduled), not stored links: payments allocate to
   invoice lines, not to schedule rows, and a stored link would be a second ledger that could drift. If the reviewer reads DATA-67 as
   requiring stored links, add `instalment_row_payments(row, payment)` filled by the scan.
3. **Reader placement.** → A separate reader instead of re-creating `package_row`/`package_patient_get` (T-082 re-creates them; avoids two
   tasks churning one body). The UI follow-up joins them.
4. **Schedule above the open amount.** → Refused (sum ≤ open); below is allowed (the rest stays unscheduled).
5. **Editing.** → Replace = new version; rows never edited (history kept).

## Plan review r1 (Argon `7987f752`, REVISE) — all findings adopted; this section overrides §4–§9 where they differ

**P1-1 coverage after earlier payments.** Paid on the target = `kasir_line_paid(tenant, pk.invoice_line_id)` for a package (real money,
≤ price; not `package_paid`, which subtracts a cheaper substitution's `moved_to_balance`, `0091:247`) and `r.collected_amount` for a
receivable. Open = `pk.price − kasir_line_paid(…)` (as `package_close_do` `0095:1076`, `kasir_outstanding` `0094:975`) or `amount −
collected − written_off`. Each schedule version stores **`base_paid`** (the target's paid amount when the version is created); the rows
cover the open amount (`sum ≤ total − base_paid`); row k (cumulative `cum_k`) is **covered iff `paid − base_paid ≥ cum_k`**. So a DP paid
before the schedule never covers row 1 (scenario PR-96 with the min DP paid raises the reminder).

**P1-2 auto-cancel, lock order, actors.**
- Fully paid without a state change: an **AFTER INSERT trigger on `payment_allocations`** (ENABLE ALWAYS; real allocations to a line) cancels
  the active schedule of the package whose `invoice_line_id` it is, with `paid`, once `kasir_line_paid ≥ price`; receivables are covered by
  their state trigger (collected). The scan keeps the check as a backstop. Still no re-created function.
- `cancelled_by/as` required only for `manual`/`replaced`; for `target_closed`/`paid` they are `coalesce(app_staff_id(), the closing row's
  actor)` or NULL when a service context closes the target (expiry scan, webhook) — the CHECK and the guard follow this.
- The scan: tenants in `onboarding/live/suspended` only (`0085:512`); **per candidate schedule takes staff_access first**
  (`pg_advisory_xact_lock('staff_access:'||tenant)`, as `package_expiry_scan` `0091:1730`), then locks the schedule and rows `FOR UPDATE`, then
  re-checks state, target, `reminded_on IS NULL` and coverage under the lock.

**P2-3 constraints, writers, RLS.**
- Per-target uniques: `UNIQUE (tenant_id, package_id, version)`, `UNIQUE (tenant_id, receivable_id, version)`; partial uniques for one active
  schedule per package / per receivable (`WHERE state = 'active' AND <target> IS NOT NULL`).
- `instalment_schedule_cancel(p_schedule uuid)` (no key in SQL; `runCommand` in TS): no-op when already cancelled `manual`, conflict when
  cancelled for another reason. `instalment_schedule_set(p_key, p)`: replay by `(tenant, command_key)` returns the schedule when target and
  rows match, else `ERR_IDEMPOTENCY_CONFLICT`; the instalments-not-allowed check (`min_dp = price`) before the open-amount check.
- `instalment_rows.branch_id` with composite FK `(tenant_id, branch_id, schedule_id) → instalment_schedules(tenant_id, branch_id, id)` (as
  `receivable_lines`, `0094:19,86`); both tables: `kasir_readable(tenant_id, branch_id)` policy, `clinic_operator` `operator_row_read`
  policies and grants, scope map `tenant-ledger`, support class `personal`. The rows guard refuses `reminded_on` on a non-active schedule.

**P3.** Open points 1 and 2 confirmed (in-app notification; derived coverage). `instalment_schedule_get` returns per row the derived
`linked_payments` (payment ids of real allocations whose cumulative interval overlaps `(base_paid + cum_{k−1}, base_paid + cum_k]`) to mirror
DATA-67. The drift test asserts byte-identity of every pre-existing function (pattern `tests/db/safety-drift.test.ts:66-72`, no expected
file needed). The scenario test also asserts that `instalment_schedule_set` itself writes no receivable, balance entry, money event or unlock.

**Updated §5:** no function re-created; added triggers on `packages`, `receivables` (state) and `payment_allocations` (insert).
