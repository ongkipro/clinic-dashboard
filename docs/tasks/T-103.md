## a2-1 Bayar finish privilege change (security boundary; Panel 2: narrowly fenced, matching the audited unbound pattern)
Problem: the app has no executor login; increment 1 granted `vendor_billing_bayar_finish` to clinic_executor only, so the request path cannot
complete an attempt. Change (0120):
- `vendor_billing_bayar_begin` (re-created, same signature) also returns a one-time **finish token** (32 random bytes, base64url) and stores only
  its SHA-256 in a new frozen column `vendor_payment_attempts.finish_token_hash` (set at insert; the guard keeps it immutable). The token lives
  only in the server process between begin and finish; never logged, never sent to the browser, never in the idempotency replay (a replayed
  begin returns no token → the replaying caller cannot finish and makes no provider call). If the first caller dies: an attempt whose provider
  id was persisted is resolved by Advice; one without a provider id is recovered to `unknown` and **stays blocking** (no second create) until
  the owner's reconciliation decision (D2) — the existing crash limitation, unchanged by the token (Sol 172bf5a5 P2).
- `vendor_billing_bayar_finish(uuid, integer, text, jsonb, timestamptz, text)` is re-created with a new first-line fence: refuses a BOUND
  connection (`vendor_billing_unbound()`: app.tenant_id / staff id set → 42501, as `satusehat_unbound`), requires the token (new signature
  `vendor_billing_bayar_finish(uuid, text, integer, text, jsonb, timestamptz, text)` — attempt, token, generation, outcome, answer, now,
  service; the old signature is DROPPED), compares sha256(token) with the stored hash in constant time; a missing / forged / other-attempt
  token → ERR_FORBIDDEN, nothing written, logged (`vendor_log` denied, reason `finish_token`). The tenant is read from the persisted attempt,
  never from the caller. Grants: clinic_app and clinic_executor (the executor grant is the existing one; no other worker grant).
- Replays: a second finish with the right token after the attempt left `creating` follows the existing stale / late-answer rules (no state
  regression; the provider id learnt once); with a wrong token nothing is written.
- Tests (state proof): a replayed begin returns no token and causes no second create; with the first caller gone and no provider id the attempt
  stays blocking after recovery; bound clinic context refused; vendor login refused (no grant); forged, empty, other attempt's token refused with the
  attempt / invoice / outstanding unchanged; correct token from another tenant's attempt impossible (token per attempt); replay after completion
  → stale, nothing regressed; replayed begin returns no token.

## 2. Invoicing (BILL-31; Scenario PR-61 prorated first month)
- First invoice on go-live (the lifecycle event onboarding → live; worker reads `tenant_lifecycle_events`): amount =
  floor(fee × days(go-live date inclusive … month end) ÷ days in month); issue date = go-live date (Asia/Jakarta), due = issue + 10 days.
  Scenario: 21 Nov, 30 days, Rp1,000,000 → floor(1,000,000 × 10 / 30) = **Rp333,333**.
- Monthly: issued on the 1st (Asia/Jakarta) for that month in advance, due on the 10th, for tenants live or suspended (suspended months are
  billed unless waived); not for exit/closed. Fee = the version whose effective_month ≤ period (latest), else default.
- Exit: billing stops at the exit date; the advance-billed remainder is credited per day from the invoice's **frozen basis** (fee_amount
  = the monthly fee, days_in_month, service_from, service_to — not its prorated amount): unused days = days after the exit date up to
  service_to; credit = floor(fee_amount × unused days ÷ days_in_month), **capped** at the invoice's uncredited amount (amount − earlier credits);
  rounding: floor per document, the vendor keeps the sub-rupiah remainder (same rule as the first-invoice proration). Exit inside the go-live
  month: 21 Nov go-live (Rp333,333 for 10 days), exit 25 Nov → unused 26–30 = 5 days → floor(1,000,000 × 5 / 30) = Rp166,666 (≤ 333,333).
  An exit-remainder credit note is a system document (the approved `exit` lifecycle request is its approval) and follows §4b allocation /
  refund rules. Closed: nothing.
- Idempotent issuer `vendor_billing_issue(p_now)` (unbound worker, `clinic_executor`): one invoice per (tenant, period) by UNIQUE; safe to run
  repeatedly; never edits an issued invoice. Numa Klinik pilot: billed like any tenant unless a waiver is recorded (Q-16 — no special case).

### 2b. Credit allocation (BILL-31 "a double settlement becomes a credit on the next invoice")
- Credits (double settlement, exit remainder on a paid invoice, approved partial credits on a paid invoice) are **open credit balance**
  documents of the tenant (`vendor_credit_notes.remaining_rupiah`). The issuer, in the same transaction that inserts the next invoice, allocates
  open credits oldest first into `vendor_credit_allocations` (credit, invoice, amount) up to the invoice amount; `remaining_rupiah` decreases;
  the invoice's issued amount never changes — its **outstanding** = amount − allocations − payments. Partial use carries the rest forward.
  A credit on an unpaid (issued) invoice is allocated to that invoice itself at once. The allocation is idempotent (UNIQUE(credit, invoice)) and
  serialized by the tenant billing lock (§Concurrency), so a credit is never spent twice. An invoice whose outstanding reaches 0 by credits
  becomes `credited` (waiver: `waived`). Leftover credit at exit stays as a balance for the vendor's offline refund (out of scope; listed on UX-43).

### Settlement allocation (no negative outstanding, no lost money)
- A verified settlement (confirmed rule, rc 00, amount = attempt amount) creates one `vendor_payments` row and is **allocated only up to the
  invoice's remaining payable** (amount − credit allocations − earlier payment allocations, never below 0) as a `vendor_payment_allocations`
  row; any **excess** (the invoice was partly credited, waived, fully credited or already paid while the attempt stayed payable) becomes an
  idempotent tenant credit note kind `overpayment` (UNIQUE per payment) with that excess as `remaining_rupiah`, allocated by §2b to the next
  invoice. Outstanding = amount − credit allocations − payment allocations ≥ 0 always (CHECK on the derived view via the writer + a test).
  The invoice becomes `paid` when payment allocations + credit allocations cover it with at least one payment; `waived` / `credited` keep
  their state and a later settlement only creates the overpayment credit.
- A waiver or credit applied while an attempt is open does **not** cancel the attempt at the provider (impossible) — the attempt stays in
  reconciliation; Bayar for the remaining amount needs that attempt resolved first (one open attempt per invoice still holds).
