# T-023 — Tenant provisioning from the vendor console (PR-1, PR-53, TEN-12)

Status: Implemented, in review (owner decision DEC-033) · Risk: R3 (tenancy, vendor access, PII-free platform write) · Depends on: T-022 (lifecycle, `vendor_console_tenant_advance`), T-019 (processor agreement evidence), T-021 (vendor console, session-bound guard) · Executor: pi (cc/claude-opus-5-5)

## Requirement

- **PR-1:** when the vendor creates a tenant, the system creates one brand and one legal entity with at least one branch, and isolates all tenant data from every other tenant.
- **PR-53:** the vendor operator console provisions tenants.
- **TEN-12:** provisioning → onboarding requires the signed processor agreement and NDA (PRIV-8). No real personal data enters a tenant before that.
- **UX-40:** Konsol Vendor › Tenant has the primary action "Buat Tenant". The table → tenant detail page has the tabs Ringkasan · Cabang · Onboarding · Integrasi · Tagihan · Sesi Dukungan · Audit. Ringkasan is the only tab built here; the others come with their tasks.
- **Done when (TASKS.md):** creating a tenant writes the registry, tenant and branch rows. Moving to onboarding is refused while the processor-agreement evidence is not approved.
- **Added by the owner's decision (DEC-033):** a first-owner invitation issued from the console (maker-checker), and Saya › Profil & Keamanan (change password, authenticator, backup codes, sessions) for every invited staff member and owner.

## Design

1. **`vendor_console_tenant_create(token, ip, legal_name, sak_framework, branch_code, branch_name, branch_timezone, reason)`**
   - SECURITY DEFINER, granted to clinic_vendor.
   - Guarded like every console write: vendor session, `vendor_guard` with the role `onboarding` or `platform_owner`, TOTP step-up within 10 minutes, allowlisted IP.
   - In one transaction it creates:
     - the `tenants_registry` row (state `provisioning`)
     - the `tenants` row (legal name, SAK framework)
     - the first `branches` row (code, name, IANA time zone from a short list: Asia/Jakarta, Asia/Makassar, Asia/Jayapura)
   - Inputs are validated (lengths, code `^[A-Z0-9]{2,8}$`) and refusals are logged.
   - It writes a `vendor_actions` row naming the new tenant, then a tenant audit-chain row through `vendor_log` (SEC-16), then the lifecycle history row `—→provisioning`.
   - The history table only records transitions. Creation is in `vendor_actions` instead, so the history keeps its `from <> to` rule.
   - It does not take PII (no owner email). No real personal data is accepted before onboarding, per TEN-12.
2. **Processor-agreement gate.** `vendor_console_tenant_advance(… 'onboarding')` from T-022 already refuses until `processor_agreement_signed` is approved.
   - **Open:** the tenant has no staff in provisioning, so nobody in the clinic can upload that evidence. See Open points.
3. **Console pages (UX-40):**
   - Tenant list: adds "Buat Tenant" for onboarding and platform owners, as a link, not a button for every role, per NAV-1.
   - `/vendor/tenant/baru`: a form for legal name, SAK framework (EMKM/EP), first branch code, name and time zone, and reason. On success it shows "Tenant dibuat" and links to the detail page.
   - `/vendor/tenant/[id]`, the Ringkasan tab:
     - state, legal name, branches (names), and creation (when, by whom)
     - the lifecycle history (from→to, reason, when)
     - the processor agreement status (approved or not), plus "Mulai Onboarding" for onboarding and platform owners, enabled only when the agreement is approved
     - nothing else, so no patient or staff data (PR-60)
   - The writes run as Server Actions. The vendor proxy currently refuses every Next-Action and every non-GET outside the auth API (T-021), so an allow-list for exactly these vendor actions is needed; `src/proxy.ts` is outside the allowed paths and gets an expand-scope.
   - States per spec 10: loading, empty, error (Coba Lagi), success, blocked (agreement missing: "Perjanjian pengolahan data belum disetujui. Owner klinik mengunggahnya di Kepatuhan.").
4. **Isolation.** Tenant ids in vendor URLs resolve only through vendor functions. The clinic app never sees `vendor_console_*`. Tenant-controlled strings are escaped (React text).

## Owner decision (2026-11-03): first owner from the vendor console; self-service security

Paduka Ongki: "user awal = owner … ya dari konsol vendor → nanti staf atau owner yang di undang bisa ganti password dan 2nd security (authenticator code)". Recorded as DEC-033.

1. **Creating a tenant names its first Owner** (name and email from the contract) and creates a **first-owner invitation** in the same transaction. The invitation is pending a second person:
   - an onboarding or platform-owner staff member creates the tenant (maker);
   - a *different* platform owner approves the invitation in the console (checker);
   - only then does the console show the one-time link once, for the vendor to send to that email.
   - This follows the recommendation and the owner's "ya" (maker-checker), because whoever holds the link becomes the clinic's only Owner.
2. **The first-owner invitation:**
   - is valid only while the tenant has no active Owner, and is cancelled when one joins;
   - works once, only for that email, and lasts 7 days;
   - can be cancelled or reissued (maker-checker again);
   - can never be accepted by a vendor-staff account (IAM-10);
   - is audited in the vendor log and the tenant chain.
   - Accepting it creates the membership with the Owner role directly. Accepting is the person's own confirmation, so the D7 rule is satisfied without a second step.
   - The Owner must enrol TOTP at first sign-in (T-006 gate).
3. **Contact data before the processor agreement.** The Owner's name and email are contract-party contact data, not patient data. TEN-12 forbids *real personal data of patients/data subjects of the clinic* before the agreement; DEC-033 records this reading.
4. **Self-service security, Saya › Profil & Keamanan (`/saya/keamanan`, 19 §2.16),** for every staff member, including the first Owner:
   - **Change password:** current password plus new password with the IAM-1 policy (≥ 15 characters, blocklist, not the email). RATE-2 counts wrong current passwords. Other sessions are ended on change.
   - **Authenticator (TOTP):** status (active/not active). Setting it up, or replacing it with a new authenticator after a password re-check, issues new backup codes.
   - **Regenerate backup codes:** after a password re-check.
   - **Turning TOTP off:** only for roles that do not require it. Roles that require TOTP cannot turn it off and see why (PR-3).
   - **Active sessions:** this device and others, with Keluar for another session.
5. **Vendor console self-service:** the same password/TOTP page for vendor staff at `/vendor/keamanan` (vendor surface, step-up rules of T-020/T-021). It can be split out if T-023 grows too large.

## As built (supersedes Design §1 and §3 where they differ)

- **Migrations:** `0039_tenant_owner_invitations` (platform table, RLS on, no grants) and `0040_tenant_provisioning_rules`.
  - The table has a forward-only history trigger (pending→issued|cancelled; issued→accepted|cancelled|expired; no rewrite, delete or truncate).
  - At most one open invitation per tenant (partial unique index).
- **`vendor_console_tenant_create(token, ip, legal_name, sak, branch_code, branch_name, timezone, owner_name, owner_email)`:** writes the registry (provisioning), tenant and first branch, plus a *pending* first-owner invitation. The Owner's name and email are contract contact data (DEC-033).
- **`vendor_console_owner_invite` / `_approve` / `_cancel`:**
  - `_approve` is platform-owner only and never the maker (`ERR_APPROVER_IS_REQUESTER`).
  - The approval is refused once an Owner exists.
  - The console generates the token; only its SHA-256 is stored, and the link is shown once to the approver.
  - Validity is 7 days. A reissue needs the checker again (open point resolved: yes).
- **`vendor_console_tenant_detail`:** returns state, name, SAK, branches, `has_owner`, the agreement flag, invitations without tokens, and lifecycle history. Nothing else.
- **`tenant_owner_invite_lookup` / `_accept`** (clinic_app, outside any tenant context), served on the existing `/undangan/[token]` page:
  - Accepting takes the `staff_access:` lock, re-checks that no Owner exists, matches the email, and refuses vendor accounts (`memberships_vendor_guard`).
  - It creates the membership, staff and Owner role, marks the invitation accepted, writes the tenant audit row `first_owner_joined`, and writes the vendor log.
- **Console writes:** these do not use Server Actions. They go to JSON routes `POST /vendor/api/console/<action>`.
  - The proxy allows only `application/json` POST there; forms, other methods and Next-Action are still refused.
  - The route checks `Origin` = VENDOR_URL and the vendor session; the database runs `vendor_guard` with a 10-minute step-up.
- **Profil & Keamanan** (`/saya/keamanan` and `/vendor/keamanan`) share `src/app/(auth)/security-panel.tsx`.
  - **Change password:** the IAM-1 policy is checked before the current password, and other sessions are always ended.
  - **Authenticator:** set up, new backup codes (password), or replace/turn off. Turning it off requires the password plus a current TOTP code. Roles that require TOTP are sent straight to re-enrolment.
  - **Sessions:** this surface's own sessions, without tokens. Another session can be ended; the current one and anyone else's cannot.
