## 6 Design sketch (to verify and complete against main after T-086)

Facts already in the code that the engine reads (checked on the T-085 tree):
- `payment_allocations` (`src/modules/cashier/schema.ts:242-256`): `payment_id`, `invoice_line_id` | `top_up_id` | `booking_deposit_id` |
  `receivable_id`, `amount`, `vat_portion`, `is_simulated`. The % basis of a line = Σ (amount − vat_portion) of its real (non-simulated)
  allocations whose target is the line (a receivable collection carries the original line through `receivable_id` → the receivable's
  originating line allocations, `11:68`; DATA-32). Top-ups and deposits earn nothing (BILL-15).
- Approval type `commission_batch` exists since 0022 (requesters finance, manager; approver owner; not owner-self).
- SET-44 batch closing day (month_end or a day 1–28); SET-24 is a reference to the rules page (no value).

Tables (DATA-36), all tenant-ledger, insert-only except the batch state:
- `commission_rules` + `commission_rule_versions`: scope (role default for a contribution type and catalog item/category, or an individual
  override for a staff member that **replaces** the role default), kind (`percent` with basis points, or `fixed` rupiah), effective from;
  versions immutable (a rule snapshot = the version id on each contribution).
- `guiding_bc_assignments`: care plan → staff, from/to, assigned/reassigned by; seeded from `selections.guiding_bc_staff_id`.
- `commission_contributions`: (staff, type ∈ closing_bc | guiding_bc | new_patient | performer, source = invoice line or counted execution
  or package session) unique per (staff, type, source) — the same person earns each actual contribution once; carries the rule version.
- `commission_entitlements`: the accrued rupiah per contribution per allocation (percent) or per completion (fixed, when the line is fully
  paid and the execution counted); `sold_branch_id` / executing branch (BILL-16).
- `commission_adjustments`: references the original entitlement; refund or moved-to-balance (B-10) → negative; before payout it reduces the
  unpaid entitlement, after payout it lands in the next open batch (PR-23); write-off (BILL-23) → the line's entitlements excluded.
- `payout_batches` (+ lines per recipient): month (per SET-44), state draft → approved (commission_batch approval, approver ≠ requester) →
  paid (Tandai Dibayar); carry-forward balance per staff when deductions exceed the month (B-13); at staff exit the remainder becomes a staff
  receivable for the owner (B-21).

Accrual: a trigger or event consumer on allocation insert (percent) and on counted execution / session redemption (fixed), idempotent by
(entitlement source, allocation id); simulated allocations and opening imports never accrue (BILL-29, DATA-58).

Screens: `/komisi/aturan` (Aturan Komisi: owner edit, finance prepare, manager view; a rule simulator), `/komisi` (Rekap Komisi & Batch:
batches by state, lines per recipient with type, adjustments and carry-forward; Setujui Batch, Tandai Dibayar, Ekspor per penerima CSV),
`/saya/komisi` (Komisi Saya: own lines only) — `/saya/komisi` is outside T-087's Allowed Paths (`src/app/(app)/komisi/**`): a scope
expansion or a later task (open point 6).

## 9 Accrual mechanism (open point 4) — finding while the plan review runs (2026-11-15)

`18-INTEGRATION-CONTRACTS.md:164-169` lists commission as a **consumer** of `TreatmentFinished(outcome)`, `PaymentAllocated`,
`PackageExpired / PackageCancelled / BalanceMoved` (TD-5, TD-7). The infrastructure exists: `domain_events` + `event_consumers` (0019;
consumers registered by their task's migration, one receipt per subscribed consumer, `consume()` once per consumer, TEN-5), the outbox
worker `src/workers/outbox.ts` (claims across tenants, applies each event in its own tenant-bound transaction, retries after the lease;
"Consumers register with their tasks (posting, stock, sessions, commission, …)"). No consumer is registered yet (grep `insert into
public.event_consumers` → nothing). Recommendation: accrue through a `commission` consumer of those events (asynchronous, idempotent by
the event id — the consumer receipt — plus the entitlement's natural key), not a trigger inside the payment transaction: the payment path
stays unchanged and fast, and the spec names this design. Consequences for the plan: (a) the batch close (SET-44) must wait for, or
re-check, unconsumed events of the period (a "lag" guard: refuse closing while receipts for events before the cut-off are pending);
(b) tests drive the worker (`runOutboxBatch`) explicitly after the money facts; (c) which events carry enough ids (PaymentAllocated payload
must name the allocation; check each producer's payload at build).

## Plan review r1 (Argon `b75ef1e9`, REVISE) — every finding checked against the code and adopted; this section overrides §3–§9

**P1-1 Attribution beyond visits.** Package sales (`visit_id IS NULL`, `0097:683-688`, `0098:386-389`), standalone substitution invoices
and visits without a `selections` row have no selection. Add `commission_sale_attributions` (tenant, `invoice_id` unique, closing BC,
attributed_by/as/at, approval_id): seeded at issue from the visit's `selections.closing_bc_staff_id`; set by command for non-visit invoices
(the FO/cashier, manager or finance who issues, before the first payment); changing a set attribution needs an approved
`attribution_correction` (`0022:15`, requesters fo_cashier/manager/finance, approvers owner/manager; wired through an approvals sync
trigger). `guiding_bc_assignments`: (tenant, `care_plan_id`) with staff, effective_from/to, assigned_by, reassigned_by, approval_id, reason;
partial unique on the open assignment; seeded from `selections.guiding_bc_staff_id` for the visit's patient's active care plan(s);
replacing an active one needs `attribution_correction`; ended when the care plan completes or stops. A sale's guiding BC = the open
assignment of the canonical patient's active care plan at the invoice's `issued_at` (visit and package invoices alike).

**P1-2 Rule time.** `rule_version_id` stays on the contribution (four contributors per line rule out one column on `invoice_lines`), and
the rule is resolved **at the originating invoice's `issued_at`** (for a package session, the package invoice's), never at the allocation
or execution time: `commission_rule_at(tenant, type, staff, item, category, p_sale_at)` over append-only versions with effective_from/to.

**P1-3 Basis paths.** % accrues on three settlement facts: (1) a real allocation to a line: basis `amount − vat_portion`; (2) a booking
deposit applied (`booking_deposits.state = 'applied'`, `applied_line_id`): basis `amount − vat_amount` on that line (`0093:405-426` writes
no line allocation); (3) a receivable collection (`receivable_id`, `vat_portion = 0`, `0094:751-754`): distributed over the receivable's
lines (`receivable_lines`) proportionally (`kasir_allocate`), each line's net share by its `vat_base / line_total`. "Line paid" for fixed =
`kasir_line_paid + collected receivable share`, with the line not cancelled, not moved to balance, not written off. **Performer** is keyed
on `treatment_executions.id` (one execution, at most one performer contribution): a package-covered execution accrues when its session is
redeemed (at the executing branch, BILL-16); a single/addition treatment accrues when both counted **and** its own line (not a
substitution difference line) is fully paid — checked on the execution finishing and on each settlement fact that completes the line.
Package lines and substitution difference lines never accrue performer through payment.

**P1-4 Consultation.** Lines of a consultation invoice (`invoices.consultation`) never match general rules; only a rule explicitly scoped
to the consultation category or item, accruing only on a charged/re-charged fee (never waived); a consultation performer is the
examination's author (`examinations`, `source_kind = 'examination'`).

**P1-5 Adjustments.** Five sources: a refund reaching paid (`refund_settle`, 0094:369), `interrupted_to_balance` (0091:1754), package close
`from_expiry`/`from_cancel` incl. unredeemed substitution lines (0091:1625, :1650-1660), `from_substitution` (0091:1927), and a write-off
(0094:774). The % adjustment basis is **net of VAT**: refund `amount − vat_reversed`; interrupted `amount − VAT reversed`; close `v_unused −
package VAT reversed` (+ each substitution line's `moved − vat reversed`); substitution `−difference − the session VAT reduction` (scenario
19: −150,000 = 5 % of 3,000,000, not of 3,330,000). When a refund, move or write-off takes a single/addition treatment line below fully
paid, its unreversed performer entitlement is reversed in full (scenario 10: −50,000). A write-off reverses every entitlement of the
written-off lines and blocks later accrual (BILL-23, scenario 14).

**P1-6 Events.** `CommissionAccrued` (entitlement insert; payload ids), `CommissionAdjusted` (adjustment insert; ids + `after_payout`),
`PayoutBatchApproved` (batch sync on approval), `CommissionPaid` (mark paid) into `domain_events` — ids, codes and booleans only
(`events_payload_ok`); amounts stay on the rows (M8 posting reads them).

**P1-7 Batches.** `payout_batches` (period key/start/end, the closing-day snapshot, state draft → pending_approval → approved → paid,
approval_id, paid_at/by/method, command key), `payout_batch_lines` (per staff: gross, adjustments, carry_forward_in, net_payable,
carry_forward_out), `payout_batch_items` (insert-only, one row per entitlement or adjustment, unique). Before/after payout: an adjustment
against an entitlement whose batch is not yet sealed (pending_approval/approved/paid) joins the open batch and reduces the unpaid amount
(scenario 9); once sealed, the batch never changes and the adjustment (`after_payout = true`) goes to the next open batch (scenario 10,
PR-23). Carry-forward (B-13): raw = gross + adjustments − carry_forward_in; net = max(0, raw); carry_forward_out = max(0, −raw). Staff exit
(B-21): `staff_commission_receivables` (open/settled/waived, the owner's decision and reason) created from an exited staff member's
unrecovered carry-forward (an `AFTER UPDATE OF effective_to ON memberships` trigger plus a check at batch close). `approvals_commission_
batch_sync`: approved → batch approved + `PayoutBatchApproved`; rejected/cancelled → draft (resubmit).

**P2-1 Mechanism, locking, rounding.** Decision: **synchronous AFTER triggers inside the fact transaction**, taking the `staff_access`
lock first (as 0090:102, 0094:295, 0101:109) — this serializes concurrent allocations and a refund racing a batch submit/approval, keeps
accrual exact at batch close, and re-creates no M4 writer. (§9's consumer option is dropped: the async lag would need a batch-close guard
and the spec's consumer table is a posting concern; the events of P1-6 are still emitted for M8.) Rounding: basis points 1–10000,
**cumulative** per contribution: `floor((cumulative_net_basis × bps + 5000) / 10000) − accrued_before`, symmetric for adjustments, so
partial payments and refunds never drift by a rupiah (SET-39 "pembulatan ke rupiah").

**P2-2 Rules UX.** Versions draft → active → superseded/cancelled: finance prepares drafts, only the owner activates or supersedes; manager
and auditor read; Admin Pusat refused (PR-63). Precedence: an active individual override for the contributor replaces every role default;
then item before category before role-wide, then priority, then version. No rule for the owner role (owner bonus separate, BILL-15).
`catalog_versions.commission_scope`: when non-empty the contribution type must be in it; when empty (the default) the item kind's standard
scopes apply (service: all four; product/package: closing BC, guiding BC, new patient). Simulator `commission_rule_simulate(p jsonb)`:
read-only, the matched versions and rupiah per contribution.

**P2-3 Tenancy.** RLS on every table; `scope_map` and `support_object_kinds` rows (rules/versions `config`; contributions, entitlements,
