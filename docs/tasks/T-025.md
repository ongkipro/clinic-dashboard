# T-025 — Support sessions (PR-53, TEN-6, TEN-14, TEN-17, TEN-19)

Status: DONE — review APPROVE (codex + claude, round 5) · Risk: R4 (vendor access into tenant data, RLS) · Depends on: T-024, T-003 · Executor: pi (cc/claude-opus-5-5) · Review: claude + codex

## Requirement

- **PR-53:** the vendor operator console opens time-limited, reasoned, tenant-visible support sessions.
  - Scenario: a vendor operator opens a support session for tenant A with a reason; when the session ends after its time limit, tenant A's owner sees the session in the audit log.
- **TEN-6:** vendor operators use a `platform_operator` role and a break-glass grant (reason, TTL ≤ 2 h, tenant-visible audit); no BYPASSRLS.
- **TEN-14:**
  - The scope declares a purpose and object kinds.
  - TTL is at most 2 h, with at most one extension, which needs a new reason.
  - Owner approval is required before a scope includes clinical kinds or specific personal data, and again for a clinical-scope extension. *Approval is T-026; this task makes such a scope stay pending.*
  - Notify-only scopes are limited to configuration, catalog, settings, integration status and money totals.
  - Every record read is audited.
  - Sessions end at TTL or on owner action.
- **TEN-17:**
  - A session binds `app.tenant_id`, `app.operator_session_id` and `app.session_scope`.
  - Every policy kind has an operator predicate (active, unexpired session, kind in scope).
  - Raw-SQL tests per kind cover in-scope, out-of-scope and expired sessions.
- **TEN-19:** operator predicates check approved **object kinds** (tables), not only policy kinds.
- **Done when (TASKS.md):** scenario PR-53 passes; RLS tests for in-scope, out-of-scope and expired sessions pass.
- **Allowed paths:** `src/modules/vendor/support/**`, `src/db/rls/operator.sql`, `drizzle/**`, `tests/vendor/support.test.ts`, `src/db/schema/index.ts`, `src/modules/vendor/schema.ts`.

## Design

1. **Database role `clinic_operator`** (NOLOGIN, no BYPASSRLS, owns nothing).
   - A dedicated login for the support reader joins it, with the same startup safety checks as `clinic_app` (`assertAppRole` with a new group).
   - It gets `SELECT` only on tenant tables that are in scope maps, plus EXECUTE on the operator context functions.
   - It never gets `clinic_app` membership, so no clinic-staff policy applies to it.
2. **`support_sessions`** (platform table): tenant, operator (vendor staff), purpose (10–500 characters), object kinds (table names from `scope_map`), state, opened/ends/ended times, extension, owner-approval reference, end reason.
   - **States:**
     - `pending_approval`: the scope has a clinical table, or a table marked personal.
     - `active`, `ended`.
   - **TTL:** at most 2 h. One extension of at most 2 h with a new reason. An extension of a clinical scope goes back to `pending_approval` (T-026).
   - **Notify-only scope:** only tables whose `scope_map` row marks them as configuration (a new `support_class` column on `scope_map`: `config`, `personal`, `clinical`, `money_total`, `never`).
     - The class for every existing table is set in this migration.
     - Platform tables are `never`.
     - Clinical tables are `clinical`.
     - Identity, contact and consent tables are `personal`.
     - Settings, branches, evidence and templates are `config`.
     - Ledger totals are `money_total` (bounded views later).
   - A test fails when a table has no class.
3. **Operator context:** `support_session_begin(token, ip, session)` on the vendor console role.
   - Validates the vendor session, `vendor_guard` (support, onboarding or platform owner) and the session's state and expiry.
   - Binds `app.tenant_id`, `app.operator_session_id` and `app.session_scope` (the object kinds) transaction-locally.
   - Opened and ended sessions are written to the tenant's audit chain (`operator_session`).
   - Every read audit (TEN-14) goes to `support_session_reads`, written by the support module's read function. Raw RLS reads are bounded by the predicate. The "every record read" listing comes from the module's read path (T-026 shows it; this task records it).
4. **Operator predicates** (`src/db/rls/operator.sql`, applied by the migration; a test keeps the two identical, like `readers.sql`):
   - For each tenant table, a policy `<table>_operator_read FOR SELECT TO clinic_operator` with `USING (tenant_id = app_tenant_id() AND operator_scope_allows('<table>'))`.
   - `operator_scope_allows` checks that the bound `app.operator_session_id` is active, unexpired by `clock_timestamp()` and for this tenant, and that the table is in its scope. It is a SECURITY DEFINER reading `support_sessions`.
   - The generator test asserts one operator policy per table that `scope_map` marks readable by operators (not `never`), and none on platform tables.
5. **PR-53 scenario:** the session opens with a reason and expires by TTL. A sweep (`support_session_expire()`, executor role) ends overdue sessions and writes the end to the tenant chain. Even without the sweep, reads are refused after expiry by the predicate. The owner sees open and end events in Audit (owner and auditor read `audit_events` already).
6. **Console entry points** (clinic_vendor, session token, `vendor_guard`, step-up for writes):
   - `vendor_console_support_open(tenant, purpose, kinds, minutes)`
   - `vendor_console_support_extend(session, reason, minutes)`
   - `vendor_console_support_end(session)`
   - `vendor_console_support_list(tenant)`

   Lock order follows T-024: the session first, then `staff_access` → tenant row → session row → audit.
7. **Owner end:** `support_session_end_by_owner(session)` (clinic_app, Owner). Ends now, audited. The page comes with T-028.

## Design decisions after reading the code (supersede the sketch above where they differ)

- **Classification:** a separate platform table `support_object_kinds(table_name → scope_map, support_class)` instead of a new `scope_map` column, so `src/db/scope-map.ts` stays unchanged. A coverage test fails when any non-platform table has no class.
  - **config** (notify-only, active at once): tenants, branches, setting_versions, approvals, evidence_items.
  - **personal** (owner approval first, T-026): memberships, staff, staff_roles, staff_branches, staff_duties, staff_invitations, membership_revocations, org_actions, role_requests, notifications, evidence_files, evidence_approvals, audit_events.
  - **never** (no operator read at all): idempotency_records, domain_events, event_receipts.
  - **clinical:** none exist yet.
- **Forgery-proof binding.** `set_config` is callable by any role, so the predicate never trusts `app.operator_session_id` alone.
  - `support_session_bind(token, ip, session)` validates the vendor session and guard, the opener, the state and the expiry. It then writes a `support_session_bindings` row (session, `pg_backend_pid()`, `txid_current()`) and sets `app.tenant_id`, `app.operator_session_id` and `app.session_scope`.
  - The predicate `operator_scope_allows(table)` requires a binding row for this backend and this transaction, the session active and unexpired (`clock_timestamp()`), the session's tenant equal to `app_tenant_id()`, and the table in its scope.
  - A forged setting, another tenant's id, a finished transaction or another connection all read nothing.
- **Who reads:** only the operator who opened the session (the binding checks the opener). The database role `clinic_operator` is NOLOGIN, not a member of `clinic_app`, and has SELECT only on tables classed config, personal or money_total, each through a `<table>_operator_read` policy.
- **Pending scope:** a scope with any personal or clinical table is `pending_approval` and cannot bind; T-026 adds the Owner's approval. TTL starts at activation.
- **Read audit** (every record read listed to the Owner) is T-026's job (its title). This task audits open, extend, end, expiry and refused binds.
- **Lock order** follows T-024: session check, then `staff_access` (only for a valid session and an existing tenant), then rows, then audit. The expiry sweep takes tenants in id order.
- **Audit rows** go through `vendor_log`, so to the vendor log and the tenant chain (owner and auditor read them: PR-53 scenario).

## Open points (proceeding with the proposals; owner may override)

- **Q1.** A support session from support or onboarding while the tenant is in `onboarding`: does it need the onboarding grant? Proposed: no, they are independent. The grant covers configuration work; a session is a reasoned, timed look.
- **Q2.** Which vendor roles may open a session? Proposed: support, onboarding and platform owner (19 §3: "Support, onboarding"); platform owner as an exception.
- **Q3.** May a clinical-scope session be requested at all before T-026? Proposed: yes, it stays `pending_approval` and cannot activate until T-026 adds the owner approval.

## As built

- **Migrations:** `0045` creates `support_sessions`, `support_object_kinds` and `support_session_bindings` (all platform tables). `0046` adds the role, the rules and the functions, and ends with `src/db/rls/operator.sql` verbatim (a test compares them).
- **Database role `clinic_operator`:** NOLOGIN, safe attributes, `SELECT` only on the 18 tables whose class is not `never`, each through one `<table>_operator_read` policy; EXECUTE on `support_session_bind` and `operator_scope_allows` only. Startup check: `OPERATOR_GROUP_ROLE` in `src/db/rls/context.ts`.
- **`operator_scope_allows(table)`:** requires all of the following:
  - a binding row for `pg_backend_pid()` and `txid_current_if_assigned()`;
  - the bound session id;
  - the session's tenant equal to `app_tenant_id()`;
  - the table in the session's scope;
  - the session live: active, `ends_at > clock_timestamp()`, tenant not closed;
  - the table's class is not `never`.

  Settings without a bind, a finished transaction or another tenant read nothing.
- **Console:** `vendor_console_support_open`, `_extend`, `_end` and `_list` (clinic_vendor) follow T-024's lock order: session check, then `staff_access` (valid session and existing tenant only), then rows, then audit.
  - Open: a scope with a personal table is `pending_approval` and cannot bind.
  - Extend: once, by the opener, with a new reason; refused for a personal scope.
- **Reads:** `support_session_bind` (clinic_operator) checks the vendor session, the guard (read age), the opener and liveness, then writes the binding and sets `app.*` transaction-locally. A refused bind is logged, and the module commits the refusal so the log row survives.
- **Endings:** `support_session_end_by_owner` (clinic_app, Owner, audited `ended_by_owner`). `support_session_expire` (clinic_executor) ends overdue sessions tenant by tenant under `staff_access`, and prunes bindings older than a day.
- **Module:** `src/modules/vendor/support/support.ts`. `withSupportSession` binds and runs `fn` in one transaction on the operator pool.

## Review round 1 (codex + claude), all fixed

- **HIGH (both reviewers): an open read transaction blocked the Owner.** Bind took `staff_access`, a `FOR SHARE` on the session and (via `vendor_guard`) a `FOR SHARE` on the operator's staff row; the binding row's foreign key held a key share on `vendor_staff`. Now:
  - bind uses `support_read_caller`, which runs the same checks as `vendor_guard` with no row lock;
  - no session row lock is taken;
  - the binding has no foreign key to `vendor_staff`;
  - endings use `FOR NO KEY UPDATE`;
  - bind sets `statement_timeout` 30 s and `idle_in_transaction_session_timeout` 60 s transaction-locally.

  Test: the Owner ends a session while a bound read transaction is open; the end returns at once and the next read in that transaction sees nothing.
- **HIGH (claude): pool safety.** A `SupportBindError` thrown by `fn` skipped the rollback, so a bound connection could go back to the pool. Fixed with a `bound` flag: only a refused bind is committed, everything else rolls back, and a client whose rollback fails is destroyed. Test: a single-connection pool after `fn` throws reads nothing and has no `app.operator_session_id`.
- **HIGH (codex) / MEDIUM (claude): reads were not recorded.** Every operator policy now calls `operator_row_read(table, tenant, id)`. It admits the row only when `operator_scope_allows` the table and the tenant matches, and it records the row in `support_session_reads` (once per session and row, append-only). Any SELECT through `clinic_operator` therefore leaves the list; there is no unaudited path. The successful bind is logged in `vendor_actions` without the tenant audit lock. Test: only returned rows are listed (filtered-out rows are not), each once, and an unbound transaction records nothing.
- **MEDIUM (claude): no re-check of the operator.** The binding stores the vendor login session and the staff id. The predicate requires the login session live (surface vendor, not expired, not locked) and the staff active and the opener. Test: deactivating or signing out the operator mid-transaction stops reads at once.
- **MEDIUM (claude): approvals and setting_versions were config.** Both are now `personal` (reasons, amounts, names), so owner approval comes first.
- **MEDIUM (codex): a pending session could not be ended** (check constraint). The constraint now allows an ended session that was never activated. Test: both the opener and the Owner end a pending session.
- **LOW (claude): closed tenant.** The sweep ends every open session of a closed tenant (`tenant_closed`). Test: reads stop at once when the tenant closes mid-session, and the sweep ends both its sessions.
- **LOW (claude): extension rule for personal scopes.** It is unreachable until T-026 makes a personal scope active. Recorded for T-026's tests.
- **T-026 scope (claude #5):** read recording now lives here, so T-026 adds the Owner approval (activate a pending scope, approve a clinical extension) and the read listing. Recorded in DECISIONS.md that T-026 may add a migration if the approval needs one.

## Review round 2 (codex + claude) — fixed (see "Round 2 fixes as built" below)

Reports: `/data/tmp/rv-T-025/codex-r2.md` and `claude-r2.md`. Round-1 fixes were verified correct by both reviewers: lock conflict with endings, `support_read_caller` parity, pool safety, pending end, closed-tenant sweep. Remaining:

1. **HIGH (both): REPEATABLE READ / SERIALIZABLE bypasses revocation.** A reader in a non-read-committed transaction keeps its snapshot, so an Owner end, a deactivation or a sign-out is not seen.
   - Fix: `support_session_bind` refuses unless `current_setting('transaction_isolation') = 'read committed'`. The level cannot change after the first statement.
   - Test: binding under REPEATABLE READ is refused.
   - Stop describing the timeouts as a guarantee: `SET LOCAL` can override them.
2. **HIGH (codex) / MEDIUM (claude): read records and the bind log row vanish on ROLLBACK** (or rollback to a savepoint).
   - Fix: a two-step bind. A short, committed transaction first issues a bind ticket and writes it to the vendor log and the tenant chain ("bind issued"); the read transaction can bind only with an unused ticket.
   - Individual row records cannot survive a reader's rollback without an autonomous transaction. Record this as accepted residual risk in DECISIONS.md (DEC-038 update) and stop claiming "no unaudited path".
3. **MEDIUM (codex) / LOW (claude): rows recorded but not returned.** Non-leakproof filters, ORDER BY … LIMIT, joins and count(*) record more rows than are returned. This errs on the safe side: document it, and reword the comment and DEC-038 ("rows the operator's queries touched").
4. **LOW (claude): performance.** Write the policies as `USING (tenant_id = public.app_tenant_id() AND public.operator_row_read(...))`, with `id = app_tenant_id()` for `tenants`, so other tenants' rows never reach the plpgsql function.
5. **LOW (claude): forged read records.** The operator can call `operator_row_read` directly and add made-up rows (it cannot hide one). Either T-026's listing joins each record to an existing row, or document it.

After the fixes: rerun the mutations (`/data/tmp/t025-mut.py`, add mutants for 1/2/4), the full suite, and review round 3 by both reviewers.

## Round 2 fixes as built (revised after review round 3)

1. **Isolation.** `support_session_bind` refuses (`isolation_not_read_committed`) unless `transaction_isolation` is `read committed`; the level is fixed by the transaction's first statement. `withSupportSession` opens `begin isolation level read committed` explicitly, so a pool default (`default_transaction_isolation`) cannot break it. The statement and idle caps stay as defaults and are hygiene only (`SET LOCAL` overrides them); revocation does not depend on them.
2. **Durable trace, one per read transaction.** New platform table `support_bind_tickets` (migration 0045). The read transaction opens first and names its `pg_backend_pid()` and `txid_current()`. `vendor_console_support_ticket(token, ip, session, pid, txid)` (clinic_vendor) runs the same checks as the bind (session, guard at read age, opener, live session), requires that txid to be in progress and older than its own, allows one ticket per txid (unique), takes the tenant's `staff_access` lock as a command, inserts the ticket (expires 2 minutes after issue) and writes `support_bind/success/ticket_issued` to the vendor log **and the tenant chain** in its own committed transaction. `support_session_bind(token, ip, session, ticket)` consumes an unused, unexpired ticket for the same session, operator, login session, backend and txid (`no_ticket` otherwise). txids are never reused, so a reader's rollback cannot replay the ticket (review round 3, codex MEDIUM / claude LOW-1): every read transaction has its own committed `ticket_issued` row. A bind rolled back to a savepoint taken before it can bind again only in the same transaction. Bind refusals go to the vendor log only (`tenant_id` null): the tenant chain's lock would otherwise be held by the reader's transaction, and a REPEATABLE READ snapshot predates the chain's tail; the attempt itself is already in the chain as its ticket. Tickets are append-only except the single consumption (trigger).
   - Residual risk (DEC-038): row records (`support_session_reads`) are written in the reader's transaction and vanish on its rollback. The ticket's time is the start of a read window, not its extent: a bound transaction may outlive the ticket's 2 minutes (liveness is still checked on every row).
3. **Over-recording.** Comments, schema docs and DEC-038 say "rows the operator's queries touched" — a superset of the rows returned (non-leakproof filters, sort+LIMIT, joins, aggregates).
4. **Policies** are `USING (tenant_id = app_tenant_id() AND operator_row_read(...))` (`id = …` for `tenants`); a test checks every operator policy's qualifier. The order of evaluation is the planner's (cost-ordered; `operator_row_read` is COST 1000), so this is a performance measure; the function re-checks the tenant.
5. **Forged records.** Documented: a bound operator can call `operator_row_read` directly and add records for made-up ids (never remove one); T-026's listing shows only records that match an existing row.
