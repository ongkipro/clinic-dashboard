## Finding (final, after the implementation reviews)

Tested on Docker Engine 29.9.2, containerd v2.4.2, runc 1.5.2, docker-init 0.19.0, Compose v5.6.1, kernel
7.0.0-42, image postgres:16.15-bookworm (dash 0.5.12-2).

- **Mechanism, reproduced deterministically** (`/data/tmp/hyg005/orphan-regression.sh`): when the
  postmaster is PID 1, any orphan it adopts that exits with a status other than 0/1 makes PostgreSQL 16
  log `server process (PID n) exited with exit code <status>` (2 for the injected orphan) and
  crash-recover the whole cluster. With Docker's
  init (or tini) as PID 1, the same orphan causes nothing.
- **The healthcheck produces such orphans, reproduced** (`/data/tmp/hyg005/probe-timeout.sh`; final
  script run recorded in the delivery ledger, evidence `/data/tmp/hyg005/probe-1793791526/` (stimulus
  counted only inside the verified freeze window, window bounds kept in `*-window.txt`); earlier runs
  with the same chain: `probe-1793789199/`, `probe-1793789372/`, `probe-1793789715/`, `probe-1793790633/`,
  `probe-1793790976/`). On a disposable
  instance with the old configuration (`CMD-SHELL pg_isready …`, no init) the postmaster (PID 1) was frozen
  from the host (`docker kill -s SIGSTOP`; state `T` checked). Probes timed out (`Health check exceeded
  timeout (3s)`); each probe's `sh` disappeared and its `pg_isready` was re-parented to the postmaster
  (PPid 1) and exited **during the freeze**, left as a zombie (state `Z`). After the resume the postmaster
  reaped it, saw exit status 2 and logged it as a crashed server process — in the final run `server
  process (PID 235) exited with exit code 2` for the adopted `pg_isready` 235 — then `terminating any other active server
  processes` → `reinitializing`. On the fixed configuration (init, exec-form probe with `-t 2`) the same
  freeze gave `no response` (exit 2) probes, each `pg_isready` the exec's own process (PPid 0) ending by
  itself; no orphan appeared and no crash/recovery line. The fixed case changes init, exec form and `-t 2`
  together; init alone (the CI configuration keeps a shell-form probe) is covered by the deterministic
  orphan test, not by this freeze test.
- **The two incidents on 2026-11-04** (08:49:15Z and 09:30:19Z, during full suites at host load 6–18)
  have exactly this signature — as would any adopted orphan exiting 2. Their own probe log is gone (Docker keeps only the last five results), so
  each incident is attributed by signature, not by a record of that probe. No other cause was found
  (no OOM, PANIC, signal sender or on-disk corruption).
- **All probe-timeout runs** (`/data/tmp/hyg005/probe-<run>/`; `*.log` files are git-ignored in the
  repository but kept there):
  - first runs, before evidence directories existed: reported "not reproduced" — invalid, because they
    signalled the postmaster from inside the container and a signal to the namespace's PID 1 is dropped,
    so the old configuration was never frozen (claude review, round 2);
  - `probe-1793789081/`: crash-recovery in the old configuration (`server process (PID 109) exited with
    exit code 2` → `reinitializing`), but the Health log was read only after the resume (only exit-0
    entries kept) and the ancestry sampler collected nothing (`docker exec` without `-i`), so the orphan's
    source is unrecorded. This run's freeze method and its outcome were not recorded (no `result.txt`, no
    ledger entry); it is listed for completeness only;
  - `probe-1793789199/` (PID 243) and `probe-1793789274/` (PID 167): the full chain on the old
    configuration, script aborted afterwards on its own `grep` under `pipefail`;
  - `probe-1793789372/`, `probe-1793789715/`, `probe-1793790633/`: full chain, completed;
  - `probe-1793790548/`, `probe-1793790591/`: baseline chain (PID 235 each), script aborted in its
    Health-check helper (`read < <(...)` on output without a newline);
  - `probe-1793790976/`: stimulus counted only inside the verified freeze window; same result;
  - `probe-1793791526/`: final script (window bounds also saved), recorded in the delivery ledger (`.delivery/runs/RUN-20261104T101034Z-6a1e319f.jsonl` in the
    repository): baseline 3 timeouts in the window, 3 adopted `pg_isready`, crash PID 235; fixed 4 failed
    probes in the window, no orphan, no crash line.
- **Also exposed** (same mechanism, other orphan sources): the pgBackRest image in production, the restore
  drill and restored instances (async `archive-push`/`archive-get` workers detach and are adopted by
  PID 1), and any `docker exec … psql/pg_isready` that outlives its parent. CI's service container has the
  same healthcheck and no init.

## Change (R3: CI and production image; no product code)
1. `compose.yaml`: `init: true` and `stop_grace_period: 60s` on `postgres` (the plain official image, used
   locally); healthcheck in exec form with a
   probe timeout below Docker's: `["CMD", "pg_isready", "-U", "clinic", "-d", "clinic_dashboard", "-t", "2"]`
   (interval 2 s, timeout 3 s, retries 30 unchanged).
2. `.github/workflows/ci.yml` service options: add `--init`; health-cmd `pg_isready -U clinic -d clinic_dashboard -t 2`
   (GitHub runs `--health-cmd` through `sh -c`, so `--init` is the protection there).
3. **Production image (claude root-cause review, HIGH):** `ops/pgbackrest/Dockerfile` installs `tini`
   (Debian bookworm package, pinned `0.19.0-1+b3`, from the same apt run as pgBackRest) and uses
   `ENTRYPOINT ["/usr/bin/tini", "--", "/usr/local/bin/entrypoint-pgbackrest.sh"]`, so every runtime of
   the production database image (Coolify, the drill, the local `postgres-backup` profile) has an init
   as PID 1 regardless of `init:`/`--init` support. The local `postgres-backup` service then does
   **not** also get `init: true` (two nested inits are avoided). `ops/pgbackrest/restore-drill.sh`
   needs no `--init` once the image has tini (the drill builds that image); its destination container
   overrides the entrypoint with `bash -c 'sleep infinity'` (PID 1 = `sleep`, postgres started by
   `docker exec`), so postgres adopts no orphans there. Restores also use `archive-get`, which is
   asynchronous under `archive-async=y`: tini in the image covers restored instances (staging, PITR)
   the same way.
   Verification on a disposable container from the rebuilt image (`/data/tmp/hyg005/image-tini.sh`):
   build check (Entrypoint = tini …, StopSignal SIGINT, `dpkg-query` tini = 0.19.0-1+b3); `/proc/1/comm` =
   `tini`; the postmaster's PPid = 1; an orphan that exits 2 (adoption by PID 1 checked) leaves no
   crash/recovery line. Not done: capturing an async pgBackRest worker's parent during an archive push —
   the test runs with archiving off (no repository); the orphan test covers the same mechanism.
4. Carried-forward items in STATUS for the deploy task: verify on the deployed Coolify container that
   PID 1 is tini (the image provides it; a platform init on top is harmless but unnecessary); the
   database healthcheck, if any, uses `pg_isready -t` below its timeout; the stop grace period is
   long enough for the archiver to push the last WAL (Docker's default 10 s can force crash recovery);
   restores run through the image entrypoint, or else postgres must not be PID 1 (DR runbook note).
   `compose.yaml` `postgres-backup` gets `stop_grace_period: 60s` and a comment that the image provides
   tini (no `init: true`).
5. Docs: docs/tasks/HYG-005.md, BUILD-LOG gotcha, STATUS row.

## Rollout and acceptance
1. Before: no test running; the dump and globals were written by commands that exited 0 (16:59,
   before any change; no task wrote to clinic_dashboard since) and are readable (`pg_restore --list`).
   This checks the archive, not a full restore (accepted for a configuration change). Record the
   volume name (`clinic-dashboard_pgdata`), table count and `pg_postmaster_start_time()`.
2. Stop the old container first with a 60 s grace and keep its shutdown log
   (`docker compose stop --timeout 60 postgres`; `docker logs --since <stop time>` must show
   `database system is shut down`), then recreate only `postgres` with the same project/files:
   `docker compose up -d --no-deps --wait postgres` (never `down -v`). Check the published port is
   unchanged (`docker port` = `127.0.0.1:5432`). After: `HostConfig.Init=true`, PID 1 = `/sbin/docker-init`, postgres its child,
   same volume mounted, `clinic_dashboard` present with the same table count.
3. Deterministic regression on isolated Compose projects (`hyg005base<run>`/`hyg005fixed<run>`, disposable volumes,
   `POSTGRES_PORT=55499` so the published port cannot collide with the retained database) using this
   service definition: orphan that exits 2 (its adoption by PID 1 checked) → no crash/recovery line; the
   same orphan on a copy without `init` → crash/recovery lines (baseline). The postmaster's start time is
   informational only: crash recovery restarts the children, not the postmaster, so it stays the same
   after a crash too (the baseline shows it); the log lines decide.
   Removed with `down -v` on that project only. Never crash the retained local database on purpose.
4. Healthcheck-specific check (disposable instances only, cleanup in a trap): freeze the postmaster from
   the host (`docker kill -s SIGSTOP`; a signal from inside the namespace to its PID 1 is dropped), check
   state `T`, sample process ancestry and the Health log during the freeze, resume, and compare the old
   configuration with the fixed one. Both cases must record a failed or timed-out probe whose start lies
   inside their verified freeze window; otherwise the run is INCONCLUSIVE (exit 2).
5. Full suite ×3 under the host rule (load ≤ 4, no other suite), output kept (`/data/tmp/hyg005/suite-watch.sh`);
   acceptance = no crash/recovery line in the container log for the whole window, the postmaster not
   restarted (start time equal: a postmaster-restart check, not a crash-recovery check), all three suites
   pass, and both observers ran the whole time. This shows no regression at load ≤ 4; it does not recreate
   the incidents' load (6–18). The proof that the fix works is steps 3 and 4.
6. Restore drill (RUN_BACKUP_DRILL=1) passes with the rebuilt image (no regression; the protection itself
   is shown by the deterministic test in change item 3).
6b. During the three suites, poll the Health log every 2 s (de-duplicated by start time; Docker keeps only
   five; largest gap between probes ≤ 12 s) and sample process ancestry every 2 s from the host
   (`docker top`, no exec into the database container; best effort: an orphan reaped by init at once is
   rarely caught). Each sample records success or failure; any observer failure fails the run. Probe timeouts and non-postgres children of init are reported; if no timeout occurs, the
   result says "no probe timeout observed", not that timeouts are harmless.
7. CI: on the next push, the run must be green and its "Initialize containers" log must show `--init`
   in the `docker create` line.
