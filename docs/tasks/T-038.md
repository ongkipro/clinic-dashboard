## Design (proposed)

**Data** (migration 0059):
- `consent_texts`: tenant, purpose (`care_notice`, `procedure`, `clinical_photo`, `marketing_wa`, `publication`), version (gap-free per tenant × purpose, from 1), body (1–8000 chars), `effective_from` (≥ now at publish, never backdated), `created_by`, `created_at`. Insert-only: a change is a new version (stricter than DATA-66 "immutable once referenced", and simpler to prove). The text in force for a purpose is the highest version whose `effective_from` ≤ now.
- `consents`: tenant, patient (composite FK), purpose, `consent_text_id` (composite FK; its purpose must match), `granted_at`, `granted_by` (staff), `grant_channel` (`in_person`, `paper`, `whatsapp`, `phone`), and the withdrawal fields `withdrawn_at`, `withdrawn_by`, `withdraw_channel`, `withdraw_reason` (all null, or all set together). One active (not withdrawn) consent per patient × purpose (partial unique index). A grant after a withdrawal is a new row, so the history is the rows.
- Guards: `consent_texts` never updated or deleted; `consents` never deleted, and the only update sets the withdrawal fields once (null → value), never on `care_notice`.
- RLS: `consents` read by the 13 non-marketing identity roles (as `patients`); `consent_texts` by every member. `scope_map` rows (tenant-shared). Support classes: `consents` `personal`, `consent_texts` `config`, each with a `clinic_operator` policy (TEN-19).

**Writes** (SECURITY DEFINER under `tenant_actor_lock`, audited `settings_change`, events with ids only):
- `consent_text_publish(purpose, body, effective_from)`: the Owner, or Admin Pusat holding an active `data_protection` duty (SET-45, IAM-13). Returns the new version.
- `consent_grant(patient, purpose, text_id, channel)`: the text must be the one in force for that purpose now (what was shown is what is recorded; otherwise `consent_text_changed`). `procedure` is refused here: procedure consent is captured per plan items and doses by UX-39 (T-054, `procedure_consents`). An active consent for the same purpose is `already_granted`.
- `consent_withdraw(consent, channel, reason)`: sets the withdrawal fields; `care_notice` is `not_withdrawable` (PRIV-1); an already withdrawn consent is `already_withdrawn`.
- Who records grants and withdrawals: the front-desk and patient-facing roles that already handle identity (fo_cashier, central_cs, bc, records_officer, manager).
- The TS module runs grant and withdraw through `runCommand` with the caller's idempotency key (DATA-45).

**Readers:**
- `patient_consents(patient)`: the ledger rows of one patient with the text version, for the identity readers (T-040 shows them).
- `consent_active(patient, purpose)`: boolean, for the outbound task (scenario PR-4 second half) and later gates.
- `marketing_contacts()`: Marketing only (TEN-18): id, name and primary phone of the tenant's patients with an active `marketing_wa` consent, nothing else. Replaces a security-barrier view: a definer function with a role check is simpler to prove than view ownership plus RLS.

## Open points for the plan review

1. **Insert-only texts.** DATA-66 says "immutable once any consent references it", which allows editing an unreferenced draft. Proposal: always insert-only (a typo fix is a new version). Drafts are a T-039 UI concern.
2. **`procedure` in the ledger.** Kept in the purpose list (DATA-14, PD-01) but refused by `consent_grant`, so procedure consent has one owner (T-054, UX-39). Alternative: accept it now as a general procedure acknowledgement.
3. **Recorder roles.** fo_cashier, central_cs, bc, records_officer, manager. Should the doctor record clinical-photo consent too (it is often taken in the treatment room)?
4. **Lifecycle.** Grants need `tenant_capability('existing_appointment')` (live and suspended); a withdrawal is accepted in every state the app can act in (withdrawal must never be blocked, PRIV-1).
5. **No seeded texts.** A tenant cannot record a consent until the Owner publishes a text per purpose (T-039 gives the editor; SET-45 default "vendor templates" is applied at onboarding later). The UX-4 consent section stays a placeholder until then.

## Plan review round 1 (Argon; GPT-6.1 Sol 429): REVISE PLAN → adopted

Open points:
1. **Insert-only texts:** accepted (stricter than DATA-66; the text in force is the highest version with `effective_from` ≤ `clock_timestamp()`).
2. **`procedure`:** accepted. It stays in the purpose list and texts can be published for it, but `consents` has `CHECK (purpose <> 'procedure')` and `consent_grant` refuses it; T-054 (UX-39, `procedure_consents`) owns procedure consent.
3. **Recorders:** fo_cashier, central_cs, bc, doctor, records_officer, manager (the doctor takes clinical-photo and publication consent in the room; 07 "Patient identity" ●).
4. **Lifecycle:** grant needs `tenant_capability('existing_appointment')` (live, suspended) and the TS wrapper calls `assertProductionGoLive` (ARCH-10, as T-037); withdrawal is never blocked by lifecycle; publish needs `configuration` or `existing_appointment` (onboarding, live, suspended).
5. **No seeded texts:** accepted.

Findings adopted:
- **P1-1 events** (ids and lower-case codes only, `events_payload_ok`): `ConsentTextPublished` (`consent_text_id`, `purpose`); `ConsentRecorded` (18:162) for a grant (`consent_id`, `patient_id`, `consent_text_id`, `purpose`, `change`='granted') and for a withdrawal (`change`='withdrawn'). No version numbers or reasons in payloads; `branch_id` column from the actor (null allowed there, not in the payload).
- **P1-2 tenant and purpose binding:** `consent_texts` has `UNIQUE (tenant_id, id)`, `UNIQUE (tenant_id, id, purpose)`, `UNIQUE (tenant_id, purpose, version)`; `consents` references `(tenant_id, consent_text_id, purpose)`. `consent_grant` checks the patient and the text exist in the caller's tenant for that purpose (`ERR_NOT_FOUND`) before comparing with the text in force (`consent_text_changed`), so another tenant's id leaks nothing.
- **P1-3 readers:** `marketing_contacts()` and `patient_consents(patient)` validate the caller with `approval_actor()` (wall-clock membership and role); marketing only for the first, the 13 identity roles for the second (an unknown or foreign patient: `ERR_NOT_FOUND`). `consent_active(patient, purpose)` accepts a valid staff context (identity roles or marketing) or a tenant-bound service context (tenant set, no staff: the outbox worker), and returns false for unknown or foreign patients and unknown purposes. The definer function in place of the TEN-18 security-barrier view is a recorded deviation (DEC-052): `clinic_app` views must be `security_invoker` (RLS test), and an invoker view cannot read `patients` for marketing.
- **P2-1 outcomes:** `consent_grant` and `consent_withdraw` return jsonb `{ok:true, consent_id}` or `{ok:false, code}` (`consent_text_changed`, `already_granted`, `not_withdrawable`, `already_withdrawn`), so `runCommand` stores and replays both under the caller's key; forbidden, not-found, invalid input and suspended tenants raise and roll back the claim.
- **P2-2 wall clock and guards:** publish refuses `effective_from` earlier than `clock_timestamp() - 1 minute` or later than +366 days and stores `greatest(effective_from, clock_timestamp())`; the in-force test uses `clock_timestamp()`. `consent_texts_guard` refuses every update and delete; `consents_guard` refuses delete, an insert with withdrawal fields or `procedure`, and any update other than setting all withdrawal fields once (not on `care_notice`, not before `granted_at`). Both `ENABLE ALWAYS` with `BEFORE TRUNCATE`.
- **P2-3 scope expansions:** `tests/rls/rls.test.ts`, `tests/rls/authority-clock.test.ts` (including an Admin Pusat whose duty ends after the transaction starts), `tests/patients/consents-drift.test.ts`, and the TEN-19 / vendor gate files if they need a row.
- **P3-1 attribution:** `consent_texts.created_as` (owner, admin_pusat); `consents.granted_as` and `withdrawn_as` from the acting role. Audit `settings_change` with object kinds `consent_text` / `consent` and reason codes `consent_text_published`, `consent_granted`, `consent_withdrawn`.

## Plan review round 2 (Argon): APPROVE PLAN

All round-1 points adopted. One implementation note, adopted: `consent_active` treats a context as a service context only when neither `app.staff_id` nor `app.roles` is set; anything else goes through `approval_actor()`.
