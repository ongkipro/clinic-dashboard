# T-025 — Support sessions (PR-53, TEN-6, TEN-14, TEN-17, TEN-19)

Status: Planned · Risk: R4 (vendor access into tenant data, RLS) · Depends on: T-024, T-003 · Executor: pi (cc/claude-opus-5-5) · Review: claude + codex

## Requirement

- **PR-53:** the vendor operator console opens time-limited, reasoned, tenant-visible support sessions.
  - Scenario: a vendor operator opens a support session for tenant A with a reason; when the session ends after its time limit, tenant A's owner sees the session in the audit log.
- **TEN-6:** vendor operators use a `platform_operator` role and a break-glass grant (reason, TTL ≤ 2 h, tenant-visible audit); no BYPASSRLS.
- **TEN-14:**
  - The scope declares a purpose and object kinds.
  - TTL is at most 2 h, with at most one extension, which needs a new reason.
  - Owner approval is required before a scope includes clinical kinds or specific personal data, and again for a clinical-scope extension. *Approval is T-026; this task makes such a scope stay pending.*
  - Notify-only scopes are limited to configuration, catalog, settings, integration status and money totals.
  - Every record read is audited.
  - Sessions end at TTL or on owner action.
- **TEN-17:**
  - A session binds `app.tenant_id`, `app.operator_session_id` and `app.session_scope`.
  - Every policy kind has an operator predicate (active, unexpired session, kind in scope).
  - Raw-SQL tests per kind cover in-scope, out-of-scope and expired sessions.
- **TEN-19:** operator predicates check approved **object kinds** (tables), not only policy kinds.
- **Done when (TASKS.md):** scenario PR-53 passes; RLS tests for in-scope, out-of-scope and expired sessions pass.
- **Allowed paths:** `src/modules/vendor/support/**`, `src/db/rls/operator.sql`, `drizzle/**`, `tests/vendor/support.test.ts`, `src/db/schema/index.ts`, `src/modules/vendor/schema.ts`.

## Design

1. **Database role `clinic_operator`** (NOLOGIN, no BYPASSRLS, owns nothing).
   - A dedicated login for the support reader joins it, with the same startup safety checks as `clinic_app` (`assertAppRole` with a new group).
   - It gets `SELECT` only on tenant tables that are in scope maps, plus EXECUTE on the operator context functions.
   - It never gets `clinic_app` membership, so no clinic-staff policy applies to it.
2. **`support_sessions`** (platform table): tenant, operator (vendor staff), purpose (10–500 characters), object kinds (table names from `scope_map`), state, opened/ends/ended times, extension, owner-approval reference, end reason.
   - **States:**
     - `pending_approval`: the scope has a clinical table, or a table marked personal.
     - `active`, `ended`.
   - **TTL:** at most 2 h. One extension of at most 2 h with a new reason. An extension of a clinical scope goes back to `pending_approval` (T-026).
   - **Notify-only scope:** only tables whose `scope_map` row marks them as configuration (a new `support_class` column on `scope_map`: `config`, `personal`, `clinical`, `money_total`, `never`).
     - The class for every existing table is set in this migration.
     - Platform tables are `never`.
     - Clinical tables are `clinical`.
     - Identity, contact and consent tables are `personal`.
     - Settings, branches, evidence and templates are `config`.
     - Ledger totals are `money_total` (bounded views later).
   - A test fails when a table has no class.
3. **Operator context:** `support_session_begin(token, ip, session)` on the vendor console role.
   - Validates the vendor session, `vendor_guard` (support, onboarding or platform owner) and the session's state and expiry.
   - Binds `app.tenant_id`, `app.operator_session_id` and `app.session_scope` (the object kinds) transaction-locally.
   - Opened and ended sessions are written to the tenant's audit chain (`operator_session`).
   - Every read audit (TEN-14) goes to `support_session_reads`, written by the support module's read function. Raw RLS reads are bounded by the predicate. The "every record read" listing comes from the module's read path (T-026 shows it; this task records it).
4. **Operator predicates** (`src/db/rls/operator.sql`, applied by the migration; a test keeps the two identical, like `readers.sql`):
   - For each tenant table, a policy `<table>_operator_read FOR SELECT TO clinic_operator` with `USING (tenant_id = app_tenant_id() AND operator_scope_allows('<table>'))`.
   - `operator_scope_allows` checks that the bound `app.operator_session_id` is active, unexpired by `clock_timestamp()` and for this tenant, and that the table is in its scope. It is a SECURITY DEFINER reading `support_sessions`.
   - The generator test asserts one operator policy per table that `scope_map` marks readable by operators (not `never`), and none on platform tables.
5. **PR-53 scenario:** the session opens with a reason and expires by TTL. A sweep (`support_session_expire()`, executor role) ends overdue sessions and writes the end to the tenant chain. Even without the sweep, reads are refused after expiry by the predicate. The owner sees open and end events in Audit (owner and auditor read `audit_events` already).
6. **Console entry points** (clinic_vendor, session token, `vendor_guard`, step-up for writes):
   - `vendor_console_support_open(tenant, purpose, kinds, minutes)`
   - `vendor_console_support_extend(session, reason, minutes)`
   - `vendor_console_support_end(session)`
   - `vendor_console_support_list(tenant)`

   Lock order follows T-024: the session first, then `staff_access` → tenant row → session row → audit.
7. **Owner end:** `support_session_end_by_owner(session)` (clinic_app, Owner). Ends now, audited. The page comes with T-028.

## Design decisions after reading the code (supersede the sketch above where they differ)

- **Classification:** a separate platform table `support_object_kinds(table_name → scope_map, support_class)` instead of a new `scope_map` column, so `src/db/scope-map.ts` stays unchanged. A coverage test fails when any non-platform table has no class.
  - **config** (notify-only, active at once): tenants, branches, setting_versions, approvals, evidence_items.
  - **personal** (owner approval first, T-026): memberships, staff, staff_roles, staff_branches, staff_duties, staff_invitations, membership_revocations, org_actions, role_requests, notifications, evidence_files, evidence_approvals, audit_events.
  - **never** (no operator read at all): idempotency_records, domain_events, event_receipts.
  - **clinical:** none exist yet.
- **Forgery-proof binding.** `set_config` is callable by any role, so the predicate never trusts `app.operator_session_id` alone.
  - `support_session_bind(token, ip, session)` validates the vendor session and guard, the opener, the state and the expiry. It then writes a `support_session_bindings` row (session, `pg_backend_pid()`, `txid_current()`) and sets `app.tenant_id`, `app.operator_session_id` and `app.session_scope`.
  - The predicate `operator_scope_allows(table)` requires a binding row for this backend and this transaction, the session active and unexpired (`clock_timestamp()`), the session's tenant equal to `app_tenant_id()`, and the table in its scope.
  - A forged setting, another tenant's id, a finished transaction or another connection all read nothing.
- **Who reads:** only the operator who opened the session (the binding checks the opener). The database role `clinic_operator` is NOLOGIN, not a member of `clinic_app`, and has SELECT only on tables classed config, personal or money_total, each through a `<table>_operator_read` policy.
- **Pending scope:** a scope with any personal or clinical table is `pending_approval` and cannot bind; T-026 adds the Owner's approval. TTL starts at activation.
- **Read audit** (every record read listed to the Owner) is T-026's job (its title). This task audits open, extend, end, expiry and refused binds.
- **Lock order** follows T-024: session check, then `staff_access` (only for a valid session and an existing tenant), then rows, then audit. The expiry sweep takes tenants in id order.
- **Audit rows** go through `vendor_log`, so to the vendor log and the tenant chain (owner and auditor read them: PR-53 scenario).

## Open points (proceeding with the proposals; owner may override)

- **Q1.** A support session from support or onboarding while the tenant is in `onboarding`: does it need the onboarding grant? Proposed: no, they are independent. The grant covers configuration work; a session is a reasoned, timed look.
- **Q2.** Which vendor roles may open a session? Proposed: support, onboarding and platform owner (19 §3: "Support, onboarding"); platform owner as an exception.
- **Q3.** May a clinical-scope session be requested at all before T-026? Proposed: yes, it stays `pending_approval` and cannot activate until T-026 adds the owner approval.

## Acceptance (runnable)

`tests/vendor/support.test.ts`:
- **Scenario PR-53.**
- **Per policy kind** (tenant-shared, branch-scoped, tenant-ledger, clinical), raw SQL as `clinic_operator`:
  - in-scope rows are visible;
  - out-of-scope tables return 0 rows;
  - another tenant's rows return 0;
  - an expired session returns 0;
  - an ended session returns 0;
  - with no session bound, the result is 0.
- **Scope rules:**
  - TTL above 2 h is refused;
  - a second extension is refused;
  - an extension needs a new reason;
  - a clinical or personal kind leaves the session `pending_approval` (not readable);
  - unknown or platform tables are refused.
- **Roles:** only support, onboarding and platform owner may open; the step-up applies; every refusal is logged.
- **Owner:** the owner ends a session; it stops at once; the end is audited.
- **Privileges:**
  - `clinic_operator` cannot write anything or read platform tables;
  - `clinic_app` cannot bind an operator session;
  - `clinic_vendor` reads no tenant table.
- **Coverage:** every tenant table has a `support_class` and an operator policy (generator test); `operator.sql` equals its migration.
