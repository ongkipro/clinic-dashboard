## Problem (evidence)

1. **Vial flake** (`tests/inventory/items.test.ts:202`, seen in T-074 close runs 1 and 2).
   - `stock_vial_open_do` (latest `drizzle/0078_depots.sql:955`) inserts `use_by = clock_timestamp() + hours`, while `opened_at` takes its column default `clock_timestamp()`. That default is evaluated separately: two reads, microseconds apart.
   - So `use_by - opened_at` is 24 h plus a few µs, and the exact `[30, 24]` assertion sometimes fails.
2. **Media-token flake** (`tests/clinical/media.test.ts:212`).
   - `media_token_issue` (`drizzle/0072_media.sql:353`) sets `issued_at = clock_timestamp()` and `expires_at = clock_timestamp() + ttl`: two reads.
   - At ttl 600 s, `expires_at - issued_at` can exceed 10 minutes by µs. `media_tokens_check` (`expires_at <= issued_at + 10 min`) then rejects a legal 600 s token, and the test fails.
   - This is a product bug, not only a test flake: a real 600 s request can fail the same way.
3. **Setup-hook limit.**
   - `vitest.config.mts` sets `hookTimeout: 120_000`. 66 test files already give their `beforeAll` an explicit 300 s; the rest rely on the 120 s default.
   - The T-076 close runs 3–8 failed only in such files (catalog/prices, vendor/staff, rls/readers, auth/second-factor, …), all at "Hook timed out in 120000ms", with I/O pressure "full" at 30–75 % from other projects. No assertion failed.

## Change

1. **Migration `0092_one_clock`.** Re-create both functions from their latest migrations, each with one `v_now timestamptz := clock_timestamp()` per call.
   - `stock_vial_open_do`: insert `opened_at = v_now` and `use_by = v_now + make_interval(hours => …)`.
   - `media_token_issue`: `issued_at = v_now` and `expires_at = v_now + make_interval(secs => p_ttl_seconds)`.
   - Everything else is byte-identical: attributes, grants, `REVOKE`.
   - Drift test `tests/db/one-clock-drift.test.ts` with `.expected.json`.
   - No schema change; the Drizzle snapshot is generated as a custom migration.
2. **`vitest.config.mts`.** Set `hookTimeout` to `300_000`, and update the comment block with the measured evidence. `testTimeout` stays 30 s.
   - Tests whose timing is the point keep their explicit limits. The harness-lock 120 s *test* limits are not touched: they are test bodies, and one timed out in T-076 close run 7 under load, which is the same contention.
   - Raising them is out of scope; it is noted as an open point.
3. **Tests.**
   - Vial: assert `use_by - opened_at = interval '24 hours'` exactly, opening vials in a loop of 20 (open, then lapse and reopen, as the test already does) to make a two-read regression visible.
   - Media: issue 20 tokens at ttl 600 and assert `expires_at - issued_at = interval '600 seconds'` exactly; each must succeed.
   - Both go in the existing files as the smallest additions.

## Close run 3 diagnosis (supervisor 16:20Z: contention not yet proven) and the harness-lock fix

**harness-lock timeouts (`tests/rls/harness-lock.test.ts:135, 183, 225`; earlier also 119, 150, 252, 512, 531).**

- **Cause:** a queue, not a slow disk. Each of these tests calls `createHarness`, which takes the cluster-wide `MIGRATE_LOCK_KEY` (`tests/rls/harness.ts:290`, T-060) and runs all 93 migrations. In the full suite the key is queued behind every other file's migration, and that wait is spent inside the test's own 120 s budget. The harness's `lock_wait` reports only the DDL key, so it showed 0 while the setups took minutes.
- **Proof** (`/data/tmp/clinic-dashboard/hyg016/diag-1794587020`). The run was taken on an idle host: pool 0/2, no Gerai or 99ribu job, I/O full 0 %. A sampler recorded who held and who awaited the migrate and DDL keys every second.
  - Phase A, harness-lock alone: 22/22, 58.7 s.
  - Phase B, beside five migrating files: 80/80, 108 s. Up to 5 harnesses waited on the migrate key at once; one waited 38 s. Each migration held the key 3–12 s.
  - Test 2 went from 11.7 s to 39.2 s and test 1 from 8.2 s to 26.5 s. In a 157-file suite the same queue passes 120 s.
- **Fix (test file only; no limit raised, harness unchanged):**
  - The DDL-lock tests (1, 2, 4, 7, 8b, 13, 14) pass a private `migrateLockKey: freshKey()`. Except where their own migrate step is the point, they use `migrate: async () => {}`.
  - Test 4 keeps its barrier step; 7 and 8b keep their failing step.
  - Test 15 still covers the real migrate key, as does every other file.
- **After the fix** (`diag-1794587361`; the 99ribu suite was running in the other slot):
  - Phase A: 22/22 in 18.5 s.
  - Phase B: 80/80 in 65.9 s. Test 2 took 3.7 s (was 39.2 s), test 1 5.5 s (26.5 s), test 13 4.4 s, test 14 3.9 s.
- **Scope expansion:** `tests/rls/harness-lock.test.ts`.

**rls `tests/db/service-drift.test.ts:64` (55P03).** The PostgreSQL log of the run shows the cause:

- At 15:19:41.298 `CREATE TABLE "staff_roles"` (migration 0006, in a fresh harness database) hit the runner's 5 s `lock_timeout`.
- At 15:19:41.708 an autovacuum of `rls_ba714a534c53.pg_catalog.pg_shdepend` was cancelled "while truncating relation". `pg_shdepend` is a shared catalog that every database's CREATE TABLE writes owner dependencies to. Vacuum truncation holds an AccessExclusive lock on it.
- Meanwhile a forced checkpoint (DROP DATABASE) ran from 15:19:30.6 to 15:19:43.2 and took 12.6 s, which made the truncation slow.

This is a cluster-catalog race between the test suite's database churn and autovacuum. It is not this task's code, and it occurred once in four runs. It is not fixed here: the 5 s runner limit is also production's (`src/db/migrate.ts`), and autovacuum settings of the test container are container configuration, left for the owner with fsync.

## Close run 4 (00:10 WIB on an idle host): every check PASS except test-full, one real failure (kept in the ledger)

- **Result:** rls PASS with the harness-lock fix. test-full: 2001 passed, 1 failed — `tests/packages/packages.test.ts` scenario 16 with `ERR_VERSION_CONFLICT` from `setTaxProfile` (`becomePkp`, line 539), at 00:18–00:31 WIB.
- **Cause: a date-zone bug in the test (T-076), not a timeout.**
  - `becomePkp` set PKP from `day(1)`, which is tomorrow in UTC. Between 00:00 and 07:00 WIB that is today's date in WIB.
  - Scenario 16 issues an invoice before turning PKP, so `tax_profile_set` (0086) refused an effective date not after the latest issued invoice's date (`v_from <= v_latest`). The run crossed WIB midnight.
  - Reproduced at 00:32 WIB (`repro-pkp.sh`: fails), and green after the fix at 00:33 WIB.
- **Fix:** `tomorrowWib()` (tomorrow in Asia/Jakarta); the unused `day` helper removed.
  - `tests/cashier/kasir.test.ts:260` and `tests/balance/balance.test.ts:315` use the same `day(1)`, but they turn PKP before issuing any invoice, so `v_latest` is null and they passed. They are left as they are and noted for a later hygiene task.
