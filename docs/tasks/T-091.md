## 3. Design
- **Link**: `complaint_tasks.message_id uuid NULL` + composite FK (tenant_id, message_id) → messages(tenant_id, id) ON DELETE RESTRICT; CHECK
  `(source = 'message') = (message_id IS NOT NULL)`. The existing CHECK `complaint_tasks_source_check` is NOT altered (it already allows
  'message'); the new CHECK is added alongside. One open task per message (partial unique (tenant_id, message_id) WHERE state <> 'resolved')
  so a double click or a second CS cannot flag the same message twice.
- **No duplicated rules**: `complaint_flag` is not re-created (drift CHANGED = []). Its body holds the triage/category/branch/notification
  rules. To reuse them without copying, the plan proposes ONE of (reviewer to choose):
  (a) a new internal (not granted) primitive `complaint_flag_core(a record, p_patient, p jsonb, p_source text, p_message uuid)` holding the
      insert/event/audit/notification block, and `complaint_flag_from_message` calling it — while `complaint_flag` keeps its own copy until a
      later task migrates it (some duplication remains in 0074);
  (b) `complaint_flag_from_message` sets a transaction-local marker (`set_config('app.complaint_message', <id>, true)`) and calls
      `complaint_flag` with source 'staff_flag'… — rejected: the source would be wrong and the 0074 refusal stays.
  (c) re-create `complaint_flag` once, accepting source 'message' only through the new wrapper (an internal argument), drift CHANGED =
      [complaint_flag] with its byte diff reviewed — removes the refusal at its origin, no duplicated rules. Recommended if the reviewer accepts
      a reviewed re-creation; otherwise (a).
- **The wrapper** `complaint_flag_from_message(p_key text, p_message uuid, p jsonb)` (SECURITY DEFINER, grant clinic_app):
  `complaint_actor()` first (the flaggers of DEC-066; marketing/auditor/admin_pusat refused); the message must be the caller's tenant's,
  inbound, in a conversation the caller can read (`inbox_readable`), routed to a branch (an unrouted brand-wide conversation → `ERR_VERSION_CONFLICT:
  route_first`), and matched to a patient (`patient_canonical`; unmatched → `ERR_VERSION_CONFLICT: match_patient_first`); the task's branch =
  the conversation's branch (central CS may flag for any branch; a branch role only for its allowed branch); kind klinis/layanan, triage /
  category as complaint_flag; the summary is the staff's own short description typed in the flag form (3–1000 chars) — the message body is NOT
  copied into the task (W-10: the message stays sealed; the clinician opens the thread link if an inbox role, or reads the summary); replay by
  key returns the existing task.
- **Routing to the doctor on duty**: reuse 0074's notification fan-out (klinis → doctor, nurse, pharmacist, facility_head of the branch; open
  point 2: "doctor on duty" = the branch's clinicians today; a roster filter is not in DEC-066 — keep branch-wide unless the reviewer finds a
  roster rule in 07/17).
- **CS sees only status**: reuse `complaint_reader` / `complaint_json(t, p_content)` (0074:499-533): a flagger outside the handlers sees the
  status of tasks they flagged without content. The inbox thread shows "Dilaporkan sebagai keluhan klinis · Terbuka/Ditangani/Selesai" for a
  flagged message (inbox_thread_get re-creation? — open point 3).
- **No clinical content in logs/events**: the domain event `ComplaintFlagged` carries ids/codes (task, branch, patient, message, kind, source);
  the audit reason code `complaint_flagged`; the notification references the task only.
- **TS**: `src/modules/messaging/inbox/flag.ts` — `flagMessage(db, key, messageId, { kind, triage?, category?, summary })` → runCommand with a
  body fingerprint of ids + kind + a digest of the summary.
